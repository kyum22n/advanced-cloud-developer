# 설계 산출물 — 나만의 업무 앱 · 웹 테트리스 게임

> 3차시 「나만의 업무 앱 만들기」의 **두 애플리케이션**을 **dev · stg · prd 세 배포 환경**에서
> 구성 · 개발 · 테스트(단위 · 통합 · E2E)까지 수행하는 데 필요한 설계 산출물입니다.
> 실행 스크립트는 [`배포/`](../배포/README.md), 실습 절차는 [`실습자료/3차시_…프롬프트.md`](../실습자료/3차시_나만의업무앱만들기_실습_프롬프트.md) 를 참조합니다.

## 0. 대상 애플리케이션

| ID | 애플리케이션 | 성격 | 상태 보관 | 대응 실습 |
| --- | --- | --- | --- | --- |
| **APP-A** | **나만의 업무 앱** | 데이터 CRUD + 주차 집계 + 리포트 | **있음** (PostgreSQL) | Part D 통합 프롬프트 0~⑤ |
| **APP-B** | **웹 테트리스 게임** | 브라우저 단독 실행(정적) | **없음** (클라이언트 메모리) | Part G Advisor Strategy |

> 두 앱은 «상태를 가진 앱»과 «상태가 없는 앱»의 **대조 사례**입니다. 같은 배포 파이프라인이 두 성격을 어떻게 다르게 다루는지가 이 설계의 학습 포인트입니다.

## 1. 문서 구조 — 왜 이렇게 나눴는가 (MECE)

설계 문서를 «환경별로 3벌 복사»하면 **같은 내용이 세 곳에 흩어져** 수정이 누락됩니다.
그래서 **바뀌지 않는 것**과 **환경에 따라 바뀌는 것**을 먼저 가르고, 각각을 한 곳에만 둡니다.

```
                    ┌──────────────────────────────────────────┐
                    │  공통/  — 환경이 바뀌어도 동일한 설계        │
                    │  «무엇을 만드는가»                          │
                    │  기능 · 도메인/클래스 · API 계약 ·          │
                    │  시퀀스/상태 · 데이터 모델 · 테스트 케이스   │
                    └───────────────────┬──────────────────────┘
                                        │ 참조(단일 원천)
              ┌─────────────────────────┼─────────────────────────┐
              ▼                         ▼                         ▼
     ┌────────────────┐        ┌────────────────┐        ┌────────────────┐
     │  dev/          │        │  stg/          │        │  prd/          │
     │ «어디에 어떻게   │        │ «어떤 방식으로   │        │ «어떻게 살아남게 │
     │   올리는가»     │        │   올리는가»     │        │   올리는가»     │
     │ 아키텍처·프로세스│        │ +GitOps        │        │ +PaaS·가용성    │
     │ ·구성·테스트범위 │        │  드리프트 교정  │        │ ·보안·운영·이행 │
     └────────────────┘        └────────────────┘        └────────────────┘
```

| 폴더 | 담는 것 | 담지 않는 것 |
| --- | --- | --- |
| **공통/** | 기능·도메인·API 계약·시퀀스·데이터 모델·테스트 케이스 정의 · **자격 증명 유형과 선택 규칙** | 인프라·배포 방식·환경 값 · 어떤 리소스에 실제 적용했는가 |
| **dev/ · stg/ · prd/** | 아키텍처(토폴로지)·배포 프로세스·구성 값·환경별 테스트 범위 | 기능 정의·API 계약(공통을 참조만) |

## 3. 문서 간 추적성 — 하나가 바뀌면 무엇을 같이 고쳐야 하나

```
  기능명세서            도메인·클래스        REST API           데이터 모델
  FR-A-01 ─────┐        ClassA ──┐          POST /api/items    items 테이블
  AC-A-01 ─┐   │                 │                 │                 │
           │   └────────────────►│◄────────────────┘                 │
           │                     ▼                                   │
           │              시퀀스·상태 설계서 ◄─────────────────────────┘
           │                     │
           └────────────────────►▼
                          테스트 설계서
                    U-xx(단위) · I-xx(통합) · E-xx(E2E)
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
              dev 테스트설계 stg 테스트설계 prd 테스트설계
              (범위·판정)    (+GitOps)      (+읽기전용·운영기준)
```

| 변경이 생기면 | 반드시 함께 갱신 |
| --- | --- |
| 기능 추가/변경 (FR) | 인수조건(AC) → API 설계서 → 테스트 케이스 → 환경별 테스트 범위 |
| API 스키마 변경 | 클래스 설계서(DTO) → 시퀀스 → 통합 TC → E2E TC |
| 테이블 변경 | 데이터 모델 → 마이그레이션 → 통합 TC |
| 환경 값 변경 | 해당 환경 구성 설계서 → `배포/<env>/config/` |
