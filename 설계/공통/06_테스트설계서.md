## 1. 테스트 전략

### 1-1. 테스트 피라미드 — 왜 나누는가

```
                    ┌──────────────┐
                    │   E2E (4~5)  │  느림 · 비쌈 · 불안정
                    │ 브라우저 실행 │  «사용자가 실제로 쓸 수 있나»
                    └──────────────┘
              ┌────────────────────────┐
              │    통합 (6~8)          │  중간 · 실제 DB·API
              │  API + DB 연동 검증     │  «연결이 맞나»
              └────────────────────────┘
        ┌──────────────────────────────────┐
        │         단위 (11~25)              │  빠름 · 쌈 · 안정
        │  순수 로직 — DB·브라우저 불필요    │  «내 계산이 맞나»
        └──────────────────────────────────┘
```

| 원칙 | 내용 |
| --- | --- |
| **아래에서 먼저 거른다** | 단위에서 잡을 수 있는 결함을 E2E 까지 끌고 가면 **진단 비용이 수십 배**가 된다 |
| **위로 갈수록 적게** | E2E 는 «대표 경로»만. 모든 조합을 E2E 로 검증하지 않는다 |
| **각 레벨은 다른 것을 본다** | 같은 것을 세 번 보는 것은 **중복(MECE 위반)** |

### 1-2. 레벨 정의

| 레벨 | 검증 대상 | 외부 의존 | 실행 도구 | 실행 위치 | 소요 |
| --- | --- | --- | --- | --- | --- |
| **단위(Unit)** | 순수 함수(URL 파싱·오류 매핑·구조 요약·주제 도출·아키텍처 추정·비밀 출처 선택) · 게임 엔진 | **없음** | `node --test` | 로컬/CI (배포 무관) | < 1초 |
| **통합(Integration)** | HTTP API + SQLite + 실제 GitHub/Notion API 왕복 | **배포된 앱** · 외부 GitHub/Notion API | `node --test` + `fetch` | 배포 후 | 2~5초 |
| **E2E** | 브라우저 → 화면 → API → GitHub/Notion 전 구간 | **배포된 앱 · 브라우저** | Playwright | 배포 후 | 10~90초 |

### 1-3. 판정 규칙

| 규칙 | 내용 |
| --- | --- |
| **게이트** | 단위 실패 → 통합·E2E 를 실행하지 않는다(파이프라인 중단) |
| **증거** | E2E 는 **캡처 파일**을 남겨야 통과로 인정 |
| **리포트** | 모든 레벨이 `배포/<env>/reports/<env>_<kind>_*.json` 에 결과 기록 |
| **개인정보** | 캡처·리포트에 실제 개인정보(커밋 작성자 이메일 등)가 없어야 통과 (NFR-05) |

> **AC-A-05(Rate Limit)** 는 통합·E2E 로 실시간 재현하기 어려워(인증 시 5,000회/시간이라 소진 자체가 오래 걸림) 단위 테스트(`mapGithubError` 의 403→429 매핑)로 결정론적으로 고정했습니다. 실제 소진 재현 기록은 [실습산출물/3차시/08_업로드실패조사.md](../../실습산출물/3차시/08_업로드실패조사.md) 를 참조합니다.

## 6. 테스트 데이터 · 환경 전략

### 6-1. 데이터 준비

| 레벨 | 준비 방식 | 정리 |
| --- | --- | --- |
| 단위 | **코드 내 리터럴**(가짜 README·구조·오류 객체) — 외부 데이터 없음 | 불필요 |
| 통합 | **실제 공개 GitHub 레포**(`octocat/Hello-World` 등) — 개인정보 없는 공개 데이터 | 불필요(누적 허용) |
| E2E | 위와 동일 + 실행 시각 기반 구분 없이 반복 실행 가능 | 불필요(누적 허용) |

> 📌 **왜 실제 공개 레포를 쓰는가** — 이 앱은 «GitHub 공개 레포를 분석»하는 것이 기능 자체이므로, 가짜 레포보다 **실제 공개 레포**(개인정보 없는 오픈소스)가 더 정확한 검증입니다. 커밋 작성자 이메일 등은 애초에 리포트에 포함하지 않으므로(U-A-04) 개인정보 걱정 없이 반복 실행할 수 있습니다.

### 6-2. 환경 변수 (테스트 러너 주입)

| 변수 | 용도 | dev | stg | prd |
| --- | --- | --- | --- | --- |

## 7. 결함 관리 · 재실행 규칙

| 상황 | 조치 |
| --- | --- |
| 단위 실패 | **파이프라인 즉시 중단** — 코드 수정 후 재실행 |
| 통합 실패 (I-A-02 `/readyz` 503) | SQLite 파일 접근 불가 → **구성 설계서** 확인 |
| 통합 실패 (I-A-11 버전 불일치) | 배포가 반영되지 않음 → **배포 단계 재확인** |
| E2E 실패 (타임아웃) | 앱 미배포 또는 URL 오류 → `BASE_URL` 확인 |
| E2E 실패 (요소 못 찾음) | 화면 변경 시 요소 ID 동기화 필요 |
| **간헐적 실패(flaky)** | 재시도로 넘어가지 말고 **원인을 기록** — 대기 조건을 명시적으로(특히 E-A-06·07 은 "업로드 중..." 중간 상태를 최종 상태로 오인하지 않도록 `toContainText` 로 최종 문구를 기다림) |

### 7-1. 안정성 규칙

| 규칙 | 이유 |
| --- | --- |
| 고정 대기(`sleep`) 대신 **조건 대기** | 환경 속도 차이에 강해진다 |
| 요소 선택은 **`id` 셀렉터** 우선 | 문구·스타일 변경에 깨지지 않는다 |
| 테스트 간 **순서 의존 금지** | 병렬·부분 실행이 가능해진다 |
| 통합·E2E 는 **배포 검증 후 실행** | 앱이 준비되지 않은 상태의 실패는 정보가 아니다 |

## 9. myapp 고유 참고 — 공통 샘플 앱과의 차이

이 문서(공통 06)는 원래 `배포/common/app`(Postgres 기반 범용 샘플)을 기준으로 작성됐던 TC 카탈로그를, **실습산출물/3차시/myapp**(레포 인사이트, SQLite + GitHub/Notion API)에 맞게 갱신한 것입니다.

| 항목 | 공통 샘플 앱(`배포/common/app`) | myapp(레포 인사이트) |
| --- | --- | --- |
| 데이터 저장 | PostgreSQL(컨테이너/PaaS) | **SQLite(파일, 3환경 공통)** — [공통 05 §5](05_데이터모델설계서.md) |
| prd 비밀 없는 접근 대상 | DB 비밀번호 → Entra 토큰 | **GitHub PAT·Notion 토큰 → Key Vault**(값은 여전히 필요 — 서드파티 SaaS는 Entra 미지원) |
| 쓰기 TC 의 부수 효과 | 자체 DB 레코드 생성만 | **실제 Notion 워크스페이스에 페이지 생성** — prd 에서 반드시 skip 해야 하는 이유가 하나 더 있음 |
