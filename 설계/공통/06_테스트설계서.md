# 06. 테스트 설계서 (공통)

> **답하는 질문**: «무엇을 어떤 수준에서 검증하는가»
> **범위**: 테스트 전략 · 레벨 정의 · **TC 카탈로그(단위 · 통합 · E2E)** · 추적성
> **환경별 실행 범위·판정 기준**은 각 환경의 `04_테스트설계서_<env>.md` 를 참조합니다.

## 1. 테스트 전략

### 1-1. 테스트 피라미드 — 왜 나누는가

```
                    ┌──────────────┐
                    │   E2E (4~5)  │  느림 · 비쌈 · 불안정
                    │ 브라우저 실행 │  «사용자가 실제로 쓸 수 있나»
                    └──────────────┘
              ┌────────────────────────┐
              │    통합 (6~8)          │  중간 · 실제 DB·API
              │  API + DB 연동 검증     │  «연결이 맞나»
              └────────────────────────┘
        ┌──────────────────────────────────┐
        │         단위 (12~14)              │  빠름 · 쌈 · 안정
        │  순수 로직 — DB·브라우저 불필요    │  «내 계산이 맞나»
        └──────────────────────────────────┘
```

| 원칙 | 내용 |
| --- | --- |
| **아래에서 먼저 거른다** | 단위에서 잡을 수 있는 결함을 E2E 까지 끌고 가면 **진단 비용이 수십 배**가 된다 |
| **위로 갈수록 적게** | E2E 는 «대표 경로»만. 모든 조합을 E2E 로 검증하지 않는다 |
| **각 레벨은 다른 것을 본다** | 같은 것을 세 번 보는 것은 **중복(MECE 위반)** |

### 1-2. 레벨 정의

| 레벨 | 검증 대상 | 외부 의존 | 실행 도구 | 실행 위치 | 소요 |
| --- | --- | --- | --- | --- | --- |
| **단위(Unit)** | 순수 함수 · 게임 엔진 | **없음** | `node --test` | 로컬/CI (배포 무관) | < 5초 |
| **통합(Integration)** | HTTP API + DB + 설정 주입 | **배포된 앱 · DB** | `node --test` + `fetch` | 배포 후 | 10~30초 |
| **E2E** | 브라우저 → 화면 → API → DB 전 구간 | **배포된 앱 · 브라우저** | Playwright | 배포 후 | 30~90초 |

### 1-3. 판정 규칙

| 규칙 | 내용 |
| --- | --- |
| **게이트** | 단위 실패 → 통합·E2E 를 실행하지 않는다(파이프라인 중단) |
| **증거** | E2E 는 **캡처 파일**을 남겨야 통과로 인정 |
| **리포트** | 모든 레벨이 `배포/<env>/reports/<env>_<kind>_*.json` 에 결과 기록 |
| **개인정보** | 캡처·리포트에 실제 개인정보가 없어야 통과 (NFR-05) |

## 6. 테스트 데이터 · 환경 전략

### 6-1. 데이터 준비

| 레벨 | 준비 방식 | 정리 |
| --- | --- | --- |
| 단위 | **코드 내 리터럴** (외부 데이터 없음) | 불필요 |
| 통합 | 실행 시각 기반 **고유 제목** (`통합테스트-<ts>`) | 불필요(누적 허용) |
| E2E | 실행 시각 기반 **고유 제목** (`E2E-<ts>`) | 불필요(누적 허용) |

> 📌 **왜 정리하지 않는가** — 삭제 API 가 없고, 고유 제목으로 충돌을 피하므로 **반복 실행이 안전**합니다. 운영에서는 애초에 쓰기를 하지 않습니다.

### 6-2. 환경 변수 (테스트 러너 주입)

| 변수 | 용도 | dev | stg | prd |
| --- | --- | --- | --- | --- |
| `BASE_URL` | 대상 엔드포인트 | `http://localhost:8080` | LB IP | Ingress IP |
| `APP_ENV` | 캡처 파일 접두어 | `dev` | `stg` | `prd` |
| `ALLOW_WRITE` | 쓰기 TC 실행 여부 | `true` | `true` | **`false`** |

## 7. 결함 관리 · 재실행 규칙

| 상황 | 조치 |
| --- | --- |
| 단위 실패 | **파이프라인 즉시 중단** — 코드 수정 후 재실행 |
| 통합 실패 (I-A-02 `/readyz` 503) | DB 준비 대기 → 재시도. 지속되면 **구성 설계서** 확인 |
| 통합 실패 (I-A-08 버전 불일치) | 배포가 반영되지 않음 → **배포 단계 재확인** |
| E2E 실패 (타임아웃) | 앱 미배포 또는 URL 오류 → `BASE_URL` 확인 |
| E2E 실패 (요소 못 찾음) | 화면 변경 시 `data-testid` 동기화 필요 |
| **간헐적 실패(flaky)** | 재시도로 넘어가지 말고 **원인을 기록** — 대기 조건을 명시적으로 |

### 7-1. 안정성 규칙

| 규칙 | 이유 |
| --- | --- |
| 고정 대기(`sleep`) 대신 **조건 대기** | 환경 속도 차이에 강해진다 |
| 요소 선택은 **`data-testid`** 우선 | 문구·스타일 변경에 깨지지 않는다 |
| 테스트 간 **순서 의존 금지** | 병렬·부분 실행이 가능해진다 |
| 통합·E2E 는 **배포 검증 후 실행** | 앱이 준비되지 않은 상태의 실패는 정보가 아니다 |
