# 배포 스크립트 조정 — myapp(레포 인사이트) 대응

작성일: 2026-08-28

## 0. 내 앱의 실제 구조 (조정 전 파악)

| 항목 | 값 |
|---|---|
| 런타임 | Node.js (Express) — `myapp/server.js` |
| 포트 | `process.env.PORT \|\| 4000` (컨테이너에서는 `PORT=8080`으로 주입해 기존 배포 스크립트의 8080 관례에 맞춤) |
| DB | **better-sqlite3**(파일 기반 임베디드 DB, `data/app.db`) — 별도 DB 서버·서비스 불필요 |
| 빌드 명령 | 컴파일 단계 없음 — `npm install` → `npm start`(`node server.js`) |
| 헬스 엔드포인트 | 조정 전: 없음 → 이번 작업에서 `/healthz`·`/readyz`·`/version` 추가 |
| 테스트 | 조정 전: `node --test test/*.test.js` 단일 스위트 → 이번 작업에서 단위/통합/E2E 3분리 |

기존 `배포/*` 9단계 스크립트는 원래 `배포/common/app`(Node+PostgreSQL 샘플)을 기준으로 작성돼 있었고, `common/lib.ps1`의 `Resolve-AppPath`가 `실습산출물/3차시/myapp`에 `Dockerfile`이 있으면 그쪽을 우선 사용하도록 이미 설계돼 있었다(즉 애초에 myapp을 대상으로 쓸 수 있게 만들어져 있었으나, myapp에 Dockerfile이 없어 지금까지 샘플 앱으로만 동작해왔다).

## 1. 수정·추가한 파일 목록과 이유

### 1-1. `실습산출물/3차시/myapp/` (앱 코드)

| 파일 | 변경 | 이유 |
|---|---|---|
| `server.js` | `/healthz`·`/readyz`·`/version` 추가 | 80_verify.ps1이 이 3개 엔드포인트를 검사한다. `/readyz`는 `db.prepare('SELECT 1').get()`으로 **실제 DB 연결**을 확인(단순 프로세스 생존과 구분) |
| `Dockerfile` | 신규 생성 | myapp에는 원래 컨테이너 이미지가 없었음(목업용 nginx Dockerfile만 존재). Node 22-slim 기반 멀티스테이지로 신규 작성 |
| `.dockerignore` | 신규 생성 | `node_modules`·`.env`·테스트 산출물이 이미지에 들어가지 않도록 |
| `test/unit/*.test.js` | `test/*.test.js`에서 이동 | 03_테스트시나리오.xlsx [단위] 시트 구조(단위/통합/E2E 분리)에 맞춤. `require` 상대경로 보정 |
| `test/integration/api.test.js` | 신규 생성 | [통합] 시트 TC-I1·I2·I5·I6·I7(+I4 분기)을 배포된 앱(BASE_URL)에 대한 실제 HTTP 호출로 옮김 |
| `test/e2e/app.spec.js` | 신규 생성 | [E2E] 시트 TC-E1~E7을 Playwright 시나리오로 옮김. 캡처는 `test/e2e/캡처/`에 저장(70_test_e2e.ps1이 이 경로를 센다) |
| `playwright.config.js` | 신규 생성 | `배포/common/app`과 동일한 구조로 E2E 실행 설정 |
| `package.json` | `test:unit`/`test:integration`/`test:e2e` 스크립트 추가, `@playwright/test` devDependency 추가 | 50/60/70_*.ps1이 호출하는 npm 스크립트 이름과 일치시킴(`배포/common/app/package.json`과 동일한 이름 규칙) |
| `src/github.js` | `mapGithubError()` 순수 함수로 분리 | GitHub API 호출 없이도 404/403(Rate Limit) 매핑을 단위 테스트로 검증할 수 있게 함(AC4·AC5의 결정론적 커버리지) |

### 1-2. `배포/dev/`

| 파일 | 변경 | 이유 |
|---|---|---|
| `20_config.ps1` | Postgres 배포 단계 제거, `myapp-config`에서 `DB_*` 키 제거, `myapp-secret`을 `GITHUB_TOKEN`·`NOTION_TOKEN`·`NOTION_PARENT_PAGE_ID`(환경 변수에서만 읽음)로 교체. k3d 클러스터 생성 직후 kubeconfig의 `host.docker.internal`을 `127.0.0.1`로 보정하는 로직 추가 | myapp은 SQLite라 Postgres가 불필요. 이 Windows/Docker Desktop 환경에서 `host.docker.internal`이 호스트에서 라우팅되지 않아 kubectl이 API 서버에 연결 못 하는 문제를 실제로 만나 근본 수정 |
| `40_deploy.ps1` | `kubectl set image`/`set env`의 인자 구성 방식을 `"$name=$val"` 한 토큰으로 보간하도록 수정 | `deploy/$name` 뒤에 `$name="$val"`를 이어 쓰면 PowerShell 네이티브 인자 전달 과정에서 토큰이 `deploy/`와 `=...`로 쪼개지는 실제 버그를 발견(`kubectl set image` 실패로 재현) |
| `config/env.dev.json` | `db` 블록을 `embedded-sqlite` 모드로 교체(`passwordEnvVar` 등 미사용 키 제거) | 20_config.ps1이 더 이상 참조하지 않는 값이 설정 파일에 남아 혼동을 주는 것을 방지 |
| `Dockerfile`(myapp, 위 표와 동일) | — | (dev 파이프라인이 직접 빌드하는 대상) |

`postgres.yaml`은 삭제하지 않고 그대로 남겨 두었다(적용만 하지 않음) — 다른 3차시 앱(공통 샘플)과 구조를 비교·학습할 수 있도록 원칙("구조가 같아야 비교·학습이 된다")을 지킴.

### 1-3. `배포/stg/`, `배포/prd/` (적용만 함, 이번 세션에서 실행 검증은 dev만)

| 파일 | 변경 | 이유 |
|---|---|---|
| `stg/20_config.ps1` | `myapp-secret`에 `GITHUB_TOKEN`·`NOTION_TOKEN`·`NOTION_PARENT_PAGE_ID` 추가(기존 `DB_PASSWORD`는 유지 — stg는 "배포 방식 자체" 검증이 목적이라 Postgres 인프라 학습 코드는 건드리지 않음) | myapp이 실제로 쓰는 값이 컨테이너까지 전달되게 하려면 Secret에 해당 키가 있어야 함(Deployment는 이미 `envFrom: secretRef`로 전체를 주입하므로 Deployment 자체는 변경 불필요) |
| `prd/20_config.ps1` | Key Vault에 `github-token`·`notion-token`·`notion-parent-page-id` 저장 로직 추가(값 없으면 경고 후 빈 값 저장, 화면에 출력하지 않음) | 동일 이유. 기존 PostgreSQL·Redis·Storage 프로비저닝(수업의 Azure PaaS 학습 목적)은 손대지 않음 |
| `prd/config/k8s/base/secretprovider.yaml` | Key Vault 오브젝트 3개(`github-token` 등) 및 `myapp-secret` 매핑 추가 | 위 Key Vault 저장값을 파드가 읽을 수 있도록 CSI 매핑 필요 |
| `prd/config/k8s/base/deployment.yaml` | `data`라는 `emptyDir` 볼륨을 추가해 `/app/data`에 마운트 | `readOnlyRootFilesystem: true`인 prd 컨테이너에서 better-sqlite3가 파일을 쓸 수 있는 경로가 없으면 앱이 뜨자마자 실패한다. **다만 emptyDir는 파드 재생성 시 데이터가 사라지는 비영속 저장소** — 운영에서는 Azure Files 등 PVC로 교체가 필요한 미해결 항목으로 남겨 둔다 |

`env.stg.json`·`env.prd.json`의 `app.containerPort`(8080)·`test.baseUrl`은 이미 myapp 구조(컨테이너 내부 `PORT=8080`으로 기동)에 맞게 설정돼 있어 **변경하지 않았다**. stg/prd의 `deployment.yaml` 프로브 경로(`/healthz`·`/readyz`)도 이미 이번에 추가한 엔드포인트와 일치해 변경하지 않았다. 50/60/70_*.ps1도 이미 `npm run test:unit`/`test:integration`/`npx playwright test`를 호출하고 있어 myapp의 새 `package.json` 스크립트 이름과 그대로 맞는다(변경 불필요).

## 2. dev `run_all.ps1` 실행 중 발견·수정한 버그 (근본 원인 포함)

전체 파이프라인을 실제로 여러 차례 클린 상태(`90_cleanup.ps1 -Force` → `run_all.ps1`)로 돌려가며 다음 문제를 실제로 재현하고 고쳤다.

| # | 증상 | 근본 원인 | 조치 |
|---|---|---|---|
| 1 | `10_prereq.ps1`에서 호스트 포트 8080 충돌 | 이전 세션에서 만든 동일 이름의 k3d 클러스터가 API 서버 응답 없이 좀비 상태로 남아 있었음 | `90_cleanup.ps1 -Force`로 정리 후 재생성(dev는 언제든 버려도 되는 디스포저블 환경) |
| 2 | `kubectl apply`가 `host.docker.internal` 접속 실패로 멈춤 | 이 Windows/Docker Desktop 환경에서 `host.docker.internal`이 호스트 자신에게는 라우팅되지 않음(컨테이너 안에서는 되지만 호스트에서 실행하는 kubectl은 안 됨) | `20_config.ps1`에 클러스터 생성 직후 kubeconfig 서버 주소를 `127.0.0.1`로 보정하는 로직 추가 |
| 3 | `kubectl set image ...` 가 `there is no need to specify a resource type as a separate argument` 오류 | `deploy/$name` 다음에 `$name="$val"`처럼 변수와 리터럴 `=`, 따옴표가 붙어 있으면 PowerShell이 네이티브 명령 인자를 쪼개 전달하는 버그성 동작 발생 | `"$name=$val"`처럼 **하나의 문자열로 보간**해서 한 토큰으로 전달하도록 수정 |
| 4 | 파드가 `CreateContainerConfigError` | `securityContext.runAsNonRoot: true`인데 이미지의 `USER app`이 숫자 UID가 아니어서 k8s가 non-root 여부를 검증 못함 | Dockerfile에서 `adduser -u 1001 ... && USER 1001`처럼 **숫자 UID**로 생성 |
| 5 | 컨테이너가 뜨자마자 `Exit Code 139`(세그폴트)로 반복 재시작 | `better-sqlite3@13`이 **Node ≥22**를 요구하는데 Dockerfile은 `node:20-alpine` 사용 → ABI 불일치로 DB 오픈 시점에 세그폴트(단순 require는 성공하지만 실제 SQLite 호출에서 죽음) | Dockerfile 베이스를 `node:22-slim`으로 교체(빌드 시 `npm install` 경고로 이미 힌트가 있었으나 처음엔 무시했던 부분 — 실제 원인으로 재확인) |
| 6 | E2E `TC-E6/E7`이 간헐적으로 실패 | Playwright 테스트가 `"업로드 중..."`(빈 문자열 아님)에서 바로 다음 단계로 넘어가 최종 상태 확인 전에 텍스트를 읽음 | `not.toBeEmpty()` 대신 `toContainText(/업로드 완료\|업로드 실패/, {timeout})`로 **최종 상태**를 기다리도록 수정 |

## 4. 남은 항목 (Post-MVP·후속 조치)

- prd `deployment.yaml`의 `/app/data` 볼륨이 현재 `emptyDir`(비영속)이다 — 파드가 재시작되면 SQLite 데이터가 사라진다. 실제 운영에서는 Azure Files(PVC) 등으로 교체가 필요하다.
- stg/prd 파이프라인은 이번 세션에서 **적용(코드 변경)까지만** 했고 **실제 Azure 리소스로 실행 검증은 하지 않았다**(AKS·Key Vault 등 실비용 리소스 생성이 필요해 별도 승인 사항).
- `배포/common/app/Dockerfile`도 동일한 `USER app`(비숫자 UID) 패턴을 가지고 있어 `runAsNonRoot: true`와 함께 쓰면 같은 문제가 재현될 수 있다 — 이번 작업 범위(myapp) 밖이라 수정하지 않았고, 참고로 남겨 둔다.
