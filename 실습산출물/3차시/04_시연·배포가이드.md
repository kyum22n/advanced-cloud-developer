### 발견한 문제 — SQLite 다중 레플리카(replicas=2) 정합성

`app.replicas=2`(Git의 desired state)로 배포된 상태에서는 앱 DB가 **pod별 로컬 SQLite**(공유 스토리지 없음)라서, 분석 생성 요청과 조회/업로드 요청이 LoadBalancer에 의해 서로 다른 pod로 라우팅되면 방금 만든 이력을 찾지 못해 `404`가 발생한다(통합테스트 TC-I1, 그리고 시연 리허설 4단계 Notion 업로드에서 각각 재현). 동일 원인으로, 스케일 조정 중 pod가 종료되면 그 pod의 SQLite에 있던 이력도 함께 사라진다(§0-1 이력 목록 리허설에서 실제로 관측).

이전 세션에서도 같은 문제를 겪었고(`git log`: `b1d1098` replicas 2→1 임시 조정 → `909b029` 1→2 원복) 이번에도 동일하게 **통합테스트·시연 리허설 동안만 replicas=1로 임시 조정 후, selfHeal 검증(G-05)과 최종 배포 상태를 위해 2로 원복**하는 방식으로 우회했다(설정 파일·코드는 변경하지 않음, `kubectl scale`만 사용). **근본 해결(Azure Files 등 공유 스토리지로 교체)은 이번 범위 밖의 미해결 항목으로 남긴다.**

### 참고 — `.env`와 stg Secret은 별개다

최초 재현 배포 직후 시연 4단계(Notion 업로드)에서 `HTTP 401`(토큰 없음)이 발생했다. `myapp/.env`에는 토큰이 있었지만, stg 배포는 `.env`를 전혀 읽지 않는다(이미지 빌드 시 `.dockerignore`로 제외됨). [`20_config.ps1:99-108`](../../배포/stg/20_config.ps1)이 자신을 실행하는 **PowerShell 세션의 환경변수**(`$env:GITHUB_TOKEN` 등)를 읽어 k8s Secret(`myapp-secret`)을 만드는데, 이번 재현 배포를 실행한 세션에는 그 값이 없어 빈 Secret이 만들어졌던 것이다. `$env:GITHUB_TOKEN`/`$env:NOTION_TOKEN`/`$env:NOTION_PARENT_PAGE_ID`를 지정한 뒤 동일한 `create secret --dry-run=client -o yaml | kubectl apply -f -` 로직으로 Secret을 갱신하고 `kubectl rollout restart`로 반영해 해결했다(스크립트·설정 파일은 변경하지 않음). **재현 배포 시 `20_config.ps1`을 실행하기 전에 해당 환경변수 3개를 먼저 지정해야 한다.**

## 2. 자주 나는 오류 재현 및 1차 방어

| 시나리오 | 방어 조치 |
|---|---|
| 빈 URL로 분석 실행 | `parseRepoUrl`이 형식 오류로 400 반환 → 화면에 안내 문구 표시(서버가 비어있는 문자열도 처리) |
| 존재하지 않는/비공개 레포 | GitHub 404 → 앱이 "비공개 레포이거나 존재하지 않는 레포입니다"로 변환해 안내 |
| GitHub Rate Limit 초과 | 403 → 429로 변환, 재시도 가능 시각(UTC) 안내 (실습 중 실제로 재현·확인됨) |
| 커밋 0건(빈 레포) | languageStats/commits가 빈 배열이어도 "커밋 없음", "언어 통계 없음"으로 정상 렌더(에러 아님) |
| Notion 토큰 미설정 | 401 + ".env 설정을 확인하세요" 안내, 토큰 값 자체는 절대 노출하지 않음 |
| 중복 커밋 SHA 수신 | `github.js`에서 SHA 기준 Set으로 중복 제거 후 저장 |

## 3. 배포 방법

로컬 실행 스크립트를 기본 배포 방법으로 채택(별도 인프라 불필요, 비개발자도 3줄로 구동 가능):

```bash
cd myapp
npm install
cp .env.example .env   # GITHUB_TOKEN, NOTION_TOKEN, NOTION_PARENT_PAGE_ID 채우기

```

컨테이너 배포는 `myapp/Dockerfile`(Node 22-slim 멀티스테이지)로 실제 지원되며, `배포/dev/run_all.ps1` 한 번으로 k3d 클러스터 생성부터 빌드·배포·테스트·검증까지 자동화되어 있습니다(§0 참고). 2단계에서 만든 nginx 기반 목업용 Dockerfile(`myapp/mockup/Dockerfile`)은 목업 화면 전용으로 별도 유지됩니다.
