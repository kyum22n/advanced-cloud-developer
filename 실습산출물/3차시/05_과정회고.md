## 3. 더 공부하면 좋을 주제 3가지

1. **상태를 가진 앱의 다중 레플리카 데이터 정합성** — 이번 myapp은 SQLite(파일)를 그대로 써서 `replicas>1`일 때 파드마다 데이터가 갈라지는 한계를 안고 있습니다(`설계/공통/05_데이터모델설계서.md` §5-1). PostgreSQL Flexible Server, 또는 최소한 PVC 공유 스토리지로 전환하는 실습이 다음 단계로 자연스럽습니다.
2. **Azure Entra ID 기반 서드파티 SaaS 인증 대안(OAuth App)** — GitHub/Notion은 Entra 페더레이션을 지원하지 않아 토큰이 끝까지 남았습니다. GitHub App/OAuth App, Notion의 향후 워크스페이스 레벨 SSO 등 "비밀을 더 줄일 수 있는" 대안을 조사해볼 가치가 있습니다.
3. **GitOps 드리프트 교정(selfHeal)의 실무 한계** — 웹 테트리스 stg 실습에서 selfHeal이 실제로 작동함을 확인했지만(`3차시_웹테트리스_...md` §3-2), "의도된 긴급 수동 변경"과 "실수로 인한 드리프트"를 구분하지 못한다는 한계는 다루지 않았습니다. Argo CD의 `syncPolicy` 예외 처리, 긴급 변경 절차를 더 공부하면 운영 안정성이 올라갑니다.

## 4. 팀 확산 체크리스트 (보안 · 권한 · 교육 · 비용)

### 보안
- [ ] `.env`/Key Vault에만 비밀을 두고, 코드·Git·이미지에 하드코딩된 값이 없는지 CI에서 자동 검사(`grep` 패턴 스캔)하는가
- [ ] `/version` 등 진단 엔드포인트가 비밀 "값"이 아니라 "출처"만 노출하는지 코드 리뷰 체크리스트에 포함했는가
- [ ] 배포 스크립트의 역할 부여가 전부 **리소스 범위**이고 **데이터 평면 역할**인지(구독 범위·`*Contributor` 금지) 확인했는가

### 권한
- [ ] 관리자/일반 역할 분리가 URL 파라미터 같은 "간이 스위치"에 머물러 있다면, 실제 로그인/SSO로 전환할 계획이 있는가(`01_앱기획_스펙.md`의 "실제 인증 아님" 한계 참고)
- [ ] 감사로그(누가·언제·무엇)가 관리자 전용 기능(삭제 등) 사용 시 성공/거부 양쪽 다 기록되는지 확인했는가

### 교육
- [ ] 신규 팀원이 `00_주제확정.md` → `04_시연·배포가이드.md` 순서로 문서만 보고 이 앱을 처음부터 재현할 수 있는가(문서 자가 완결성 점검)
- [ ] "왜 이렇게 설계했는가"(예: SQLite 선택, Key Vault 자가 복구 경로)에 대한 근거가 설계 문서에 남아 있어, 팀원이 같은 실수를 반복하지 않는가

### 비용
- [ ] dev(로컬 k3d)에서 충분히 검증한 뒤에만 stg/prd(실제 Azure 과금)로 넘어가는 게이트가 있는가
- [ ] 실습·검증이 끝난 stg/prd 리소스를 `90_cleanup.ps1` 등으로 즉시 정리하는 습관이 팀 전체에 있는가(웹 테트리스 stg가 실제로 이렇게 정리된 사례 참고)
- [ ] "이번 릴리스에서 실제로 Azure 리소스를 생성해야 하는가"를 매번 명시적으로 확인하는 절차가 있는가(myapp의 stg/prd처럼 비용 때문에 의도적으로 미룰 수 있는 선택지를 팀이 인지하고 있는가)

## 5. 3차시 stg·prd 실습 중 겪은 문제와 대응 (2026-08-29)

myapp(APP-A)의 stg·prd 실배포를 처음으로 시도하며 겪은 문제와 대응을 기록한다. 상세 과정·판정 근거는 [11_최종검토_대조.md](11_최종검토_대조.md) 참고.

| # | 문제 | 원인 | 대응 | 결과 |
