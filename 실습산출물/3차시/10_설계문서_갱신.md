## 변경한 문서별 요약 (무엇을·왜)

### 설계/공통/01_기능명세서.md
- FR-A-01~14, AC-A-01~08 을 "항목/주차별 집계" 도메인에서 "GitHub 레포 분석·프로젝트 주제 도출·아키텍처 추정·Notion 업로드·이력 관리·감사로그" 도메인으로 전면 교체(ID 체계 FR-A-*/AC-A-* 는 유지)
- 왜: 실제 myapp(`server.js`)이 하는 일과 스펙 문서가 완전히 달랐던 상태를 해소하기 위함
- APP-B(테트리스) FR-B/AC-B 는 손대지 않음 — 다른 앱이며 이미 정확함

### 설계/공통/03_REST_API_설계서.md
- 엔드포인트 요약·상세를 `/api/items`·`/api/summary` 에서 myapp 의 실제 10개 엔드포인트(`/api/analyze`, `/api/analyses`, `/api/analyses/:id`(GET/DELETE), `/api/analyses/:id/notion-upload`, `/api/audit-log`, `/api/env-status` 등)로 교체
- 왜: 문서상 계약과 `server.js` 의 실제 라우트가 완전히 어긋나 있었음 — 이제 서로 대조 가능
- 상태 코드 규칙에 401(Notion 미설정)·403(관리자 전용)·429(GitHub Rate Limit) 추가 — 실제 코드가 반환하는 코드와 일치시킴

### 설계/공통/05_데이터모델설계서.md
- ERD·테이블 정의를 `items`/`audit_log`(PostgreSQL)에서 `analysis`/`language_stat`/`commit_summary`/`report`/`audit_log`(SQLite, `db.js` 원문 그대로)로 교체
- 왜: myapp 은 SQLite 만 쓰고 PostgreSQL 을 전혀 쓰지 않으므로, 정본(`db.js`)과 문서를 일치시킴. §5-1 에 **"replicas>1 일 때 파드마다 SQLite 파일이 분리된다"는 실제 한계를 숨기지 않고 명시**

### 설계/공통/06_테스트설계서.md
- 단위(11) · 통합(11) · E2E(7) TC 카탈로그를 myapp 의 실제 테스트 파일(`test/unit/*.test.js` 등, 실행 시 25개 단위 테스트로 확인됨)에 맞게 재작성
- 왜: 추적성 매트릭스가 100% 이려면 TC 정의부터 실제 코드와 일치해야 함. AC-A-05(Rate Limit)는 통합·E2E 로 재현하기 어려워 **단위 테스트로 결정론적으로 고정**했다는 판단 근거를 명시
- §9 에 "공통 샘플 앱과 myapp 의 차이"를 별도 표로 남겨, 07(아이덴티티 설계서, 이번 범위 밖)와의 정합성을 유지

### 설계/dev|stg|prd/04_테스트설계서_*.md — §2 실행 범위 표만 갱신
- 새 TC-ID 체계(U-A-01~11, I-A-01~11, E-A-01~07)로 교체
- prd 는 GitHub 실제 호출·SQLite 쓰기·**실제 Notion 워크스페이스 부수 효과**가 있는 TC(I-A-03·06·08·09, E-A-03·04·06·07)를 모두 skip 으로 유지

### 설계/dev|stg|prd/03_구성설계서_*.md — §6/§7 설정 변경 영향 범위 표만 갱신
- dev: `db.name`/`db.user`/`db.passwordEnvVar` 행을 `db.secretEnvVars`(GITHUB_TOKEN 등) 행으로 교체 — 실제 `env.dev.json` 이 `db.mode: "embedded-sqlite"` 인 것과 일치
- stg: GitHub/Notion 토큰이 기존 `DB_PASSWORD` 와 함께 Secret 에 저장된다는 행 추가
- prd: `configmap.yaml` 의 `KEYVAULT_NAME` 치환, GitHub PAT·Notion 토큰 회전 절차 링크 추가 — 실제 `secretprovider.yaml`(`github-token`/`notion-token`/`notion-parent-page-id`)과 일치

| 항목 | 이유 |
|---|---|
| `설계/dev|stg|prd/01_아키텍처설계서_*.md`, `02_프로세스설계서_*.md` | 지시사항: "구조는 바꾸지 말 것" — 세 환경을 가로로 비교하는 학습 목적 보존 |
| `설계/공통/02_도메인·클래스설계서.md`, `04_시퀀스·상태설계서.md`, `07_아이덴티티·시크릿_설계서.md` | 이번 갱신 대상 목록(01·03·05·06)에 없었음 |
| `배포/*/config/k8s/base/configmap.yaml` 의 `DB_HOST`/`DB_PORT`/`DB_NAME` 등(공통 샘플 앱용 잔존 키) | myapp 은 사용하지 않지만 무해하며, 다른 3차시 앱과의 구조 비교 학습 목적으로 코스 차원에서 유지되는 값 — 이번 지시는 "설계 문서" 갱신이었고 배포 스크립트 자체 변경은 범위 밖 |
| `설계/dev|stg|prd/03·04` 의 §2/§6/§7 **이외** 내용(예: dev/03 §2~§5 의 ConfigMap 키 표, §6 결함 진단 가이드) | 지시사항이 "실행 범위 표만", "설정 변경 영향 범위 표만"으로 명시적으로 한정함 — 이 표들이 여전히 PostgreSQL 예시를 담고 있는 것은 알고 있으나, 범위를 벗어나는 수정이라 손대지 않음 |

> 마지막 항목은 criterion (b)와 표면적으로 긴장 관계가 있어 보일 수 있어 밝혀둡니다 — **이번에 갱신하도록 지시받은 표(§2 실행 범위, §6/§7 설정 변경 영향 범위)는 모두 실제 config 값과 일치**하도록 만들었고, 지시받지 않은 다른 표(ConfigMap 키 목록 등)는 원래 상태(공통 샘플 앱 기준)로 남아 있습니다. 이 잔여 불일치를 완전히 없애려면 다음 작업에서 dev|stg|prd 03 문서 전체를 갱신 대상으로 넓혀야 합니다.
