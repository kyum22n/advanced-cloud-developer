# 1단계 · Notion 업로드 실패 원인 조사

작성일: 2026-08-28

## 1. 결론 먼저

**Notion 업로드 코드 자체(`myapp/src/notion.js`, `server.js`)에는 버그가 없었습니다.** 로컬(npm start)과 dev(k3d 컨테이너) 양쪽에서 각각 3회씩, 총 **6회 연속 실제 업로드에 성공**했습니다(아래 §4 표). "실패"로 보였던 현상은 다음 두 가지가 원인이었고, 둘 다 **업로드 로직 자체의 버그가 아니라 조사·테스트 과정의 문제**였습니다.

| 원인 | 구분 | 근거 |
|---|---|---|
| ① 로컬에서 **오래된(stale) 서버 프로세스**가 계속 떠 있었음 | 환경 문제(코드 버그 아님) | §2 참고 |
| ② dev 파이프라인 **E2E 테스트의 타이밍(assertion) 버그** | 테스트 코드 버그(업로드 로직 버그 아님) | §3 참고 |

## 2. 원인 ① — 로컬의 오래된 서버 프로세스

로컬 4000번 포트를 점검한 결과, `/healthz`(6단계 배포 조정 때 추가한 엔드포인트)에는 404를 반환하면서 `/api/env-status`에는 정상 응답하는 프로세스가 떠 있었습니다.

```
curl localhost:4000/healthz        → 404 (있어야 할 라우트가 없음)
curl localhost:4000/api/env-status → 200 {"githubTokenSet":true, ...}
```

이는 **6단계(배포 스크립트 조정) 작업 초반, `/healthz` 라우트를 추가하기 훨씬 전에 기동된 오래된 `node server.js` 프로세스(PID 14184)가 그 이후 계속 재시작 없이 남아 있었다**는 뜻입니다. Node.js는 코드를 수정해도 이미 떠 있는 프로세스에 자동 반영되지 않으므로, 그 사이 어떤 테스트를 이 프로세스로 실행했다면 **실제로는 최신 코드가 아니라 옛날 코드로 실행된 결과**였을 수 있습니다.

- 조치: 해당 프로세스를 종료(`taskkill /PID 14184 /F`)하고 `node server.js`로 재기동
- 재기동 후 `/healthz` → `{"status":"ok","env":"local"}` 정상 확인

## 3. 원인 ② — dev E2E 테스트의 타이밍 버그 (실제 업로드 로직과는 별개)

`배포/dev/reports/`의 E2E 리포트를 시간순으로 대조한 결과:

| 리포트 파일 | 시각 | E2E 스위트 결과 |
|---|---|---|
| `dev_e2e_20260828-140412.json` | 14:04:12 | **Pass** |
| `dev_e2e_20260828-140824.json` | 14:08:24 | **Fail** (exit=1) ← 이 시점에 "실패"가 기록됨 |
| `dev_e2e_20260828-140852.json` | 14:08:52 | **Pass** (28초 뒤, 코드 수정 후 재실행) |
| `dev_e2e_20260828-141057.json` | 14:10:57 | **Pass** |

`14:08:24` 실패 건의 실제 원인은 `myapp/test/e2e/app.spec.js`의 **TC-E6/E7 assertion 로직**이었습니다(6단계에서 이미 발견·수정한 문제, `06_배포스크립트_조정.md` §2의 버그 #6과 동일 건):

- 업로드 버튼을 누르면 화면에 먼저 `"업로드 중..."`이라는 **중간 상태 문구**가 표시됩니다(이 자체도 빈 문자열이 아님).
- 수정 전 테스트는 `not.toBeEmpty()`로만 확인했기 때문에, **실제 업로드가 끝나기도 전에** "빈 문자열이 아니니 통과"로 오판하고 다음 줄에서 `"업로드 완료|업로드 실패"` 정규식 매칭에 실패한 것입니다.
- 즉 **Notion API 호출은 정상 진행 중이었고, 테스트 스크립트가 결과를 기다리지 않고 너무 일찍 값을 읽은 것**이 실패 원인입니다. Notion 쪽 응답 자체(401/403/429/500 등)와는 무관했습니다.

수정 내용(`test/e2e/app.spec.js`):
```diff
- await expect(page.locator('#notionStatus')).not.toBeEmpty({ timeout: 15000 });
- const text = await page.locator('#notionStatus').innerText();
- expect(text).toMatch(/업로드 완료|업로드 실패/);
+ await expect(page.locator('#notionStatus')).toContainText(/업로드 완료|업로드 실패/, { timeout: 15000 });
```

## 4. 환경 변수 주입 확인 (값은 출력하지 않음)

| 환경 | 확인 방법 | GITHUB_TOKEN | NOTION_TOKEN | NOTION_PARENT_PAGE_ID |
|---|---|---|---|---|
| 로컬(`.env`) | `GET /api/env-status` | 설정됨 | 설정됨 | 설정됨 |
| dev(k3d Secret) | `GET /api/env-status` (컨테이너 응답) | 설정됨 | 설정됨 | 설정됨 |

`/api/env-status`는 `Boolean(process.env.X)`만 반환하도록 설계되어 있어(`server.js` 144-150행) 값 자체는 어디에도 출력되지 않습니다.

## 5. 재현 테스트 — 분석→Notion 업로드 반복 실행 (각 환경 3회)

원인을 수정(로컬 프로세스 재기동, 테스트 assertion 수정)한 뒤, **서로 다른 3개 공개 레포**로 "분석 → Notion 업로드"를 로컬·dev 양쪽에서 각각 3회씩 실제로 실행했습니다.

### 로컬 (`npm start`, localhost:4000)

| 회차 | 레포 | 분석(POST /api/analyze) | Notion 업로드(POST /api/analyses/:id/notion-upload) |
|---|---|---|---|
| 1 | octocat/Hello-World | 200 OK | 200 OK (`app.notion.com`) |
| 2 | octocat/Spoon-Knife | 200 OK | 200 OK (`app.notion.com`) |
| 3 | expressjs/express | 200 OK | 200 OK (`app.notion.com`) |

### dev (k3d 컨테이너, localhost:8080)

| 회차 | 레포 | 분석(POST /api/analyze) | Notion 업로드(POST /api/analyses/:id/notion-upload) |
|---|---|---|---|
| 1 | octocat/Hello-World | 200 OK | 200 OK (`app.notion.com`) |
| 2 | octocat/Spoon-Knife | 200 OK | 200 OK (`app.notion.com`) |
| 3 | expressjs/express | 200 OK | 200 OK (`app.notion.com`) |

**6/6 전부 성공.** 응답 바디는 `{"notionUrl":"https://app.notion.com/p/..."}` 형태였고, 페이지 링크(비밀값 아님)만 확인했습니다.

## 6. 실패 시점 구분 (요청하신 ③ 항목)

| 가능한 실패 지점 | 이번 조사에서 실제로 발생했는가 |

| Notion API 호출 자체 실패(401/403/429/타임아웃 등) | 아니오 — 6회 모두 200, 토큰·페이지 권한 정상 |
| **테스트 코드의 타이밍(assertion) 버그** | **예 — 이것이 dev 리포트에 남은 유일한 "실패" 기록의 원인** |
| 로컬의 오래된 서버 프로세스로 인한 혼선 | **예 — 조사 시작 시점에 실제로 발견됨** |
