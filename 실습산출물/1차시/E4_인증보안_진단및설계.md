# 인증 보안 설정 진단 및 정책 설계안

> 본 실습은 **조회 전용**으로 진행했으며, 어떤 정책도 실제로 생성·수정·삭제하지 않았습니다. 실행한 명령 전체는 8절에 나열되어 있으며, 모두 GET(조회) 요청입니다.

---

## 1. MFA(다단계 인증)란? — 5줄 설명

MFA(Multi-Factor Authentication)는 로그인 시 비밀번호(지식 요소) 외에 인증 앱·전화·문자 같은 추가 요소(소유 요소)를 하나 더 요구해 본인 확인을 강화하는 기능입니다. 비밀번호만으로는 유출·추측·피싱에 취약하므로, 특히 관리자 계정이나 민감한 리소스에 접근할 때 추가 확인을 요구합니다. MFA 자체는 "언제 요구할지"를 스스로 정하지 않고, 이를 언제·누구에게·어떤 조건에서 발동시킬지는 **조건부 액세스(Conditional Access)** 정책이 결정합니다. 즉 조건부 액세스는 "IF(위치·기기·위험도 조건) THEN MFA 요구/차단" 형태의 규칙 엔진이고, MFA는 그 규칙이 호출하는 인증 수단 중 하나입니다. Premium 라이선스가 없는 경우에도 "보안 기본값(Security Defaults)"이라는 전체 계정 일괄 MFA 강제 옵션으로 최소한의 MFA를 켤 수 있습니다.

## 2. SSPR 구현 시 결정해야 할 3가지

| 결정 항목 | 선택지 | 고려 사항 |
|---|---|---|
| 대상 사용자 | 전체 사용자 / 특정 그룹만 | 전체 적용이 원칙적으로 안전하지만, 단계적 도입 시 IT팀·관리자 그룹부터 먼저 적용 후 확대하는 방식도 흔함 |
| 필요한 인증 방법 수 | 등록 시 1개 / 재설정 시 2개(권장) | 재설정처럼 민감한 작업은 등록보다 더 많은 인증 방법 확인을 요구하는 것이 일반적 |
| 사용 가능한 인증 방법 | 이메일 / 휴대폰(문자·통화) / 보안 질문 / 인증 앱 | 보안 질문은 추측·소셜엔지니어링에 취약해 최근에는 비권장 추세, 인증 앱·휴대폰 조합이 더 안전 |

## 3. 현재 테넌트 보안 설정 조회 결과

| 조회 항목 | 조회 방법(API) | 결과 |
|---|---|---|
| 보안 기본값(Security Defaults) 활성화 여부 | `GET /policies/identitySecurityDefaultsEnforcementPolicy` | **권한 부족으로 확인 불가** — `AccessDenied: required scopes are missing in the token` |
| 조건부 액세스 정책 존재 여부 | `GET /identity/conditionalAccess/policies` | **권한 부족으로 확인 불가** — 오류 메시지에 필요한 역할 명시: *Security Reader, Company Administrator, Security Administrator, Conditional Access Administrator, Global Reader, Devices Admin, Entra Network Access Administrator 중 하나 필요* |
| 인증 방법 정책(Authentication Methods Policy) | `GET /policies/authenticationMethodsPolicy` | **권한 부족으로 확인 불가** — `accessDenied: Request Authorization failed` |

**진단**: 세 조회 모두 이전 실습(E2, E3)에서 확인한 것과 같은 원인 — 이 계정에 **디렉터리 역할(Global Reader/Security Reader 등)이 전혀 없어서** 보안 설정 조회 자체가 차단됩니다. 오류 메시지가 친절하게 "어떤 역할이 있으면 되는지"까지 알려주고 있어, 해결 절차(7절)에 그대로 반영했습니다.

### 포털에서 확인하는 경로 (참고 — 실제 클릭은 권한이 있는 계정에서만 가능)

- 보안 기본값: `Microsoft Entra ID` → `속성(Properties)` → 하단 `보안 기본값 관리` 링크
- 조건부 액세스: `Microsoft Entra ID` → `보호(Protection)` → `조건부 액세스(Conditional Access)`

## 4. 권장 정책 설계안 (설계만 — 미적용)

### 시나리오 (a) 관리자 계정 로그인 시 MFA 필수

| 항목 | 내용 |
|---|---|
| 왜 필요한가 | 관리자 계정은 탈취 시 테넌트 전체에 영향을 미치므로, 일반 사용자보다 훨씬 엄격한 본인 확인이 필요함 |
| 적용 시 사용자 영향 | 관리자 역할 보유자만 로그인 시 추가 인증 1회 요구 — 일반 사용자는 영향 없음 |
| 롤백 방법 | 조건부 액세스 정책을 "사용 안 함(Report-only 또는 Off)"으로 전환하면 즉시 원복. 정책 삭제도 가능하나 우선 비활성화 권장(이력 보존) |

### 시나리오 (b) 신뢰할 수 없는 위치에서의 접근 차단

| 항목 | 내용 |
|---|---|
| 왜 필요한가 | 해외 이상 로그인, 알려지지 않은 IP 대역에서의 접근은 계정 탈취 시도일 가능성이 높음 |
| 적용 시 사용자 영향 | 사내망·허용된 국가/IP 목록 밖에서 접속 시 차단 또는 추가 인증 요구 — 재택·출장자는 VPN 또는 명명된 위치 등록 필요 |
| 롤백 방법 | 명명된 위치(Named Locations) 조건을 정책에서 제외하거나 정책 자체를 Off로 전환. 긴급 시 "긴급 액세스 계정(Break-glass account)"으로 우회 접근 확보 필요 |

### 시나리오 (c) 레거시 인증 프로토콜 차단

| 항목 | 내용 |
|---|---|
| 왜 필요한가 | POP·IMAP·기본 SMTP 인증 등 레거시 프로토콜은 MFA를 지원하지 않아 무차별 대입 공격(Brute-force)의 주요 경로가 됨 |
| 적용 시 사용자 영향 | 구형 이메일 클라이언트·일부 레거시 앱 연결이 끊길 수 있음 — 사전에 최신 인증(Modern Authentication) 지원 클라이언트로 전환 필요 |
| 롤백 방법 | 정책을 Report-only 모드로 되돌려 영향받는 사용자·앱을 먼저 파악한 뒤 재적용. 급한 경우 정책 Off로 즉시 원복 |

> 세 시나리오 모두 **먼저 "보고 전용(Report-only)" 모드로 켜서 영향받는 사용자를 관찰한 뒤 실제 적용(On)으로 전환**하는 단계적 롤아웃을 권장합니다.

## 5. 필요 라이선스

| 시나리오 | 필요 라이선스 | 비고 |
|---|---|---|
| (a) 관리자 MFA 필수 | **Premium P1** 이상 (조건부 액세스 정책 기능) | 라이선스가 없으면 "보안 기본값"으로 전체 사용자 일괄 MFA만 가능(세부 조건 설정 불가) |
| (b) 위치 기반 차단 | **Premium P1** 이상 | 명명된 위치(Named Locations) + 조건부 액세스 정책 필요 |
| (c) 레거시 인증 차단 | **Premium P1** 이상 | 클라이언트 앱 조건(레거시 인증 클라이언트) 기반 조건부 액세스 필요 |

세 시나리오 모두 최소 **P1**로 구현 가능하며, 위험 기반 조건(사용자 위험/로그인 위험 탐지)까지 추가하려면 **P2**(Identity Protection)가 필요합니다 — 단, 이는 이번 3개 시나리오의 필수 요건은 아닙니다.

## 6. 검증 (인수조건)

| 조건 | 결과 | 비고 |
|---|---|---|
| (a) 조회 결과가 실제 값 또는 '확인 불가' 사유와 함께 기록됨 | O | 3개 항목 모두 "권한 부족으로 확인 불가" + 구체적 오류 원인 기록 |
| (b) 정책 3개 설계안 완성 | O | (a)(b)(c) 시나리오 각각 왜 필요한가/사용자 영향/롤백 방법 포함 |
| (c) 어떤 정책도 실제로 생성·변경되지 않음 | O | 8절에 실행한 명령 전체 나열(전부 GET 조회) |

## 7. 해결 절차 (조회 권한을 확보하려면)

1. 학교 IT 관리자에게 본인 계정에 **Security Reader** 또는 **Global Reader** 디렉터리 역할 부여를 요청 (조회만 필요하면 이 정도로 충분, 정책 변경까지 필요하면 Conditional Access Administrator).
2. 역할 확보 후 3절의 세 API를 동일하게 재실행하면 실제 값(Security Defaults On/Off, 조건부 액세스 정책 개수 등)을 확인할 수 있음.
3. 권한 확보가 어렵다면, 강사 또는 Global Administrator 계정으로 포털에서 실제 값을 캡처해 공유받는 방식으로 대체.

## 8. 실행한 명령 목록 (정책 미변경 증명용 — 전부 GET)

```
az rest --method get --url "https://graph.microsoft.com/v1.0/policies/identitySecurityDefaultsEnforcementPolicy"
az rest --method get --url "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies"
az rest --method get --url "https://graph.microsoft.com/v1.0/policies/authenticationMethodsPolicy"
```

세 명령 모두 `--method get`(조회)이며, 생성(POST)·수정(PATCH)·삭제(DELETE) 명령은 어떤 것도 실행하지 않았습니다.
