# Azure Storage 선택 가이드 (실무 판단용)

이 문서는 "Azure Storage 서비스가 무엇인지"보다 **"지금 이 데이터를 어디에 둘 것인가"를 현장에서 바로 판단**할 수 있게 정리한 것입니다.

---

## 1. Azure Storage 4종 비교

| 종류 | 저장하는 데이터 형태 | 접근 방식 | 대표 사용 사례 | 한 줄 비유 |
|---|---|---|---|---|
| **Blob 컨테이너** | 비정형 바이너리(이미지, 동영상, 로그, 백업 파일 등) | REST(HTTPS), SDK | 웹사이트 이미지 서빙, 로그/백업 아카이브, 정적 웹사이트 호스팅 | "큰 창고에 상자를 쌓아두는 곳" — 상자 안 내용은 신경 안 씀 |
| **Tables** | 스키마가 느슨한 키-값/NoSQL 데이터 | REST(HTTPS), SDK | 사용자 세션 로그, IoT 센서 값처럼 구조는 있지만 관계형 DB까지는 필요 없는 데이터 | "칸이 고정되지 않은 엑셀표" — 행마다 다른 컬럼이 있어도 됨 |
| **큐(Queue)** | 짧은 텍스트/JSON 메시지 | REST(HTTPS), SDK | 주문 처리 파이프라인에서 "결제 완료" 메시지를 다음 서버가 처리하도록 전달 | "우체통" — 메시지를 넣어두면 순서대로 누군가 꺼내감 |
| **Files** | 파일/폴더 구조를 가진 공유 스토리지 | **SMB, NFS**, REST | 여러 VM이 같은 드라이브 문자(예: `Z:`)로 마운트해서 쓰는 공유 폴더, 레거시 앱의 파일서버 대체 | "회사 네트워크 드라이브" — 탐색기에서 폴더처럼 열림 |

**판단 기준 한 줄 요약**: 파일 그 자체(이미지·동영상·백업)면 Blob, 여러 서버가 폴더처럼 공유해야 하면 Files, 구조화된 레코드를 대량으로 빠르게 조회하면 Tables, 서버 간 비동기 작업 전달이면 큐.

## 2. 스토리지 계정 → 컨테이너 → Blob 구조

```
스토리지 계정 (예: stadvdevlkm001)
 └── 컨테이너 (예: images)
      ├── Blob: logo.png
      ├── Blob: banner-2026.jpg
      └── Blob: reports/2026-08.pdf   ← 폴더처럼 보이지만 실제로는 이름에 '/'가 들어간 것

 └── 컨테이너 (예: backups)
      └── Blob: db-backup-20260805.bak
```

- **스토리지 계정**은 최상위 컨테이너로, 접근 키·연결 문자열·지역·복제 방식(LRS/GRS 등)이 이 레벨에서 결정됩니다.
- **컨테이너**는 Blob들을 담는 논리적 폴더(1단계만 존재, 실제 하위 폴더 개념은 없음).
- **Blob**은 실제 파일 데이터.

### 계정 이름이 전역 고유(globally unique)여야 하는 이유

스토리지 계정 이름은 접속 URL의 일부(`https://<계정이름>.blob.core.windows.net/...`)로 쓰입니다. 이 URL은 Azure 전체 사용자가 공유하는 DNS 네임스페이스 위에 있기 때문에, 다른 회사·다른 구독의 계정과 이름이 겹치면 어느 쪽 데이터로 연결해야 할지 구분할 수 없습니다. 그래서 리소스 그룹이나 구독 범위가 아니라 **Azure 전체 범위**에서 유일해야 합니다.

## 3. Azure Files vs Azure Blob

| 기준 | Azure Files | Azure Blob |
|---|---|---|
| 인터페이스 | SMB/NFS(파일시스템처럼 마운트) + REST | REST(HTTP API) 중심 |
| 동시 접근 | 여러 클라이언트가 **동시에 읽기/쓰기** 가능 (파일 잠금 지원) | 동시 읽기는 자유롭지만, 쓰기 충돌 관리는 애플리케이션(REST 호출) 몫 |
| 리프트 앤 시프트 적합성 | **적합** — 기존에 "파일 서버(SMB 공유 폴더)"를 쓰던 온프레미스 앱을 코드 변경 없이 그대로 클라우드로 옮길 수 있음 | 부적합 — 앱이 REST API를 호출하도록 코드를 고쳐야 함 |

**Q. 여러 VM이 공유 폴더처럼 써야 한다면?**
→ **Azure Files.** 각 VM에서 `Z:` 드라이브(SMB)나 마운트 경로(NFS)로 붙여서 기존 파일 서버처럼 그대로 쓸 수 있습니다.

**Q. 웹에서 이미지를 직접 서빙해야 한다면?**
→ **Azure Blob.** 컨테이너를 공개 액세스로 설정하면 `https://.../images/logo.png` 형태의 URL로 브라우저가 직접 요청할 수 있고, CDN과도 자연스럽게 연동됩니다.

## 4. 액세스 계층(Hot / Cool / Archive)

| 계층 | 접근 빈도 | 최소 보관 기간 | 검색(꺼내기) 대기 시간 | 비용 성향 |
|---|---|---|---|---|
| **핫(Hot)** | 자주 접근 | 없음 | 즉시 | 저장 비용 높음 / 액세스(읽기) 비용 낮음 |
| **쿨(Cool)** | 가끔 접근(월 1회 미만 수준) | **30일** | 즉시 | 저장 비용 중간 / 액세스 비용 핫보다 높음 |
| **보관(Archive)** | 거의 접근 안 함(장기 보존용) | **180일** | 수 시간(수동 rehydrate 필요) | 저장 비용 가장 낮음 / 조기 삭제·꺼내기 비용 큼 |

**왜 30일·180일 기준이 등장하는가**: 각 계층은 "이 계층에 최소 이 기간만큼은 두고 있어야 손해가 안 난다"는 손익분기 기준을 갖고 있습니다. 저장 비용이 싼 대신 조기 삭제/계층 이동 시 위약금 성격의 요금(Early Deletion Fee)이 붙기 때문에, 실제 접근 패턴이 그 기간보다 짧으면 오히려 하위 계층으로 옮기는 게 손해입니다. 즉 30일/180일은 "이 계층을 선택했을 때 최소 이만큼은 보관해야 본전"이라는 관리형 계약 기간입니다.

## 5. 의사결정 트리 — "우리 회사 데이터를 Azure로 옮긴다면 어디에 둘 것인가"

```
데이터를 옮기려 한다
│
├─ Q1. 여러 서버가 "같은 폴더"처럼 동시에 읽고 써야 하는가? (예: 기존 파일 서버 이관)
│    └─ YES → Azure Files (SMB/NFS로 그대로 마운트)
│
├─ Q1이 NO라면 → Q2. 이미지/동영상/백업처럼 "파일 그 자체"를 저장/서빙하는가?
│    └─ YES → Azure Blob 컨테이너
│         │
│         └─ Q2-1. 이 파일에 지금 당장(또는 자주) 접근하는가?
│              ├─ 자주 접근 → Hot 계층
│              ├─ 가끔 접근(한 달에 한두 번 수준, 최소 30일 이상 보관 예정) → Cool 계층
│              └─ 규정 준수·감사용으로 장기 보관만 하고 거의 안 읽음(최소 180일 이상) → Archive 계층
│
├─ Q2도 NO라면 → Q3. 구조화된 레코드(속성이 늘었다 줄었다 하는 로그/센서 값 등)를
│                     빠르게 키 기반으로 조회해야 하는가?
│    └─ YES → Tables
│
└─ Q3도 NO라면 → Q4. 서버 A가 만든 작업을 서버 B가 순서대로 받아 처리해야 하는가?
     └─ YES → 큐(Queue)
```
