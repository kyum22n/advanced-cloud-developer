# 테스트 사용자 생성 & 최소 권한 역할 부여 실습 기록

## 1. 기존 사용자 이름 충돌 확인

`az ad user list --query "[?contains(userPrincipalName, 'test-lkm')].userPrincipalName" -o tsv` 조회 결과 **충돌 없음** → `test-lkm-01` 사용 가능한 것으로 확인.

## 2. 사용자 생성 시도 — **차단됨 (401)**

포털 경로([Microsoft Entra ID] → [사용자] → [+ 추가] → [사용자 생성])로 아래 값을 입력해 생성을 시도함:

| 항목 | 값 |
|---|---|
| 사용자 계정 이름 | `test-lkm-01@shinhan365.onmicrosoft.com` |
| 표시 이름 | `test-lkm-01` |
| 암호 | 자동 생성(Auto-generate) 옵션 사용 예정 |

**결과**: 생성 시도 단계에서 아래 오류 발생 (E2 테넌트 생성 실습과 **동일한 오류**):
```json
{"sessionId":"c21064963be1433c8c312dd93e8aed3b","subscriptionId":"","resourceGroup":"","errorCode":"401","resourceName":"","details":"권한이 부족하여 작업을 완료할 수 없습니다."}
```

### 원인 진단 (추가 확인)

막힌 지점이 정확히 어디인지 확인하기 위해 두 종류의 권한을 분리해서 점검함:

| 권한 종류 | 확인 명령 | 결과 |
|---|---|---|
| Azure RBAC (구독 범위) | `az role assignment list --assignee kyumni207@o.shinhan.ac.kr --all` | **Owner** 보유 — 구독 범위 리소스 관리·역할 할당 권한은 있음 |
| Microsoft Entra 디렉터리 역할 | `az rest .../me/memberOf` (E2 실습에서 확인) | **없음** — User Administrator 등 사용자 생성에 필요한 디렉터리 역할 미보유 |

**결론**: 막힌 원인은 "Azure 리소스 권한 부족"이 아니라 **"Microsoft Entra ID 디렉터리에 대한 관리자 역할이 없기 때문"**입니다. 이 계정은 구독 리소스는 Owner로서 자유롭게 다룰 수 있지만, 사용자·그룹 같은 디렉터리 객체 생성은 별도의 Entra 디렉터리 역할(User Administrator 등)이 필요하며, 신한대학교 조직 테넌트가 이를 일반 계정에 부여하지 않은 것으로 판단됩니다.

이 진단 덕분에, **"사용자만 있었다면 Reader 역할 부여(4단계)는 실제로 가능했을 것"**이라는 점도 함께 확인했습니다(Owner 권한은 역할 할당 쓰기(`Microsoft.Authorization/roleAssignments/write`)를 포함하므로).

## 3. 이후 단계(역할 부여·검증) — **수행 불가**

2단계에서 사용자 객체 자체가 생성되지 않았으므로, 아래 단계는 실제로 실행할 대상(개체 ID)이 없어 **수행하지 못했습니다**:
- 3단계: 사용자 [개요] 확인 (개체 ID / UPN / 사용자 유형)
- 4단계: `rg-advdev-<ini>` 범위 Reader 역할 부여
- 5단계: `az role assignment list --assignee <개체ID>`로 검증

참고로 대상 리소스 그룹 `rg-advdev-lkm`도 `az group exists` 조회 결과 **아직 존재하지 않음(false)** — 아직 Part E 5-5(VNet 실습) 이전 단계라 리소스 그룹이 없는 상태였습니다.

### 준비된 명령 (실행하지 않음 — 향후 사용자 생성 권한이 확보되면 그대로 사용 가능)

```powershell
# 4) 리소스 그룹 범위 Reader 역할 부여 (사용자 생성 후, <개체ID>를 실제 값으로 교체)
az role assignment create --assignee <개체ID> --role "Reader" --scope "/subscriptions/<구독ID>/resourceGroups/rg-advdev-lkm"

# 5) 부여 결과 검증
az role assignment list --assignee <개체ID> --output table

# 실습 종료 후 정리(삭제) — 실행 전 반드시 대상 재확인
az ad user delete --id <개체ID>   # 테스트 사용자 삭제 (실행 안 함 — 안내만)
```

## 4. Owner / Contributor / Reader 비교

| 역할 | 리소스 읽기 | 리소스 생성·수정·삭제 | 접근 권한(IAM) 관리 | 이번 실습 적용 여부 |
|---|---|---|---|---|
| **Owner** | O | O | O (다른 사용자에게 권한 부여 가능) | ❌ 사용 금지(원칙) |
| **Contributor** | O | O | X (권한 관리 불가) | 미사용 |
| **Reader** | O | X | X | ✅ 이번 실습 목표 역할(부여 시도했으나 사용자 생성 차단으로 미완료) |

### 왜 Reader인가 — 최소 권한 원칙(Least Privilege) 관점

테스트 계정은 "리소스가 잘 만들어졌는지 눈으로 확인"하는 용도이지 직접 리소스를 만들거나 지울 이유가 없으므로, 딱 그만큼의 권한인 Reader만 주는 것이 맞습니다. 필요 이상의 권한(Contributor·Owner)을 주면 테스트 계정이 탈취되거나 실수로 조작될 때의 피해 범위가 커지므로, "할 수 있는 일"을 "해야 하는 일"만큼으로 좁히는 것이 최소 권한 원칙의 핵심입니다. 특히 Owner는 다른 사람에게 권한을 재분배할 수 있어 파급력이 가장 크므로, 실습·테스트 계정에는 원천적으로 배제해야 합니다.

## 5. 검증 (인수조건)

| 조건 | 결과 | 비고 |
|---|---|---|
| (a) 사용자 목록에 새 계정이 보임 | **X** | 사용자 생성이 401로 차단되어 `test-lkm-01` 계정 자체가 존재하지 않음 |
| (b) 역할 할당 조회 결과에 Reader가 나옴 | **X** | 대상 사용자가 없어 역할 할당 자체를 실행하지 못함 |
| (c) Owner 역할이 부여되지 않음 | **O** | 애초에 어떤 역할도 부여되지 않았으므로 원칙 위반 없음(단, 목적 자체는 미달성) |
| (d) 암호가 어떤 파일에도 저장되지 않음 | **O** | 사용자 생성이 되지 않아 암호가 발급된 적 자체가 없음 |

**종합**: (a)(b)는 X — 이는 제 작업의 실패가 아니라 **조직 테넌트의 권한 정책(디렉터리 역할 없음)에 의한 차단**입니다. (c)(d)는 안전 원칙 위반이 없었다는 의미에서 O이나, 실습 목적(실제 Reader 역할이 살아있는 사용자에 부여된 상태 확인)은 달성하지 못했습니다.

## 6. 해결 절차

1. 학교 IT 관리자에게 본인 계정에 **User Administrator**(또는 그 이상) Entra 디렉터리 역할 부여를 요청 — 이후 3~5단계를 그대로 재실행 가능(본 문서 3절의 준비된 명령 재사용).
2. 또는 **개인 Microsoft 계정 + 개인 무료/체험 구독**으로 별도 테넌트를 만들어(가능하다면) 그 안에서 동일 실습 진행.
3. 권한 확보가 어렵다면, 강사에게 이미 User Administrator 역할이 있는 계정으로 데모를 요청하고, 본인은 결과 화면(개체 ID·역할 할당 목록)만 보고 이해하는 것으로 대체.

## 7. 테스트 사용자 삭제 안내 (실행하지 않음)

실습이 정상적으로 완료되어 `test-lkm-01` 사용자가 생성됐었다면, 실습 종료 후 아래 명령으로 정리합니다. **이번 세션에서는 사용자 자체가 없으므로 실행 대상이 없습니다.**

```powershell
# 삭제 전 반드시 대상 재확인
az ad user show --id test-lkm-01@shinhan365.onmicrosoft.com
# 확인 후 삭제 (실행 전 사용자 확인 필수)
az ad user delete --id test-lkm-01@shinhan365.onmicrosoft.com
```
