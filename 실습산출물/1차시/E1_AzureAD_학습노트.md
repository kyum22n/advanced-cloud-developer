# Azure AD(Microsoft Entra ID) 핵심 개념 학습 노트

> 강의자료에서는 "Azure AD"라는 명칭을 주로 사용하지만, 2023년부터 Microsoft의 공식 제품명은 **Microsoft Entra ID**로 변경되었습니다. 이 문서에서는 강의 용어를 기본으로 쓰고, 괄호로 현재 공식 명칭을 병기합니다.
> Part E~F 실습 매핑표(6절)는 강의자료(1차시-2-Application Developer 심화(서경진)-준비 및 기본 실습.pptx) 원문의 목차·슬라이드 번호와 대조해 작성했습니다. 그 외 개념 설명(1~5절)은 일반 Azure 지식을 기준으로 정리한 것이라 강의자료 표현과 세부 문구가 다를 수 있으며, 그런 부분은 "확인 필요"로 표시했습니다.

## 1. 핵심 용어 정리

| 용어 | 정의 | 한 줄 비유 | 포함 관계 |
|---|---|---|---|
| **ID(신원, Identity)** | 시스템이 "누구인지"를 판단하는 근거가 되는 정보 단위(사람, 앱, 서비스 등 모두 포함) | 신분증 그 자체의 개념 | 가장 상위의 추상 개념 — 아래 '계정'들은 모두 ID의 한 형태 |
| **계정(Account)** | 특정 시스템에 로그인하기 위해 실제로 발급된 자격 단위(로컬 계정, 회사 계정 등 포괄) | 특정 건물 출입증 한 장 | ID의 한 종류. Azure AD 계정은 계정의 하위 집합 |
| **Azure AD 계정(Microsoft Entra ID 계정)** | 특정 테넌트(디렉터리) 안에 등록되어 Azure AD가 인증을 책임지는 계정(예: user@company.onmicrosoft.com) | 특정 회사 건물에서만 통하는 사원증 | 반드시 하나의 테넌트에 소속됨 |
| **테넌트(디렉터리, Tenant/Directory)** | 조직 전용으로 격리된 Azure AD 인스턴스. 사용자·그룹·앱 등록 정보를 담는 논리적 컨테이너 | 회사 건물 한 채 (그 건물 안 사람만 그 건물 출입증 사용 가능) | 여러 Azure 구독을 신뢰(trust)할 수 있음. 하나의 테넌트 = 여러 구독의 상위 신뢰 컨테이너가 될 수 있음 |
| **구독(Subscription)** | Azure 리소스(VM, 스토리지 등)를 만들고 과금이 집계되는 단위 | 그 건물 안에서 쓰는 법인카드(비용 청구 단위) | 정확히 하나의 테넌트에 연결됨(신뢰 관계). 한 테넌트가 여러 구독을 가질 수 있음(1:N) |

**포함 관계 요약**: ID(추상) ⊃ 계정(일반) ⊃ Azure AD 계정(특정) / 테넌트는 Azure AD 계정들을 담는 그릇이며, 하나의 테넌트는 하나 이상의 구독과 신뢰 관계를 맺어 리소스 과금을 관리합니다.

## 2. 온프레미스 AD DS vs Azure AD(Microsoft Entra ID) 비교

| 구분 | 온프레미스 AD DS (Active Directory Domain Services) | Azure AD (Microsoft Entra ID) |
|---|---|---|
| 주요 인증 프로토콜 | Kerberos, NTLM | HTTP/S 기반 — SAML, OpenID Connect, OAuth 2.0 |
| 조직 구조 | OU(조직 구성 단위), GPO(그룹 정책 개체) 존재 | OU/GPO 개념 없음 — 대신 관리 단위(Administrative Unit), 조건부 액세스(Conditional Access) 정책 사용 |
| 조회(쿼리) 방식 | LDAP | Microsoft Graph 등 REST API |
| 주 대상 시나리오 | 사내망 도메인 가입 PC, 파일 서버·프린터 등 온프레미스 리소스 접근 제어 | SaaS 앱 로그인, 클라우드 리소스 접근, 모바일/원격 근무 환경의 SSO |
| 네트워크 전제 | 사내망/VPN 등 도메인 컨트롤러 접근 가능 환경 전제 | 인터넷 연결만 있으면 어디서든 접근 가능 |

**한 줄 요약**: AD DS는 "회사 건물 안에서만 통하는 출입 시스템", Azure AD는 "인터넷만 되면 세계 어디서든 통하는 신분 확인 서비스"입니다.

## 3. 라이선스 버전 비교

| 버전 | 주요 포함 기능 | 비고 |
|---|---|---|
| **무료(Free)** | 사용자·그룹 관리, 온프레미스 디렉터리 동기화, 기본 SSO | Azure 구독 생성 시 기본 제공 |
| **Microsoft 365 Apps용(구 Office 365 앱용)** | 무료 버전 기능 + 일부 SSPR(암호 재설정) 기능 등 | 정확한 세부 기능 차이는 **확인 필요** (Microsoft 공식 라이선싱 페이지 대조 권장) |
| **Premium P1** | 하이브리드 신원(하이브리드 Azure AD 조인), 조건부 액세스, 그룹 기반 액세스 관리, 고급 SSPR(자동 암호 롤백 등) | 대부분의 중소~중견 기업이 실무에서 사용하는 표준 라인 |
| **Premium P2** | P1의 모든 기능 + Identity Protection(위험 기반 로그인 탐지), PIM(Privileged Identity Management, 적시(Just-In-Time) 권한 상승) | 고위험 관리자 계정 보호, 규제 준수(컴플라이언스) 요구가 있는 조직 대상 |

> 각 버전의 정확한 기능 목록·가격은 시점에 따라 변동될 수 있어 **확인 필요**(Microsoft 공식 라이선싱 비교표 기준으로 재확인 권장).

### "우리 회사라면 어느 버전이 필요한가" 판단 기준 3가지

1. **하이브리드 환경 여부**: 온프레미스 AD DS와 Azure AD를 연동(동기화)해서 써야 하는가? → 필요하면 최소 P1 이상 고려.
2. **접근 제어 정교함 요구 수준**: 위치·기기 상태·위험도에 따라 로그인을 차단/추가 인증하는 조건부 액세스가 필요한가? → 필요하면 P1 이상.
3. **관리자 계정 보호·컴플라이언스 요구**: 관리자 권한을 상시 부여하지 않고 필요할 때만 주는 PIM, 이상 로그인 자동 탐지가 법적/보안 정책상 필요한가? → 필요하면 P2.

## 4. 디바이스 ID 구성 3가지 — 언제 무엇을 쓰는가

| 구성 | 언제 쓰는가 | 핵심 특징 |
|---|---|---|
| **Azure AD 등록 (Registered)** | 개인 소유 기기(BYOD)로 회사 이메일·앱에만 접근하고 싶을 때 | 기기 전체를 회사가 관리하지 않고, 앱 단위로만 회사 계정 연결 |
| **Azure AD 조인 (Joined)** | 회사가 지급한 기기이고, 클라우드 전용 환경(온프레미스 AD 없음)일 때 | 기기 자체가 Azure AD에 등록되어 완전히 클라우드로 관리됨(Intune 등과 결합) |
| **하이브리드 Azure AD 조인 (Hybrid Azure AD Joined)** | 기존 온프레미스 AD DS 도메인에 이미 가입된 회사 PC를, 클라우드 서비스에도 SSO로 접근시키고 싶을 때 | 온프레미스 도메인 가입 + Azure AD 등록을 동시에 유지(과도기/혼합 환경에 적합) |

**선택 가이드 한 줄**: "개인 기기면 등록, 신규 클라우드 전용 회사면 조인, 기존 사내망 도메인 PC를 그대로 쓰면서 클라우드도 붙이고 싶으면 하이브리드 조인."

## 5. SSPR과 MFA의 관계 / IAM의 역할

**SSPR(Self-Service Password Reset)과 MFA**
SSPR은 사용자가 IT 헬프데스크를 거치지 않고 스스로 비밀번호를 재설정하게 해주는 기능입니다. 하지만 "본인 확인 없이" 비밀번호를 바꿀 수 있다면 오히려 보안 구멍이 되므로, SSPR은 반드시 MFA(다단계 인증: 전화, 인증 앱, 이메일 등 추가 확인 수단)와 함께 동작하도록 설계됩니다. 즉 MFA는 SSPR이 "진짜 본인"에게만 재설정 권한을 주기 위한 전제 조건입니다. 실무에서는 SSPR 활성화 시 최소 1~2가지 인증 방법 등록을 강제하는 것이 일반적입니다. 결과적으로 SSPR은 편의성, MFA는 그 편의성이 악용되지 않도록 막는 안전장치 역할을 합니다.

**IAM(역할 기반 접근 제어, RBAC)의 역할**
IAM(Identity and Access Management)에서 RBAC(Role-Based Access Control)는 "누가 어떤 리소스에 어떤 작업을 할 수 있는가"를 역할(Role) 단위로 정의하고 부여하는 체계입니다. 개인마다 권한을 일일이 설정하지 않고 "읽기 전용", "기여자", "소유자" 같은 역할을 사용자·그룹·앱에 할당해 관리 부담을 줄입니다. Azure에서는 구독/리소스 그룹/개별 리소스 등 여러 범위(scope) 레벨에서 역할을 상속·중첩 적용할 수 있습니다. 최소 권한 원칙(Least Privilege)을 실현하는 핵심 도구이며, 감사·컴플라이언스 대응의 기초가 됩니다. 결과적으로 IAM/RBAC은 "누구에게 어디까지 열어줄 것인가"를 체계적으로 통제하는 역할을 합니다.
