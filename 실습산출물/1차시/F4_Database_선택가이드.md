# Azure 관리형 데이터베이스 선택 가이드

이 문서는 "무엇이 있는지"보다 **"우리 데이터를 어디로, 어떻게 연결해서 옮길 것인가"**를 실무에서 바로 판단할 수 있게 정리한 것입니다.

## 1. Azure 관리형 DB 라인업

| 서비스명 | 엔진 | 관계형/비관계형 | 대표 사용 사례 | 마이그레이션 원천(온프렘에서 무엇을 옮길 때) |
|---|---|---|---|---|
| **Azure SQL** (Database / Managed Instance / VM) | Microsoft SQL Server 계열 | 관계형 | 사내 업무 시스템, ERP 연동 DB, .NET 기반 업무 앱의 백엔드 | 온프렘 **SQL Server** |
| **Azure Database for MySQL** (Flexible Server) | MySQL | 관계형 | 웹/전자상거래 애플리케이션(WordPress, 오픈소스 웹앱 등) | 온프렘/자체호스팅 **MySQL** |
| **Azure Database for PostgreSQL** (Flexible Server) | PostgreSQL | 관계형 | 지리정보(PostGIS), 확장 기능이 필요한 앱, 오픈소스 선호 팀 | 온프렘/자체호스팅 **PostgreSQL** |
| **Azure Database for MariaDB** | MariaDB | 관계형 | *(과거)* MySQL 호환 오픈소스 워크로드 — **현재는 신규 사용 불가, 6절 참고** | 온프렘 **MariaDB** *(신규 마이그레이션 비권장)* |
| **Azure Cosmos DB** | 멀티 모델(SQL API, MongoDB API, Cassandra API, Gremlin, Table 등) | **비관계형**(NoSQL, 일부 API로 관계형 유사 인터페이스 제공) | 글로벌 분산 앱, 실시간 개인화, IoT 대량 쓰기, 낮은 지연시간이 필수인 서비스 | 온프렘/자체호스팅 **MongoDB, Cassandra** 등 NoSQL DB |

**판단 기준 한 줄 요약**: 지금 쓰는 온프렘 엔진과 같은 엔진의 관리형 서비스를 먼저 보고, "전 세계 어디서든 밀리초 단위로 응답해야 하는 비관계형 데이터"일 때만 Cosmos DB를 검토합니다.

## 2. Azure SQL 3가지 배포 형태 — 리프트 앤 시프트 → 현대화 → 클라우드 네이티브

```
[리프트 앤 시프트]                [현대화]                      [클라우드 네이티브]
SQL Server on Azure VM   ──────▶  SQL Managed Instance  ──────▶  SQL Database
   (IaaS)                          (PaaS, 인스턴스 단위)            (PaaS, DB 단위)
```

| 배포 형태 | 스펙트럼 위치 | 관리 책임 범위 | 언제 고르는가 |
|---|---|---|---|
| **SQL Server on Azure VM** | 리프트 앤 시프트 | **IaaS** — OS 패치·SQL Server 설치/패치·백업·HA 구성까지 사용자가 직접 관리 | 온프렘 SQL Server를 코드/설정 변경 없이 그대로, 최단 시간에 옮겨야 할 때 (예: OS 레벨 커스텀 설정이나 특정 SQL Server 버전 종속성이 있는 레거시 앱) |
| **SQL Managed Instance** | 현대화(중간 단계) | **PaaS**(인스턴스 단위) — OS·엔진 패치는 자동, 단 SQL Server 인스턴스 전체와 호환되어 Linked Server·SQL Agent·Cross-DB 쿼리 등 온프렘 기능을 거의 그대로 사용 | 온프렘의 인스턴스 레벨 기능(여러 DB 간 쿼리 등)은 유지하면서 관리 부담만 줄이고 싶을 때 |
| **SQL Database** | 클라우드 네이티브 | **PaaS**(DB 단위, 완전관리형) — 패치·백업·HA·확장까지 Microsoft가 전담, 사용자는 DB 설계·쿼리·튜닝에만 집중 | 신규 앱을 처음부터 클라우드에 맞게 설계하거나, 관리 부담을 최소화하고 자동 확장을 활용하고 싶을 때 |

## 3. 연결 정책: 리디렉션(Redirect) vs 프록시(Proxy)

| 기준 | 리디렉션(Redirect) | 프록시(Proxy) |
|---|---|---|
| 동작 방식 | 게이트웨이로 최초 연결 → 이후 요청은 **DB 노드에 직접** 연결 (실패 시 게이트웨이로 재연결) | 모든 요청이 **항상 게이트웨이를 경유** |
| Azure 내부에서 연결할 때 기본값 | Azure 내부 연결의 **기본값** (같은 VNet/리전 내 클라이언트는 자동으로 Redirect 우선 사용) | 내부에서도 선택은 가능하지만 기본은 아님 |
| 외부(인터넷)에서 연결할 때 기본값 | 클라이언트-DB 간 직접 경로 확보가 어려운 경우가 많아 실제로는 Proxy로 대체되는 경우가 많음 | 외부(온프렘, 인터넷) 연결의 **사실상 기본/일반적 경로** |
| 지연 시간(latency) | 게이트웨이를 거치지 않는 구간이 많아 **낮음** (직접 경로) | 모든 트래픽이 게이트웨이를 통과해 상대적으로 **높음** |
| 방화벽 관점 | 클라이언트가 DB 노드로 직접 붙는 포트 범위(1433 + 동적 포트 범위)를 **아웃바운드로 열어야 함** — 사내 방화벽이 막혀 있으면 실패하기 쉬움 | 게이트웨이의 **단일 포트(1433)만 열면 되므로** 방화벽 정책이 단순하고 사내망에서 안정적 |

**요약**: Azure 내부(같은 VNet)에서는 Redirect가 빠르고 기본이지만, 외부(사내망·인터넷)에서 접속할 때는 방화벽 정책이 단순한 Proxy가 실무적으로 더 안정적입니다.

## 4. Azure Database의 이점 5가지 — 온프레미스 대비

| 이점 | Azure Database에서는 | 온프레미스에서는 이걸 하려면 |
|---|---|---|
| **완전 관리형** | 패치·백업·버전 업그레이드가 자동/설정만으로 처리됨 | DBA가 패치 일정을 직접 잡고, 야간 작업으로 다운타임을 감수하며 수동 적용 |
| **고가용성** | 리전 내 다중 복제본, 존 중복 등을 옵션 체크만으로 구성 | 별도의 클러스터링 솔루션(Always On, Galera 등)을 직접 설계·구축·검증 |
| **지능형 성능·규모** | 자동 튜닝, 사용량에 따른 스케일 업/다운(서버리스 티어 포함) | 용량 산정을 미리 해서 하드웨어를 구매하고, 트래픽이 늘면 증설 프로젝트를 새로 진행 |
| **보안·규정 준수** | 저장 데이터 암호화, 위협 탐지, 각종 컴플라이언스 인증이 기본 제공 | 암호화·감사 로그·인증 획득을 자체적으로 구축하고 주기적으로 심사받아야 함 |
| **에코시스템 통합** | Azure AD 인증, Private Link, Monitor, Defender 등과 몇 번의 클릭으로 연동 | 각 도구를 개별적으로 설치·연동하고 버전 호환성을 직접 관리 |

## 5. 의사결정 트리 — "온프레미스 MySQL 서버를 Azure로 옮긴다면"

```
온프레미스 MySQL을 옮기려 한다
│
├─ Q1. 애플리케이션 코드/드라이버를 전혀 바꿀 수 없는가? (MySQL 프로토콜을 그대로 써야 함)
│    └─ YES → Azure Database for MySQL 계열로 이동 (엔진 동일)
│         │
│         └─ Q1-1. 세밀한 OS 레벨 커스텀(특정 플러그인, 커널 튜닝 등)이 반드시 필요한가?
│              ├─ YES → IaaS(Azure VM에 MySQL 직접 설치) — 관리 부담은 그대로 떠안는 대신 완전한 제어권 확보
│              └─ NO  → Azure Database for MySQL - Flexible Server (PaaS, 관리 부담 최소화)
│
├─ Q1이 NO(코드 일부 변경 가능)라면 → Q2. 전 세계 여러 리전에서 밀리초 단위 지연으로
│                                        읽고 써야 하거나, 스키마가 자주 바뀌는 비정형 데이터가 섞여 있는가?
│    └─ YES → Cosmos DB(MongoDB API 등)로 재설계 검토 — 단, 관계형 스키마·트랜잭션 로직 재작성 비용 고려
│    └─ NO  → Q1-1과 동일하게 Azure Database for MySQL 계열 선택
│
└─ Q3. (연결 정책) 클라이언트가 Azure 내부(같은 VNet)에 있는가, 사내망/인터넷에 있는가?
     ├─ Azure 내부 → Redirect 기본값 유지(지연시간 최소화)
     └─ 사내망/인터넷 → Proxy로 명시 설정(방화벽 정책 단순화, 안정성 우선)
```

## 6. 강의자료(2023년 기준) 대비 변경된 항목

| 항목 | 강의자료(2023) 기준 | 현재 상태 | 비고 |
|---|---|---|---|
| **Azure Database for MariaDB** | 관리형 DB 라인업의 정식 구성원으로 소개됨 | **신규 배포 불가 / 단계적 지원 종료(retirement) 대상**으로 전환됨 — 기존 사용자는 Azure Database for MySQL 등으로 마이그레이션 권고 | 정확한 지원 종료 시점은 계정·구독별 공지가 다를 수 있어 **확인 필요**(Azure 포털의 서비스 정상 상태/공지 배너에서 직접 확인 권장) |
| **Azure Database for MySQL / PostgreSQL — Single Server 배포 옵션** | Single Server가 기본 선택지 중 하나로 소개되었을 가능성 있음 | **Flexible Server로 일원화**되는 추세이며, Single Server는 신규 생성이 막혔거나 지원 종료 수순 | 정확한 종료 일정은 **확인 필요**(포털/공지 확인 권장) |

위 두 항목은 실제 구독에서 서비스 생성 화면을 열어보지 않고는 100% 확정하기 어려운 부분이 있어, **실습 시 반드시 Azure 포털에서 "사용 가능한 배포 옵션"을 먼저 확인**한 뒤 진행하는 것을 권장합니다.
