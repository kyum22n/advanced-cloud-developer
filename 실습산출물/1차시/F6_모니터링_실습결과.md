이니셜: `lkm` / 리전: `koreacentral`

## 1. 메트릭 vs 로그 (3줄 요약)

**메트릭(Metric)**
- 특정 시점의 숫자 값(예: CPU 6.36%, 사용 용량 X바이트)이 정해진 주기로 쌓이는 경량 데이터입니다.
- 저장 비용이 낮고 조회가 빨라 대시보드·실시간 상태 파악에 적합합니다.
- **언제 쓰는가**: "지금 이 리소스가 정상 범위인가"를 즉시 확인하거나, 임계값 기반 경고(예: CPU 80% 초과)를 걸 때.

**로그(Log)**
- 여러 속성(타임스탬프, 메시지, 리소스ID, 상태 등)을 가진 레코드로, 이벤트가 발생할 때마다 기록됩니다.
- 쿼리 언어(KQL)로 필터링·집계·상관관계 분석이 가능해 무거운 대신 정보량이 많습니다.
- **언제 쓰는가**: "언제, 누가, 무엇을, 왜" 했는지 원인을 추적하는 사후 분석·감사·트러블슈팅.

## 2. Azure Monitor가 수집하는 데이터 형식 5계층

| 계층 | 예시 데이터 |
|---|---|
| 애플리케이션 | 앱 내부 예외 로그, 사용자 정의 이벤트, 요청 응답 시간(Application Insights) |
| 게스트 OS | VM 내부의 CPU/메모리/디스크 사용률, Windows 이벤트 로그, syslog |
| Azure 리소스 | 스토리지 계정의 UsedCapacity, MySQL 서버의 cpu_percent 같은 리소스별 메트릭 |
| Azure 구독 | 활동 로그(누가 언제 무슨 리소스를 만들고 지웠는지), 서비스 상태(Service Health) |
| Azure 테넌트 | Microsoft Entra ID 감사 로그, 로그인 로그(디렉터리 수준 이벤트) |

### [환경 이슈] 넓은 시간 범위 조회 시 결과 누락

`az monitor activity-log list --offset 24h`(또는 48h)처럼 넓은 시간 범위로 한 번에 조회하면, 이 구독에 자동으로 쌓이는 Azure Policy 감사(`audit`/`auditIfNotExists`) 이벤트가 많아 실제 응답이 최근 특정 구간(예: MySQL 생성 시점)에만 편중되어 이전 이벤트(스토리지 계정 생성 등)가 누락되는 현상이 있었습니다. `--start-time`/`--end-time`으로 **조회 구간을 좁혀서(예: 35분 단위)** 재조회하니 정상적으로 모든 이벤트가 확인되었습니다. 표의 데이터는 좁은 구간 재조회로 확보한 값입니다.

## 4. 포털에서 활동 로그 확인하는 경로

포털 상단 검색창에 **"모니터"** 입력 → **[활동 로그]** 클릭 → 상단 필터 바에서:
- **구독**: 실습 중인 구독 선택
- **리소스 그룹**: `rg-advdev-lkm-data` (또는 확인하려는 그룹) 선택
- **기간(Timespan)**: 필요한 범위(예: 지난 24시간, 사용자 지정)로 조정

필터 적용 후 목록에서 작업 이름·상태·시간·수행자를 확인할 수 있고, 각 행을 클릭하면 JSON 상세(요청/응답 본문 등)까지 볼 수 있습니다.

## 6. Log Analytics 작업 영역

### 무엇인가
Log Analytics 작업 영역은 여러 리소스에서 보낸 로그·메트릭 데이터를 **수집·집계·분석하는 하나의 논리적 컨테이너**입니다. 데이터가 이 안에 쌓이면 KQL(Kusto Query Language)로 여러 리소스의 로그를 한 번에 질의할 수 있습니다.

### 지리적 위치·데이터 격리가 중요한 이유
작업 영역은 생성된 리전에 데이터를 저장하므로, 리전을 잘못 선택하면 데이터 주권(data residency) 규정을 어길 수 있고, 리소스와 다른 리전에 두면 조회 지연이나 추가 송신 비용이 생길 수 있습니다. 또한 조직·프로젝트별로 작업 영역을 분리하면 접근 권한(RBAC)과 데이터 보존 정책을 세밀하게 나눠 관리할 수 있어, 한 팀의 로그가 다른 팀에 노출되는 것을 막는 **데이터 격리** 효과도 있습니다.

## 7. 경고(Alert) 규칙 설계안 (문서로만 제시 — 실제 생성하지 않음)

| 항목 | (a) VM CPU 80% 초과 | (b) 스토리지 가용성 저하 | (c) 예산 초과 |
|---|---|---|---|
| 조건 | Percentage CPU 메트릭, 5분 평균이 80%를 15분 이상 지속 초과 | 스토리지 계정 Availability 메트릭이 99% 미만으로 하락 | 월간 지출이 설정한 예산 금액의 80%/100% 도달 |
| 심각도 | Sev 2 (경고) | Sev 1 (오류에 가까움 — 서비스 영향 가능) | Sev 3 (정보/계획성) |
| 알림 대상 | 운영 담당자 이메일/Teams 채널 (Action Group) | 인프라 담당자 + 온콜 채널 | 프로젝트 관리자, 비용 담당자 |
| 왜 필요한가 | 리소스 고갈로 인한 응답 지연·서비스 장애를 사전에 감지하기 위함 | 클라이언트가 데이터를 못 읽는 상황을 실제 장애 신고 전에 먼저 인지하기 위함 | 실습·개발 환경에서 예상치 못한 과금 폭증(리소스 방치 등)을 조기에 차단하기 위함 |

이 설계안은 문서로만 정리했으며, `az monitor metrics alert create` 등 실제 경고 규칙 생성 명령은 **이번 실습에서 실행하지 않았습니다.**
