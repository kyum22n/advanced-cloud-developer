## 🅑1. 시나리오를 «사실»로 분해 (7분)

> 💬 **프롬프트 B‑1**
>
> ```
> ① 역할·규칙
>   너는 DDD 를 적용하는 시니어 도메인 분석가다.
>   추측을 사실처럼 쓰지 말고, 원문에 근거가 없는 것은 «미결»로 남긴다.
>
> ② 맥락
>   아래는 Fabrikam 드론 배달 시나리오다.
>   ---
>   가상의 회사 Fabrikam, Inc. 는 드론 항공기를 관리한다. 기업들이 서비스에 등록하며,
>   사용자는 배달할 상품을 드론이 픽업하도록 요청할 수 있다. 고객이 픽업을 예약할 때
>   백엔드 시스템은 드론을 할당하고 예상 배달 시간을 사용자에게 알린다.
>   배달이 진행되는 동안 고객은 드론의 위치를 추적하고 지속적으로 업데이트된 도착 시간을 본다.
>   ---
>
> ③ 작업
>   (1) 이 문장에서 «사실(Fact)» 을 뽑아 F-01 부터 번호를 붙여라.
>       각 사실에는 «원문 근거»(어느 구절에서 나왔는지)를 반드시 적어라.
>   (2) 액터를 식별하고 시스템 경계 다이어그램을 ASCII 로 그려라.
>   (3) 기능 요구사항을 «누구의 요청으로, 어떤 개념에, 무슨 상태 변화를 일으키는가»
>       기준으로 MECE 하게 그룹핑하고 FR-{그룹}-{번호} 로 매기라.
>   (4) 비기능 요구사항을 «측정 가능한 숫자»로 정의하라.
>       "빨라야 한다" 는 요구사항이 아니다. "p95 ≤ 300ms" 가 요구사항이다.
>   (5) 제약사항(CON)을 정리하라. 이 과정의 제약은 다음과 같다.
>       Azure · Java Spring Boot · Vue.js 3 · Terraform · JUnit · Swagger ·
>       실제 배포 실행 없음 · 개인정보 사용 금지 · 분산 트랜잭션 사용 불가
>   (6) «이 단계에서 일부러 결정하지 않은 것»을 표로 남기고,
>       각각 언제·어느 문서에서 결정할지 적어라.
>
> ④ 형식
>   드론배달/분석/01_시나리오_요구사항_분석.md
>   표 중심. 각 요구사항에 «검증 방법» 열을 포함.
>
> ⑤ 검증
>   · 모든 사실에 원문 근거가 있는가
>   · 모든 비기능 요구사항에 «숫자와 측정 지점»이 있는가
>   · 요구사항 그룹이 서로 겹치지 않는가(ME) · 빠진 것이 없는가(CE)
>   · «미결» 항목에 결정 시점이 적혀 있는가
> ```

📌 **여기서 나오는 것** — 사실 12개 · 기능 요구사항 23건 · 비기능 12건 · 제약 8건

> 🔍 **왜 «사실 분해»부터 하는가**
> "고객은 드론의 위치를 추적한다"에서 **드론이 위치를 계속 발신한다**는 사실이 나오고,
> 그것이 «초당 수천 건 쓰기»라는 접근 패턴을 낳고, 결국 **저장소 선택**을 결정합니다.
> 문장을 대충 읽고 넘어가면 이 연결이 끊깁니다.

## 🅑2. 전략적 DDD — 서브도메인 분류 (10분)

> 💬 **프롬프트 B‑2**
>
> ```
> ① 역할·규칙
>   너는 전략적 DDD 를 적용하는 도메인 분석가다.
>   서브도메인 분류는 «기술 판단»이 아니라 «사업 판단»이다.
>   무엇이 이 회사의 경쟁 우위인지를 근거로 판단하고, 그 근거를 반드시 적어라.
>
> ② 맥락
>   드론배달/분석/01_시나리오_요구사항_분석.md
>
> ③ 작업
>   (1) 서브도메인을 식별하라. 지금 구현하지 않을 «미래» 서브도메인도 포함한다.
>       (미래 것을 알아야 «지금의 경계가 그것을 막지 않는지» 검증할 수 있다.)
>   (2) 각 서브도메인을 핵심(Core) / 지원(Supporting) / 일반(Generic) / 외부로 분류하고
>       «왜 그렇게 분류했는가»를 한 줄로 적어라.
>   (3) 분류에 따라 구현 전략을 정하라.
>       핵심 → 직접 개발 · 최우선 투자
>       지원 → 직접 개발하되 최소
>       일반 → 기성품 구매 (예: 인증은 Microsoft Entra ID)
>       외부 → 손상 방지 계층으로 격리
>   (4) 바운디드 컨텍스트를 도출하고 Mermaid 로 그려라.
>   (5) ★ «같은 단어, 다른 뜻» 표를 만들어라.
>       예: «드론» 이 배송 컨텍스트와 드론 관리 컨텍스트와 청구 컨텍스트에서
>       각각 무엇을 뜻하는지. 이것이 컨텍스트를 나누는 근거다.
>   (6) 컨텍스트 맵을 그리고 각 관계에 통합 패턴을 명시하라.
>       (고객-공급업체 / 개방형 호스트 서비스 / 게시된 언어 / 순응주의자 /
>        손상 방지 계층 / 별도의 방법)
>   (7) 전술적 DDD 로 심화할 컨텍스트를 «하나» 고르고 선택 근거를 적어라.
>   (8) 그 컨텍스트의 유비쿼터스 언어 사전을 만들어라.
>       ★ «이 컨텍스트에서 쓰지 않을 금지 용어»도 함께 적어라.
>
> ④ 형식
>   드론배달/분석/02_전략적_DDD_도메인_분석.md
>   Mermaid 다이어그램 2개(컨텍스트 · 컨텍스트 맵) 포함.
>
> ⑤ 검증
>   · 모든 분류에 «사업적» 근거가 있는가 (기술 편의가 근거면 안 된다)
>   · «같은 단어, 다른 뜻» 사례가 최소 3개 있는가
>   · 컨텍스트 맵의 모든 관계에 통합 패턴 이름이 붙어 있는가
>   · 유비쿼터스 언어에 «금지 용어»가 포함되어 있는가
> ```

> 🔑 **여기가 이 차시에서 가장 중요한 판단입니다.**
> «사용자 계정»을 핵심으로 분류하면 인증 시스템을 직접 만들게 되고,
> 그 노력만큼 «배송»에 쓸 시간이 사라집니다.
> **핵심 = 배송·드론 관리 / 일반 = 계정·콜센터** 라는 판단이 이후 모든 우선순위를 정합니다.

## 🅑3. 이벤트 스토밍 — 동적 흐름 (8분)

> 💬 **프롬프트 B‑3**
>
> ```
> ① 역할·규칙
>   너는 이벤트 스토밍 퍼실리테이터다.
>   도메인 이벤트는 «과거형»으로만 쓴다 ("배달이 생성되었다").
>   현재형·미래형이 나오면 그것은 이벤트가 아니라 커맨드다.
>
> ② 맥락
>   드론배달/분석/02_전략적_DDD_도메인_분석.md 에서 고른 배송 컨텍스트
>
> ③ 작업
>   (1) 도메인 이벤트를 시간 순으로 나열하라.
>       구간을 나누어라: 예약 → 준비 → 실행 → 완료 · (별도) 예외
>   (2) 각 이벤트를 일으키는 커맨드와, 그 커맨드를 받는 애그리거트를 표로 매핑하라.
>       성공 이벤트와 실패 이벤트를 «둘 다» 적어라.
>   (3) 배달의 상태 기계를 Mermaid stateDiagram 으로 그려라.
>   (4) ★ 상태 기계에서 «불변식(INV)» 을 도출하라. INV-01 부터 번호를 붙이고
>       각각에 «위반 시 어떻게 되는가»를 적어라.
>   (5) 정책(Policy)을 «이벤트가 나면 → 커맨드를 낸다» 형태로 정리하라.
>       POL-01 부터 번호를 붙이고 «어디서 구현되는가»를 적어라.
>   (6) 읽기 모델을 식별하라. 갱신 계기와 조회 빈도를 함께 적어라.
>   (7) ★ 핫스팟(아직 답이 없는 질문)을 빨간색 🔴 로 남기고,
>       각각에 «어떻게 처리할 것인가»를 적어라. 답을 모르면 «미결»로 두어라.
>
> ④ 형식
>   드론배달/분석/03_이벤트_스토밍.md
>   색 표기법(🟧이벤트 🟦커맨드 🟨애그리거트 🟪정책 🟩읽기모델 🟫외부 🔴핫스팟) 사용.
>   Mermaid graph 와 stateDiagram 포함.
>
> ⑤ 검증
>   · 모든 이벤트가 과거형인가
>   · 커맨드 → 애그리거트 매핑에서 «애그리거트 후보»가 3~5개로 좁혀지는가
>   · 각 불변식에 위반 시 동작이 적혀 있는가
>   · 정책마다 구현 위치(어느 서비스)가 지정되어 있는가
> ```

> 💡 **여기서 애그리거트가 «드러납니다»**
> 커맨드를 받아 불변식을 검사하고 이벤트를 내는 것 = 애그리거트.
> 매핑 표를 만들면 애그리거트 열에 **Delivery · Package · Drone** 세 개만 남습니다.
> 이것을 «미리 정하는 것»이 아니라 «흐름에서 발견하는 것»이 이벤트 스토밍의 목적입니다.

## 🅑4. 전술적 DDD — 애그리거트 설계 (10분)

> 💬 **프롬프트 B‑4**
>
> ```
> ① 역할·규칙
>   너는 전술적 DDD 를 적용하는 도메인 모델러다.
>   애그리거트 3원칙을 반드시 지켜라.
>     ① 작게 설계한다
>     ② 다른 애그리거트는 «ID 로만» 참조한다 (객체 참조 금지)
>     ③ 애그리거트 간에는 최종 일관성을 쓴다
>
> ② 맥락
>   드론배달/분석/03_이벤트_스토밍.md 의 애그리거트 후보와 불변식 INV-01~06
>
> ③ 작업
>   (1) 엔터티와 값 개체를 판별하라.
>       판별 질문을 명시하라: "속성이 모두 같아도 다른 것인가?" → 엔터티
>   (2) 애그리거트 경계를 정하고 Mermaid classDiagram 으로 그려라.
>       ID 참조는 점선(..>), 포함은 실선 컴포지션(*--)으로 구분하라.
>   (3) 각 애그리거트가 «트랜잭션 일관성 경계»인 이유를 적어라.
>   (4) ★ 애그리거트 3원칙 준수를 표로 검증하라.
>   (5) ★ «흔한 잘못된 설계»와 나란히 비교하는 코드 블록을 만들어라.
>       (객체 참조 vs ID 참조가 무엇을 망가뜨리는지)
>   (6) 각 불변식이 «어느 애그리거트의 어느 메서드»에서 검사되는지 표로 정리하라.
>   (7) 도메인 이벤트 카탈로그와 «게시 스키마 규약»을 정의하라.
>       eventId(멱등) · eventVersion(진화) · correlationId(추적) · causationId(인과)
>   (8) 도메인 서비스와 애플리케이션 서비스를 구분하라.
>       각각 «하는 일»과 «하지 않는 일»을 명시하라.
>   (9) 헥사고날(포트-어댑터) 계층 구조를 ASCII 로 그려라.
>       ★ 도메인 계층에 «프레임워크 의존 금지» 규칙을 명시하라.
>   (10) 핵심 유스케이스 2개(배달 예약 · 배달 추적)의 시퀀스 다이어그램을 그려라.
>
> ④ 형식
>   드론배달/분석/04_전술적_DDD_모델링.md
>   Mermaid classDiagram 1개 · sequenceDiagram 2개 포함.
>
> ⑤ 검증
>   · 애그리거트가 다른 애그리거트를 «객체로» 들고 있지 않은가
>   · 모든 불변식이 «애그리거트 루트 메서드» 안에서 검사되는가
>       (컨트롤러·서비스에서 검사하면 우회 가능한 구멍이 생긴다)
>   · 빈혈 도메인 모델이 아닌가
>       판별법: 애그리거트 클래스에서 «if» 문을 찾을 수 있는가
>   · 이벤트 스키마에 멱등 처리용 고유 ID 가 있는가
> ```

> ❗ **여기서 걸러야 할 안티패턴 — 빈혈 도메인 모델**
> 애그리거트가 getter/setter 만 갖고 모든 규칙이 서비스에 있으면 DDD 가 아닙니다.
> **판별법: `Delivery` 클래스에서 `if` 문을 찾을 수 없다면 빈혈 모델입니다.**

## 🅑5. 마이크로서비스 경계 (5분)

> 💬 **프롬프트 B‑5**
>
> ```
> ① 역할·규칙
>   너는 마이크로서비스 경계를 설계하는 아키텍트다.
>   «애그리거트 = 서비스» 로 끝내지 마라. 그것은 «후보»일 뿐이다.
>   비기능 요구사항으로 합치거나 쪼개는 «조정»이 반드시 필요하다.
>
> ② 맥락
>   드론배달/분석/04_전술적_DDD_모델링.md
>   드론배달/분석/01_시나리오_요구사항_분석.md 의 NFR
>
> ③ 작업
>   (1) 애그리거트와 도메인 서비스에서 «후보 서비스»를 도출하라.
>   (2) 각 후보를 네 가지 질문으로 조정하라. 표로 만들어라.
>       Q1 확장 특성이 다른가?      다르면 → 쪼갠다
>       Q2 팀 경계와 맞는가?        한 팀이 항상 함께 바꾸면 → 합친다
>       Q3 함께 배포되어야만 하는가? 그렇다면 나눈 의미가 없다 → 합친다
>       Q4 장애가 격리되어야 하는가? 필요하면 → 쪼갠다
>   (3) ★ 비기능 요구사항이 «새로 요구하는» 서비스를 찾아라.
>       힌트: 피크 500 req/s 를 즉시 응답으로 받아내려면 무엇이 필요한가?
>             장기 이력 조회를 «짧은 수명 저장소»에 두면 무엇이 문제인가?
>   (4) 최종 서비스 목록을 만들어라. 각 서비스에 다음을 적어라.
>       책임 · «하지 않는 것» · 확장 트리거 · 저장소 · 구현 범위(완전/모듈/모의)
>   (5) ★ 「합치지 않은 이유」와 「합친 이유」를 문서화하라.
>       특히 별도 배포하지 않기로 한 것이 있으면 그 트레이드오프를 적어라.
>   (6) 서비스 관계도를 Mermaid 로 그려라. 동기/비동기를 구분해서 표시하라.
>   (7) ★ 자가 진단표를 만들어 «잘 쪼갰는가»를 검증하라.
>       독립 배포 / 독립 확장 / 데이터 비공유 / 장애 격리 /
>       분산 트랜잭션 없음 / 왕복 과다 아님 / 신(God) 서비스 아님
>   (8) 진단에서 ⚠️ 가 나온 항목은 «위험»으로 등록하고 완화책을 적어라.
>
> ④ 형식
>   드론배달/분석/05_마이크로서비스_경계_식별.md
>
> ⑤ 검증
>   · 각 서비스에 «하지 않는 것»이 명시되어 있는가
>   · 두 서비스가 같은 저장소를 공유하지 않는가
>   · 합치거나 나누지 않은 «판단의 근거»가 모두 기록되어 있는가
>   · 자가 진단의 ⚠️ 항목이 위험으로 관리되고 있는가
> ```

📌 **여기서 나오는 것** — 서비스 9개 (배포 단위 6개 · 모듈 1개 · 모의 2개)

## 🅑6~7. 아키텍처 스타일 비교 · 품질 속성 (통합 프롬프트)

> 💬 **프롬프트 B‑6**
>
> ```
> ① 역할·규칙
>   너는 아키텍처 결정을 «근거와 대가»로 기록하는 아키텍트다.
>   "마이크로서비스로 한다" 를 기본값으로 두지 마라. 그것은 선택의 «결과»여야 한다.
>
> ② 맥락
>   드론배달/분석/01 · 05
>
> ③ 작업
>   (1) 세 가지 아키텍처 스타일을 «같은 시나리오에 적용»해 비교하라.
>       N-계층 / 웹-큐-워커 / 마이크로서비스
>       각각 이 시나리오에 적용하면 어떤 그림이 되는지 ASCII 로 그려라.
>   (2) 요구사항별로 «어느 스타일이 충족하는가» 판정표를 만들어라 (✅/⚠️/❌).
>   (3) 결정을 내리고, ★ «지불하는 대가»를 명시적으로 표에 적어라.
>   (4) ★ «언제 이 결정을 되돌려야 하는가» — 되돌릴 조건 4가지를 적어라.
>   (5) ADR(아키텍처 결정 기록)을 작성하라. 형식:
>       상태 · 일자 · 맥락 · 결정 · 근거 · 결과(➕➖) · 대안(과 기각 이유) · 되돌릴 조건
>   (6) 이어서 별도 문서로, 비기능 요구사항을
>       Azure Well-Architected Framework 5기둥으로 재정렬하라.
>       신뢰성 · 보안 · 비용 최적화 · 운영 우수성 · 성능 효율성
>       각 항목을 «목표(숫자) + 측정 방법 + 설계 대응» 3점 세트로.
>   (7) ★ 기둥 사이의 «충돌»을 표로 정리하고 각각 어느 쪽을 택했는지 적어라.
>       (신뢰성↔비용 · 보안↔성능 · 일관성↔확장성 · 관측성↔비용)
>   (8) 성능 안티패턴 10가지를 이 설계에 대조해 자가 점검하라.
>
> ④ 형식
>   드론배달/분석/06_아키텍처_스타일_비교.md   (ADR 3건 포함)
>   드론배달/분석/07_품질속성_및_제약사항.md
>
> ⑤ 검증
>   · 판정표에 «마이크로서비스가 못 하는 것»도 솔직히 적혀 있는가
>     (초기 개발 속도 · 운영 단순성은 다른 스타일이 낫다)
>   · 모든 ADR 에 «되돌릴 조건»이 있는가
>   · 모든 품질 목표가 «숫자»인가
>   · 트레이드오프 표에서 «양쪽 다 얻는다»고 쓰지 않았는가
> ```

> 🔑 **ADR 에 «되돌릴 조건»을 쓰는 이유**
> 아키텍처 결정은 언젠가 틀립니다. 조건을 미리 적어 두면
> **«감»이 아니라 «신호»로 판단**할 수 있습니다.
> 예: "두 서비스를 항상 함께 배포하고 있다" → 경계가 틀렸다는 신호.

## 🅒2. 통신 · API · 게이트웨이 (14분)

> 💬 **프롬프트 C‑2**
>
> ```
> ① 역할·규칙
>   너는 분산 시스템의 통신을 설계하는 아키텍트다.
>   «시간 제한 없는 호출»과 «재시도만 있고 회로 차단기 없는 구성»은

> ② 맥락
>   드론배달/설계/01 · 분석/05
>
> ③ 작업 — 통신 설계서
>   (1) 통신 방식 결정 트리를 ASCII 로 그려라.
>       "결과를 지금 알아야 하는가" → "수신자가 하나인가 여럿인가"
>   (2) 전체 통신 매트릭스를 만들어라 (발신 · 수신 · 방식 · 프로토콜 · 실패 시).
>   (3) REST/JSON vs gRPC 를 비교하고 선택하라. 되돌릴 조건도.
>   (4) ★ 시간 제한 «예산»을 만들어라.
>       전체 예산 안에서 각 호출의 몫을 나누고,
>       「재시도 횟수 × (연결+읽기) 가 상위 예산을 넘지 않는가」를 검증하라.
>   (5) 재시도 구성을 쓰고, ★ 다음을 반드시 포함하라.
>       · 4xx 는 재시도하지 않는다 (요청 자체가 틀렸다)
>       · 지수 백오프 + «지터» (지터 없으면 재시도 폭풍)
>       · 재시도 대상은 반드시 멱등이어야 한다
>   (6) 회로 차단기 구성. ★ 외부 서비스는 «더 빨리, 더 오래» 닫는 이유를 적어라.
>   (7) Bulkhead 구성. ★ 공유 스레드 풀의 문제를 ASCII 로 대비해 보여라.
>   (8) ★ 복원력 패턴의 «적용 순서»를 설명하라.
>       Bulkhead → CircuitBreaker → Retry → TimeLimiter (바깥→안쪽)
>       재시도가 회로 차단기 바깥에 있으면 무슨 일이 생기는가?
>   (9) 비동기 설계: 큐 설정(피어락·DLQ·중복감지) · 스트림 설정(파티션·소비자그룹)
>       ★ 파티션 키를 애그리거트 ID 로 두는 이유(순서 보장)를 설명하라.
>   (10) 멱등 소비자 구현 방법.
>   (11) ★ 상관 ID 전파 — 「메시징 구간이 빠지면 추적이 큐에서 끊긴다」를
>        다이어그램과 코드로 보여라.
>   (12) 서비스 메시를 쓰지 않은 이유와 대체 수단을 표로.
>
> ③' 작업 — API 설계서
>   (13) 공개 API 와 백엔드 API 를 구분하고 우선 가치의 차이를 적어라.
>   (14) DDD → REST 매핑 규칙 표 (애그리거트→리소스, 아이덴티티→URL 등)
>   (15) ★ RPC 스타일 URL 과 리소스 스타일 URL 을 나란히 비교하라.
>   (16) 전체 API 카탈로그를 만들어라. 요청·응답 예시 JSON 포함.
>   (17) ★ 비동기 접수를 «202 Accepted + Location + Retry-After» 로 표현하고,
>        201 을 쓰면 무슨 문제가 생기는지 설명하라.
>   (18) 멱등성 설계. POST 를 피할 수 없을 때 Idempotency-Key 규약.
>        ★ 「같은 키 + 다른 본문」은 422 로 거부하는 이유.
>   (19) 낙관적 동시성(ETag/If-Match). 비관적 잠금을 쓰지 않는 이유.
>   (20) RFC 9457 Problem Details 오류 규약과 상태 코드 표.
>        ★ 400 / 409 / 412 의 구분 기준을 명확히.
>   (21) 버전 관리 — 주 버전만 URL 에 넣는 이유. 이벤트 스키마 버전 규칙.
>   (22) OpenAPI(Swagger) 규약과 «계약 우선» 원칙.
>
> ③'' 작업 — 게이트웨이 설계서
>   (23) 게이트웨이의 세 역할(라우팅 · 집계 · 오프로딩)을 이 시스템에 배치하라.
>   (24) ★ 오프로딩 표에 «게이트웨이로 옮기지 않을 것»을 반드시 포함하라.
>        힌트: 도메인 지식이 필요한 것(소유권 검증)을 옮기면 어떻게 되는가?
>   (25) ★ 집계를 할 것인가 말 것인가 결정하고 근거를 적어라.
>        하지 않기로 했다면 대안(BFF)과 도입 조건을 적어라.
>   (26) Azure 게이트웨이 5종 비교표. APIM 을 쓰지 않는 이유.
>   (27) WAF 정책. ★ 「감지 모드로 먼저」의 이유.
>   (28) 속도 제한 설계. ★ 속도 제한과 Bulkhead 의 역할 차이.
>
> ④ 형식
>   드론배달/설계/03_서비스간_통신_설계서.md
>   드론배달/설계/04_API_설계서.md
>   드론배달/설계/05_API_게이트웨이_설계서.md
>
> ⑤ 검증
>   · 모든 시간 제한·재시도·임계값에 «왜 이 숫자인가»가 있는가
>   · 재시도되는 모든 연산이 멱등인가

>   · 상태 코드 400/409/412 의 구분이 예시로 설명되어 있는가
> ```

## 🅓4. Workflow — Saga · Supervisor · ACL (10분)

> 💬 **프롬프트 D‑4**
>
> ```
> ① 역할·규칙
>   ★ Scheduler 는 «순서»만 알고 «규칙»은 모른다.
>     이 클래스에 도메인 규칙(if weight > 5 같은)이 나타나면
>     Workflow 가 「분산된 단일체의 중심」이 되는 것이다.
>   ★ 보상 실패를 조용히 삼키지 마라. 재시도하고, 그래도 안 되면
>     수동 개입 상태로 표시하라. 무한 재시도는 문제를 감춘다.
>
> ② 맥락
>   드론배달/설계/06 §5 Saga · 설계/07 §3.2 스케줄러 에이전트 감독자
>   드론배달/설계/03 §4 복원력 구성

> ③ 작업
>   (1) Saga 모델
>       · SagaStep (열거) — ★ 각 단계에 «보상이 필요한가» 표시
>         읽기 전용 단계(계정 검증)는 보상 대상이 아니다.
>       · SagaState — 완료 단계 기록 · 상태 · 보상 시도 횟수 · 단계별 산출물 ID
>         ★ stepsToCompensate() 는 «역순»으로 돌려라.
>           나중에 만든 것을 먼저 지워야 참조 무결성이 깨지지 않는다.
>       · SagaStateRepository (포트) — findStalled 포함
>   (2) 에이전트 포트 5개 (Account · Package · Drone · Delivery · ThirdParty)
>       ★ DroneAgent.assign() 은 Optional 을 돌려라.
>         「가용 드론 없음」은 예외가 아니라 «정상적인 결과의 한 종류»다.
>   (3) SchedulerService
>       · 4단계 순차 실행 + 각 단계 후 상태 저장
>       · ★ 이미 성공한 배달이면 아무것도 하지 않는다 (큐 재전달 멱등성)
>       · 드론 없음 → 타사 위탁 분기
>       · 실패 → compensate() 역순 실행
>       · ★ 보상 3회 초과 → 수동 개입 상태 + 경고
>   (4) SupervisorService
>       · @Scheduled(fixedDelay) 로 30초마다 스캔
>         ★ fixedRate 가 아니라 fixedDelay 인 이유를 주석에 적어라.
>       · 5분 초과 Saga 를 찾아 보상
>       · ★ 한 건의 실패가 나머지 스캔을 막지 않게 하라
>       · ★ 「여러 인스턴스가 동시에 실행해도 안전한 이유」(보상이 멱등)를 적어라.
>         그래서 리더 선출이 필요 없다.
>   (5) ★ ThirdPartyTransportAdapter — 손상 방지 계층
>       · 도메인 → 외부 스키마 번역 (deliveryId→ref_no, Location→orig 등)
>       · 외부 → 도메인 역번역
>       · @Bulkhead + @CircuitBreaker + 폴백
>       · ★ 외부 용어(ref_no · stat_cd · wt_kg)가 이 파일 «밖으로» 나가지 않게 하라
>       · ★ 폴백은 예외가 아니라 «빈 결과»를 돌려라
>   (6) HttpAgents — 내부 서비스 호출
>       ★ 어노테이션 순서: @Bulkhead → @CircuitBreaker → @Retry
>         재시도가 회로 차단기 «바깥»에 있으면 회로가 열려도 재시도가 반복된다.
>         이 이유를 Javadoc 에 적어라.
>       ★ 409 「가용 드론 없음」은 오류가 아니라 «분기»다 — 예외로 만들지 마라.
>       ★ 보상용 DELETE 는 404 를 성공으로 처리하라.
>       ★ AccountAgent 폴백은 「활성으로 가정」 — 이것은 사업적 판단이며
>         부정 이용 위험을 감수하는 대신 가용성을 얻는 것이다. 주석에 적어라.
>   (7) RedisSagaStateRepository
>       ★ 정렬 집합(ZSET)을 써서 「시작한 지 오래된 것」을 O(log N) 에 찾아라.
>         KEYS 명령으로 전체를 스캔하면 운영 환경의 Redis 가 멈춘다.
>   (8) DeliveryRequestConsumer
>       ★ SET NX EX 로 원자적 멱등 처리
>       ★ 상관 ID 를 메시지 속성에서 복원 — 없으면 추적이 큐에서 끊긴다
>       ★ 형식이 깨진 메시지는 재시도해도 소용없다 → 즉시 DLQ
>   (9) application-resilience.yml
>       ★ 모든 수치에 «왜 이 값인가» 주석을 달아라.
>       ★ 4xx 는 재시도하지 않는다 (ignoreExceptions)
>       ★ 지터(randomizedWaitFactor) — 없으면 재시도 폭풍
>       ★ 외부(thirdParty)는 30% 로 «더 빨리» 차단하고 대기 없이(0) 거부
>   (10) JUnit 테스트
>       ★ 가짜 에이전트에 «호출 기록장»을 만들어 호출 «순서»까지 검증하라.
>       · 정상 경로: 4단계가 순서대로 호출된다
>       · 멱등: 재전달 시 아무 서비스도 호출하지 않는다
>       · AC-5: 드론 없음 → 타사 위탁
>       · AC-6: ★ 배달 생성 실패 → 「드론 해제 → 패키지 삭제」 역순 보상
>         indexOf 로 «순서»를 검증하라.
>       · 계정 비활성 → 즉시 중단, 아무것도 만들지 않음
>       · ★ 보상 실패를 성공으로 기록하지 않는가
>       · Supervisor: 타임아웃 전 무동작 / 후 보상 / 재실행 시 중복 보상 없음
>
> ④ 형식
>   드론배달/개발/services/workflow/**
>
> ⑤ 검증
>   mvn -pl workflow -am test

## G‑2. 프롬프트 라인별 해설 — 왜 이렇게 썼는가

| 프롬프트에 넣은 문장 | 없으면 벌어지는 일 |
| --- | --- |
| "도메인 계층에 프레임워크 import 금지" | 애그리거트에 `@Entity` 가 붙고, 저장소를 바꿀 때 도메인을 고쳐야 한다 |
| "불변식은 애그리거트 메서드 «안에서» 검사" | 컨트롤러가 검사하고, 다른 경로로 우회하는 구멍이 생긴다 |
| "다른 애그리거트는 ID 로만 참조" | 배달 하나 읽는데 4개 테이블을 조인하고, 서비스 분리가 불가능해진다 |
| "`Clock` 을 주입하라" | `Instant.now()` 가 박혀 시간 의존 로직을 테스트할 수 없다 |
| "재시도는 회로 차단기 «안쪽»" | 회로가 열려 있어도 재시도가 반복돼 장애를 키운다 |
| "4xx 는 재시도하지 않는다" | 잘못된 요청을 3번 더 보내 서버 부하만 늘린다 |
| "지터를 넣어라" | 모든 인스턴스가 동시에 재시도해 재시도 폭풍이 난다 |
| "보상은 멱등해야 한다" | 없는 것을 지울 때 404 로 실패해 Saga 가 멈춘다 |
| "`timestamp()` 금지" | `plan` 마다 모든 리소스가 변경 대상이 된다 |
| "`envs` 는 조립만 한다" | dev 와 prd 가 서서히 달라지고, dev 에서 잡히던 문제가 prd 에서 터진다 |
| "고정 대기 대신 조건 폴링" | 느린 환경에서 깨지는 불안정한 테스트가 된다 |
| "«비밀이 남는 지점»을 정직히 적어라" | "비밀 0" 이라고 써 놓고 실제로는 남아 있어 문서 전체의 신뢰가 무너진다 |
| "쓰지 «않은» 패턴도 기록하라" | 나중에 "왜 안 썼지?"에 답할 수 없고, 재검토 시점도 놓친다 |
| "되돌릴 조건을 적어라" | 결정이 틀렸을 때 «감»으로 판단하게 된다 |
| "⑤ 검증 블록" | 「됐다」를 아무도 판단할 수 없다 |

## G‑3. 이 실습이 보여 준 것

```
   ① 5줄짜리 시나리오 → 요구사항 35건 → 서비스 6개
      「분해가 곧 설계」다. 문장을 대충 읽으면 연결이 끊긴다.

   ② 애그리거트 경계 = 트랜잭션 일관성 경계 = 서비스 경계의 «후보»
      후보에서 멈추면 나노서비스, 조정하지 않으면 분산된 단일체.

   ③ 저장소는 «접근 패턴»이 고른다
      Redis·Cosmos·Data Lake 를 나눈 대가로 분산 트랜잭션을 포기하고 Saga 를 쓴다.
      공짜는 없다. 어떤 대가를 지불할지 «고르는» 것이 설계다.

   ④ 보안은 「비밀을 관리하는 것」이 아니라 「비밀을 없애는 것」
      관리 ID 로 대체할 수 있는 곳을 전부 대체하고,
      남는 곳은 «어디에 왜 남는지» 밝힌다.

   ⑤ 검증 없는 산출물은 산출물이 아니다
      117개 테스트 · 정적 검증 7항목 · 구문 검증이
      「만들었다」를 「동작한다」로 바꾼다.
```
