> - `az group delete`는 **되돌릴 수 없습니다.** 실행 전 **리소스 그룹 이름을 두 번 확인**하고, 프롬프트에는 항상 "삭제 대상 목록을 먼저 보여주고 확인받은 뒤 실행"을 넣습니다.

> - ③ **요청** — "무엇을 해서"
> - ④ **출력** — "어디에·어떤 형식으로 저장"
>
> 아래 실습의 각 프롬프트도 이 구조로 되어 있으니, **한 줄씩 '왜 그렇게 썼는지'**를 보며 본인 업무 문장으로 바꿔 보세요.

## 1-2. Visual Studio Code · Git for Windows · Claude Desktop — URL에서 다운로드 설치

아래 **순서대로** 설치합니다. (에디터 → 버전관리 → AI 도구 순으로, 뒤 도구가 앞 도구를 활용합니다.)

   - 설치: https://git-scm.com/install/windows 에서 다운로드 → 실행 → **기본 옵션 그대로** 설치.

> 세 도구는 **"편집(VS Code) → 이력관리(Git) → 실제 작업(Claude)"** 로 서로 맞물립니다. Claude가 만든 결과물을 **VS Code로 열어 보고**, 그 변경을 **Git이 이력으로 남기며**, 그 모든 작업을 **Claude가 대신 수행**하는 구조입니다.

| 도구 | 무엇인가 (한 줄) | 이 교육에서의 목적 | 실제 활용 방식 |
| --- | --- | --- | --- |

## 1-3. 실습 전 공통 설정 — 모델 · 작업량 · 모드

> **Claude Desktop을 설치·로그인(1-2)** 했다면, 본격 실습에 들어가기 전에 아래 3가지를 한 번 맞춰 둡니다. 환경 구성은 **가볍고 빠른** 작업이 많아 이 조합이 최적입니다. *(설정은 이후 실습 내내 그대로 적용됩니다.)*

| 설정 항목 | 값 | 의미 (쉽게) |
| --- | --- | --- |
| **모델(Model)** | **Sonnet 5** | 속도·비용·품질의 균형이 좋은 범용 모델 |
| **작업량(Effort)** | **중간(Medium)** | AI가 '생각하는 깊이' — 중간이면 빠르면서도 정확 |
| **모드(Mode)** | **자동(Auto)** | 안전한 작업은 매번 확인 없이 자동 진행 → 실습이 매끄럽게 |

> ⚠️ **Part E~F(Azure 리소스 생성·삭제) 구간에서는 모드를 '자동'으로 두더라도, 프롬프트 안에 "삭제·과금 발생 작업은 실행 전 반드시 확인받아라"를 항상 포함**하세요. 자동 모드가 파괴적 작업까지 자동 승인하지 않도록 하는 안전장치입니다.

**설정 방법**

- **방법 A · Claude Desktop**: 설정(⚙️)에서 **모델 → Sonnet 5**, **작업 강도(Effort) → 중간(Medium)**, **실행 모드 → 자동(Auto)** 을 선택합니다.
- **방법 B · CLI** (`claude` 세션 안에서 — CLI 설치(1-7) 후 동일하게 적용):
  ```text
  /model      → 목록에서 'Sonnet 5' 선택 (작업 강도도 여기서 '중간(Medium)'으로 지정)
  /status     → 현재 모델·작업 강도·모드가 맞는지 확인
  ```
  - **모드(자동)**: 세션에서 **Shift+Tab** 키로 실행 모드를 바꿔 **자동(auto-accept)** 으로 맞춥니다.
  - *버전에 따라 메뉴 위치가 다를 수 있으니, 헷갈리면 `/help`·`/status`로 현재 설정을 확인하세요.*

## 1-4. 한 번에 준비 — 통합 설치 프롬프트 (Claude Desktop 또는 `claude` 세션에 붙여넣기)

> 붙여넣으면 Claude가 **상태 점검 → 없는 것만 설치 → PATH 환경변수 등록 → 폴더 생성 → (새 터미널) 어느 경로에서든 정상 구동 확인**까지 수행합니다.

```text
내 로컬 PC(Windows 11) 교육 환경을 준비해줘. 모두 "이미 있으면 건너뛰고, 없으면 설치" 원칙으로 진행하고, 권한이 필요한 작업은 먼저 알려줘.
1) Claude Desktop(https://claude.com/ko/download)·Visual Studio Code(https://code.visualstudio.com/download)·Git for Windows(https://git-scm.com/install/windows)를 설치 여부 확인 후 미설치면 설치하고,
2) WSL2(+Ubuntu)·Docker Desktop·LibreOffice·Node.js LTS·Claude Code CLI를 설치·실행해줘(가능하면 winget 사용, 이미 있으면 건너뛰기),
3) Docker Desktop은 설치 후 실행해 로그인 화면까지 안내하고(구글 계정 SSO로 회원가입/로그인 가능하다고 알려줘),
4) 실습 산출물 폴더를 만들어줘: C:\dev\workspace-igm\advanced-cloud-developer\실습산출물,
5) [PATH 자동 등록] 설치한 프로그램이 Windows Terminal의 '어느 폴더에서든' 실행되도록, 각 실행 파일이 있는 폴더를 사용자 PATH 환경변수에 영구 등록해줘(이미 등록돼 있으면 중복 추가 금지). 최소 아래를 포함해:
   - Node.js/npm: C:\Program Files\nodejs  및  npm 전역 %APPDATA%\npm
   - Claude Code CLI: 실제 설치 경로(예: %USERPROFILE%\.local\bin 또는 npm 전역),  Git: C:\Program Files\Git\cmd
   등록은 setx PATH 또는 PowerShell의 [Environment]::SetEnvironmentVariable('Path', <기존+추가>, 'User')로 하고(각 프로그램의 실제 설치 경로를 which/Get-Command으로 찾아 반영), 시스템 PATH 수정이나 관리자 권한이 필요하면 먼저 알려줘,
6) [검증] PATH가 반영된 '새 Windows Terminal'을 열거나 현재 세션 PATH를 갱신한 뒤, 임의의 폴더(예: cd C:\)로 이동해 claude --version · node -v · npm -v · git --version · docker --version 이 모두 정상 출력되는지 확인하고, claude doctor로 환경 진단까지 수행해줘,
7) 위 전체 결과를 표로 요약해서 보고해줘 — 각 도구의 '설치 여부 · PATH 등록 여부 · 어느 경로에서든 실행 확인(O/X) · 버전'을 한눈에 볼 수 있게.
```

```powershell
$add = @("C:\Program Files\nodejs", "$env:APPDATA\npm", "C:\Program Files\Git\cmd", (Split-Path (Get-Command claude -ErrorAction SilentlyContinue).Source))
$cur = [Environment]::GetEnvironmentVariable('Path','User')
foreach ($p in $add) { if ($p -and (Test-Path $p) -and ($cur -notlike "*$p*")) { $cur = "$cur;$p" } }

# PATH 반영 후 '어느 폴더에서든' 정상 구동 검증 (새 터미널 권장 · 또는 현재 세션 PATH 갱신)

cd C:\ ; claude --version ; node -v ; npm -v ; git --version ; docker --version   # 모두 버전이 출력되면 OK
```

# Part C. Claude Code 실행 & 내장 슬래시 명령

## 3-1. Claude Desktop vs Claude Code CLI — 무엇이 같고 무엇이 다른가

### 한 문장으로
> 둘은 **같은 'Claude Code 엔진'을 쓰는 두 개의 입구**입니다. **Desktop = 화면(클릭·대화) 입구**, **CLI = 명령(터미널) 입구**. 두뇌·도구·규칙(엔진)은 **공유**하고, **들어가는 문만 다릅니다.**

### 🧭 쉽게 이해하기 (비유로)
같은 **은행(= Claude Code 엔진)**에 가는데, **Desktop은 창구 직원과 대화**(클릭·채팅), **CLI는 ATM·자동응답에 명령**(터미널)으로 일을 보는 것과 같습니다. 처리하는 은행 업무(계좌·이체 = 모델·산출물)는 **동일**하고, **이용하는 방식(창구 vs 기계)** 만 다릅니다. → 그래서 **결과물은 같습니다.**

### 🗺️ 도식 — "입구는 둘, 엔진은 하나"

```
        입구 A (화면)                        입구 B (명령)
   ┌──────────────────────┐          ┌──────────────────────┐
   │   Claude Desktop      │          │  Windows Terminal      │
   │   클릭·대화 (GUI 앱)   │          │  claude 세션 (명령)    │
   └───────────┬──────────┘          └───────────┬──────────┘
               └────────────────┬────────────────┘
                                ▼
        ┌────────────────────────────────────────────┐
        │   Claude Code 코어(엔진) · 공통               │
        │   • 모델(Claude)로 계획·판단                  │
        │   • 파일 읽기·쓰기 / 명령 실행                │
        └───────────────────────┬────────────────────┘
                                ▼
                 결과물 ( 스크립트 · 리포트 · Azure 리소스 … )
```

> 위 그림의 **가운데(엔진)부터 아래(결과물)까지는 Desktop·CLI가 완전히 동일**합니다. 다른 것은 **맨 위 '입구' 한 층뿐**입니다.

### 📊 상세 비교표

| 구분 | **Claude Desktop** (방법 A) | **Claude Code CLI** (방법 B) |
| --- | --- | --- |
| **입구(형태)** | 화면형 GUI 앱 (클릭·채팅) | 터미널 명령 (`claude` 세션) |
| **주 사용 목적** | 일반 업무·문서 작업·시연·탐색 | 반복·자동화·정밀 제어·파이프라인 |
| **구동 방식** | 앱 창에 프롬프트 입력 → **대화로** 진행 | 터미널에 명령/프롬프트 → **세션 또는 1회 실행** |
| **강점** | 비개발자 친화, 결과를 화면으로 바로 확인 | 슬래시 명령, `claude -p` 비대화형, **스케줄·반복·무인화**에 강력 |
| **대표 조작** | 채팅창에 붙여넣기·전송, 파일 드래그 | `claude`, `claude -p "..."`, `/init`·`/status` |
| **엔진·모델·권한** | **공통 — 같은 Claude Code 코어** | **공통 — 같은 Claude Code 코어** |
| **적합 상황** | "지금 이 리소스를 만들어줘"류 **즉시 작업·시연** | "매일 아침 비용 리포트"류 **반복·무인화** |

### ✅ 언제 무엇을 쓰나 (선택 가이드)
- **비개발자 · 처음 · 시연 · 문서 작업** → **Desktop(방법 A)** 로 시작
- **반복 · 자동화 · 스케줄 · 정밀 제어** → **CLI(방법 B)** 로 확장
- **핵심**: 결과는 같으니 **편한 입구로 시작**하고, 자동화가 필요해지면 CLI로 넘어가면 됩니다. *(본 교육은 **Desktop 권장**, CLI는 '차이 이해'용으로 강사 데모 가능)*

## 3-3. 프롬프트 해부 — "왜 이렇게 썼나" (모든 실습 프롬프트 공통 구조)

> 실습 프롬프트를 **그냥 복붙**하지 말고 **각 줄을 왜 그렇게 썼는지** 알면, **본인 업무 문장으로 바꿔** 쓸 수 있습니다. 이 문서의 모든 프롬프트는 아래 **5블록 구조**를 따릅니다.

### 🗺️ 프롬프트 설계 도식 (공통 5블록)

```
   프롬프트 한 통 = 아래 5개 블록을 위에서 아래로 채운 것
 ┌────────────────────────────────────────────────────────────────┐
 │ ① 목표 선언   "무엇을 해줘" — 결과를 한 문장으로 먼저 못박음      │ ─▶ 방향 고정(딴짓 방지)
 ├────────────────────────────────────────────────────────────────┤
 │ ② 원칙·제약   "이렇게/이건 하지 마" — 안전·범위 규칙              │ ─▶ 실수·범위초과 예방
 ├────────────────────────────────────────────────────────────────┤
 │ ③ 작업 단계   1) 2) 3) … 번호로 나눈 구체 작업                    │ ─▶ 순서·빠짐 방지
 ├────────────────────────────────────────────────────────────────┤
 │ ④ 산출물 지정 "어디에 · 어떤 형식으로 저장"                       │ ─▶ 결과를 재사용 가능하게
 ├────────────────────────────────────────────────────────────────┤
 │ ⑤ 검증·안전   결과 검증(테스트·인수조건 충족) · 예외/실패 대응    │ ─▶ 품질 게이트 + 안전
 │               · 파괴적 작업은 먼저 확인                          │
 └────────────────────────────────────────────────────────────────┘

     ⑤는 "품질 게이트"입니다 →  ✅ 검증 : 제대로 됐는지 확인(예: 설치 후 버전 출력 확인)
                                 ✅ 테스트: 실제로 실행·클릭해 동작 확인
                                 ✅ 인수  : "이렇게 되면 합격"을 O/X로 채점(인수조건)
```

### 왜 이 5블록인가 — 각 블록의 '존재 이유'

| 블록 | 이 블록이 없으면 생기는 문제 | 그래서 이렇게 씀 |
| --- | --- | --- |
| **① 목표 선언** | 엉뚱한 걸 만들거나 답이 장황해짐 | 첫 문장에 **결과·대상**을 명령형으로 |
| **② 원칙·제약** | 멋대로 리소스를 만들거나 범위를 넘음 | "리전은 koreacentral만·삭제 전 확인" 같은 **가드레일** |
| **③ 작업 단계** | 일부를 빠뜨리거나 순서가 꼬임 | **번호 목록**으로 검증 가능하게 |
| **④ 산출물 지정** | 결과가 화면에만 뜨고 사라짐 | **경로·형식** 지정 → 다음 실습에서 재사용 |
| **⑤ 검증·안전** | 결과가 틀렸는데 '완료'로 착각 · 에러로 중단 | **검증 게이트**(테스트·인수조건 충족 확인) + "없으면 안내만 · 실패 시 대체" · 파괴적 작업 사전 확인 |

> 🚦 **⑤의 '검증 게이트'란?** 결과를 '완료'로 인정하기 전에 통과해야 하는 **품질 관문**입니다 — **검증**(제대로 됐는지 확인: 예 설치 후 `terraform version`으로 버전 확인) · **테스트**(실제로 실행·접속해 동작 확인) · **인수조건**("이렇게 되면 합격"을 O/X로 채점). *시험을 통과해야 졸업하듯*, 이 관문을 넘어야 비로소 "다 됐다"가 됩니다.

## 4-0. 먼저 정하고 시작 — 실습 명명 규칙 & 공통 변수

> 강의자료의 명령은 `"리소스 그룹 이름"`, `"vnet 이름"` 같은 **자리표시자**로 되어 있습니다. **한 명이 여러 리소스를 만들고 여러 사람이 같은 구독을 쓰므로**, 이름이 겹치면 실습이 서로 충돌합니다. 아래 규칙을 **먼저 확정**하고 모든 프롬프트에서 재사용하세요.

| 항목 | 규칙(권장 값) | 비고 |
| --- | --- | --- |
| **이니셜** `<ini>` | 본인 영문 이니셜 3자 (예: `kjs`) | 모든 이름의 충돌 방지 키 |
| **리전** | `koreacentral` | 강의자료 기준 · 모든 실습 동일 |
| **리소스 그룹** | `rg-advdev-<ini>` | 실습 단위로 분리하고 싶으면 `rg-advdev-<ini>-net` / `-data` |
| **가상 네트워크** | `vnet-advdev` / 주소 `10.0.0.0/16` | 서브넷 `subnet-1` = `10.0.0.0/24` |
| **Bastion 서브넷** | `AzureBastionSubnet` = `10.0.1.0/26` | ⚠️ **이름 고정** (다른 이름이면 배포 실패) |
| **공용 IP** | `pip-bastion`, `pip-nat`, `pip-vm1` | 모두 `Standard` SKU |
| **Bastion 호스트** | `bastion-advdev` | 생성에 **약 10분** 소요 |
| **가상 머신** | `vm-1`, `vm-2` / 이미지 `Ubuntu2204` | 관리자 계정 예: `azureuser` |
| **NAT 게이트웨이** | `natgw-advdev` | 유휴 시간 제한 10분 |
| **스토리지 계정** | `stadvdev<ini><숫자4자리>` | ⚠️ **전역 고유** · 소문자·숫자만·3~24자 |
| **MySQL 유연한 서버** | `mysql-advdev-<ini>` | ⚠️ **전역 고유** · 소문자·숫자·하이픈 |
| **Log Analytics 작업 영역** | `law-advdev-<ini>` | 모니터링 실습용 |

> 🔐 **암호 규칙**(강의자료 슬라이드 50 기준): 길이 12~123자 · **대문자·소문자·숫자·특수문자 중 3종 이상** 포함 · 백틱(`` ` ``) 사용 금지.
> **암호는 문서·프롬프트에 적지 말고**, 명령 실행 시 대화형으로 직접 입력하세요.

```
        [ 내 브라우저 ]
              │ HTTPS
              ▼
   ┌──────────────────────────────────────────────┐
   │  vnet-advdev  (10.0.0.0/16)                  │
   │  ┌────────────────────────┐                  │
   │  │ AzureBastionSubnet     │  bastion-advdev  │ ← pip-bastion (Standard)
   │  │ 10.0.1.0/26            │                  │
   │  └────────────────────────┘                  │
   │  ┌────────────────────────┐                  │
   │  │ subnet-1  10.0.0.0/24  │  vm-1 ◀─ ping ─▶ vm-2   (사설 IP 통신)
   │  └────────────────────────┘                  │
   └──────────────────────────────────────────────┘
```

> ⏱️ **소요 시간**: Bastion 배포에만 **약 10분**. VM 2대 포함 전체 **20~30분** 예상.
> 💰 **비용 주의**: Bastion은 **시간당 과금**. 실습이 끝나면 반드시 5-7의 리소스 정리를 수행하세요.

**수동 절차 요약(강의자료)**: ① 리소스 그룹 → ② VNet+서브넷 → ③ `AzureBastionSubnet` → ④ 공용 IP → ⑤ Bastion → ⑥ VM 2대 → ⑦ 포털에서 Bastion으로 VM-1 접속 → ⑧ VM-2로 ping

## 5-6. 실습 — NAT Gateway로 아웃바운드 IP 고정 (강의자료 2.8 ~ 2.19)

> 📖 슬라이드 40~58 · 참조: https://learn.microsoft.com/ko-kr/azure/virtual-network/quick-create-cli
> 🎯 **핵심 질문**: *"VM에 공용 IP가 없는데 인터넷에 어떻게 나가지?"* → **NAT Gateway가 아웃바운드 전용 출구**가 되어 줍니다. 그 결과 **밖에서 본 내 IP = NAT의 공용 IP** 가 됩니다.

```
   [ vm-1 (공용 IP 없음) ]
            │ 아웃바운드
            ▼
   ┌──────────────────────┐
   │  natgw-advdev        │  ── pip-nat (Standard) ──▶  인터넷
   │  (subnet-1 에 연결)   │
   └──────────────────────┘
            검증: vm-1 에서  curl ifconfig.me  →  pip-nat 주소와 일치하면 성공
```

**수동 절차 요약(강의자료)**: ① 리소스 그룹 → ② NAT용 공용 IP → ③ NAT 게이트웨이(유휴 10분) → ④ VNet+서브넷 → ⑤ AzureBastionSubnet → ⑥ Bastion 공용 IP → ⑦ Bastion → ⑧ VM용 공용 IP → ⑨ **서브넷에 NAT 연결(`az network vnet subnet update --nat-gateway`)** → ⑩ VM 생성 → ⑪ Bastion 접속 후 `curl ifconfig.me` 로 IP 일치 확인

### ▶ 프롬프트 — NAT Gateway 실습 (5-5 환경 재사용 버전)

```text

[산출물]

[검증]
- 인수조건: (a) natgw-advdev 가 subnet-1 에 연결됨 (b) curl ifconfig.me 결과 == pip-nat 주소
  (c) VM에는 여전히 인바운드 공용 IP가 없음.
- 3가지를 O/X로 보고하고, "NAT Gateway가 인바운드 접속을 허용하지 않는 이유"를 2줄로 설명해줘.
```

## 6-6. 실습 — 모니터링: 활동 로그 · 메트릭 · Log Analytics (강의자료 3.1 ~ 3.8)

> 📖 슬라이드 87~94 (Azure Monitor 기능·구성요소 · 메트릭 vs 로그 · 데이터 형식 5계층 · 경고 관리 · Log Analytics · 작업 영역)
> 🎯 **핵심**: 지금까지 **내가 만든 모든 리소스의 흔적**이 **활동 로그**에 남아 있습니다. 그것을 직접 확인하는 것이 이 실습입니다.

**수동 절차 요약(강의자료)**: 검색창에 **[모니터]** → [활동 로그] → 지금까지 실습한 로그 확인

### ▶ 프롬프트 — 활동 로그 조회 + 메트릭 확인 + Log Analytics 작업 영역

```text
지금까지 1차시 실습에서 내가 만든 리소스들의 흔적을 Azure Monitor로 확인하고, 모니터링 기본기를 정리해줘.
[원칙]
- 조회 중심으로 진행하고, 경고(Alert) 규칙은 만들지 마(과금·알림 발송 위험). 설계안만 문서로 제시해줘.
- Log Analytics 작업 영역은 데이터 수집량에 따라 과금되니, 생성 전에 알리고 확인을 받아.
  실습 후 삭제 대상에 포함해줘.
[단계]
1) 개념을 먼저 3줄씩 정리해줘 — 메트릭(특정 시점의 숫자 값, 실시간 시나리오)과
   로그(속성 집합을 가진 레코드, 분석 시나리오)의 차이, 그리고 각각 언제 쓰는지.
2) Azure Monitor가 수집하는 데이터 형식 5계층을 표로 정리해줘 —
   애플리케이션 / 게스트 OS / Azure 리소스 / Azure 구독 / Azure 테넌트. 각 계층의 예시 데이터를 함께.
3) az monitor activity-log list 로 최근 24시간 동안 내 구독에서 발생한 활동 로그를 조회해줘.
   리소스 그룹 생성·VNet 생성·VM 생성·스토리지 생성 같은 이번 실습의 작업이 실제로 보이는지 확인하고,
   '작업 이름 / 리소스 / 상태 / 발생 시각 / 수행자' 열로 표를 만들어줘(수행자 계정은 마스킹).
4) 포털 경로도 안내해줘: 검색창 [모니터] → [활동 로그] → 필터(리소스 그룹·시간 범위) 사용법.
5) 아직 살아 있는 리소스가 있으면 대표 메트릭을 하나 조회해줘
   (예: VM이 있으면 Percentage CPU, 스토리지가 있으면 UsedCapacity — az monitor metrics list).
   없으면 "조회 가능한 리소스 없음"으로 표시하고 넘어가.
6) Log Analytics 작업 영역 law-advdev-<ini> 생성 여부를 나에게 물어보고, 승인하면 만들어줘.
   작업 영역이 무엇인지(데이터가 수집·집계·분석되는 컨테이너), 왜 지리적 위치·데이터 격리가 중요한지 설명해줘.
7) 경고 규칙 설계안을 문서로만 만들어줘 — 최소 3개:
   (a) VM CPU 80% 초과 (b) 스토리지 가용성 저하 (c) 예산 초과.
   각각 '조건 / 심각도 / 알림 대상 / 왜 필요한가'를 표로. 실제 생성은 하지 마.
[산출물]
- 활동 로그 표·메트릭 결과·개념 정리·경고 설계안을
  …\실습산출물\1차시\F6_모니터링_실습결과.md 로 저장.
[검증]
- 인수조건: (a) 활동 로그에서 이번 실습의 리소스 생성 기록이 확인됨 (b) 데이터 형식 5계층 표 완성
  (c) 경고 규칙이 실제로 생성되지 않음(실행 명령 목록으로 증명) (d) 만든 작업 영역이 있다면 정리 목록에 포함됨.
```

# Part G. 마무리 — 전체 리소스 정리 & 비용 확인

> 🚨 **이 파트는 선택이 아니라 필수입니다.** Bastion·NAT·VM·MySQL은 **켜 두는 것만으로 과금**됩니다.

### ▶ 프롬프트 — 1차시 전체 리소스 정리 + 비용 리포트

```text
1차시 실습에서 만든 모든 Azure 리소스를 확인하고 정리한 뒤, 비용 리포트를 만들어줘.
[원칙]
- 삭제는 절대 자동 실행하지 마. 반드시 (1) 전체 목록 제시 → (2) 항목별 유지/삭제 확인 → (3) 실행 순서.
- 이번 실습과 무관한 리소스 그룹이 발견되면 삭제 목록에서 제외하고 경고만 해줘.
- 삭제 명령은 리소스 그룹 단위로만 실행하고, 개별 리소스 삭제는 하지 마(누락 방지).
[단계]
1) az group list --output table 로 전체 리소스 그룹을 보여주고, 이번 실습에서 만든 것
   (rg-advdev-<ini>, rg-advdev-<ini>-data)을 표시해줘.
2) 각 그룹별로 az resource list --output table 을 실행해 남아 있는 리소스와 개수를 보여줘.
   시간당 과금 리소스(Bastion / NAT Gateway / VM / 공용 IP Standard / MySQL 유연한 서버 /
   Log Analytics 작업 영역)를 별도로 강조 표시해줘.
3) 삭제하기 전에, 산출물로 남겨야 할 것을 백업해줘 —
   각 리소스 그룹의 리소스 목록을 JSON으로 …\실습산출물\1차시\G1_리소스_스냅샷.json 에 저장.
4) 그룹별로 "삭제할까요?"를 하나씩 물어보고, 내가 승인한 그룹만
   az group delete --name <그룹> --yes --no-wait 로 삭제해줘.
5) 삭제 후 az group exists 로 각 그룹이 false 인지 확인하고, 아직 삭제 중이면 대기 방법을 알려줘.
6) 이번 실습의 비용을 확인하는 방법을 안내해줘 — 포털 [비용 관리 + 청구] → [비용 분석],
   그리고 az consumption usage list 로 조회하는 방법. 실제 청구 반영에는 시차가 있다는 점도 알려줘.
7) 향후 실습에서 비용 사고를 막을 안전장치 3가지를 제안해줘
   (예: 구독 예산·경고 설정 / 리소스 그룹 태그로 실습용 표시 / 자동 종료 스케줄).
[산출물]
- 정리 결과와 비용 확인 방법을 …\실습산출물\1차시\G1_정리_및_비용리포트.md 로 저장.
  포함: 삭제한 그룹 / 남긴 그룹과 이유 / 각 그룹의 리소스 수 / 삭제 시각 / 비용 확인 절차.
[검증]
- 인수조건: (a) 모든 실습 리소스 그룹이 삭제되었거나, 남긴 경우 그 이유가 기록됨
  (b) 시간당 과금 리소스가 하나도 남지 않음 (c) 스냅샷 JSON이 저장됨.
- 마지막에 "다음 접속 시 포털에서 남은 리소스가 없는지 한 번 더 확인하세요"를 안내해줘.
```

**수동 명령**

```powershell
az group list --output table                              # 전체 그룹 확인
az resource list --resource-group $RG --output table      # 남은 리소스 확인 (삭제 전 필수)
az group delete --name $RG --yes --no-wait                # ⚠️ 되돌릴 수 없음
az group delete --name "$RG-data" --yes --no-wait         # ⚠️ 되돌릴 수 없음
az group exists --name $RG ; az group exists --name "$RG-data"   # 둘 다 false 면 정리 완료
```
