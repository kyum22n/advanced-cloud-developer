> **목적** — 「모니터링 및 진단」의 원칙에 따라 **메트릭·로그·추적** 세 신호를 설계하고,
> SLO 와 경고를 «숫자로» 정의합니다.

## 1. 왜 마이크로서비스에서 관측성이 «필수»인가

```
   단일체(모놀리스)                      마이크로서비스
   ─────────────────                    ────────────────
   느리다 → 스택 트레이스 하나면 끝       느리다 → 어느 서비스? 어느 호출?
                                                 큐에서 대기? DB?
   장애 → 프로세스 하나 확인              장애 → 6개 서비스 × N 인스턴스
   로그 → 파일 하나                       로그 → 여러 곳에 흩어짐
```

> 마이크로서비스에서 관측성은 «있으면 좋은 것»이 아니라 **디버깅의 유일한 수단**입니다.
> 설계 단계에서 넣지 않으면 나중에 넣을 수 없습니다(코드 전체를 고쳐야 하므로).

## 2. 세 가지 신호

| 신호 | 답하는 질문 | 저장 | 보존 |
| --- | --- | --- | --- |
| **메트릭 (Metrics)** | *"지금 시스템이 건강한가?"* | Azure Monitor 메트릭 | 93일 |
| **로그 (Logs)** | *"그때 무슨 일이 있었나?"* | Log Analytics | 30일 (prd 90일) |
| **추적 (Traces)** | *"이 요청이 어디를 거쳤고 어디서 느렸나?"* | Application Insights | 30일 |

## 3. 메트릭 설계

### 3.1 RED 메서드 — 모든 서비스가 공통으로 내보내는 3가지

| 메트릭 | 의미 | Micrometer 이름 |
| --- | --- | --- |
| **R**ate | 초당 요청 수 | `http.server.requests` (count) |
| **E**rrors | 오류율 | `http.server.requests{status=~"5.."}` |
| **D**uration | 응답 시간 분포 | `http.server.requests` (histogram, p50/p95/p99) |

### 3.2 USE 메서드 — 자원 관점

| 메트릭 | 의미 |
| --- | --- |
| **U**tilization | CPU·메모리 사용률 |
| **S**aturation | 스레드 풀 대기 큐 길이 · 커넥션 풀 대기 |
| **E**rrors | JVM GC 시간 · OOM |

### 3.3 도메인 메트릭 (이 시스템 고유)

> 기술 메트릭만으로는 «사업이 잘 돌아가는지» 알 수 없습니다.

| 메트릭 | 유형 | 태그 | 왜 필요한가 |
| --- | --- | --- | --- |
| `drone.delivery.requests` | Counter | `result=accepted\|rejected` | 예약 유입량 |
| `drone.delivery.created` | Counter | — | 실제 생성 성공 |
| `drone.delivery.completed` | Counter | — | 완료 |
| `drone.delivery.failed` | Counter | `reason` | **실패 원인 분포** |
| `drone.delivery.duration` | Timer | — | 예약 → 완료 소요 시간 |
| `drone.saga.compensated` | Counter | `step` | **어느 단계에서 보상이 발생하나** |
| `drone.assignment.rejected` | Counter | `reason=no_drone\|capacity` | 드론 부족 감지 |
| `drone.thirdparty.delegated` | Counter | — | 타사 위탁 비율 (드론 가동률의 반대 지표) |
| `drone.eta.deviation` | Distribution | — | **예측 ETA vs 실제 도착의 오차** |
| `drone.queue.depth` | Gauge | — | Service Bus 활성 메시지 |
| `drone.telemetry.received` | Counter | — | 텔레메트리 수신량 |

```java
// 도메인 메트릭 등록 예
@Component
class DeliveryMetrics {
    private final Counter created;
    private final Counter failed;
    private final Timer   duration;

    DeliveryMetrics(MeterRegistry registry) {
        this.created  = Counter.builder("drone.delivery.created")
                               .description("생성에 성공한 배달 수").register(registry);
        this.failed   = Counter.builder("drone.delivery.failed")
                               .description("실패한 배달 수").register(registry);
        this.duration = Timer.builder("drone.delivery.duration")
                             .description("예약 접수부터 완료까지 소요 시간")
                             .publishPercentiles(0.5, 0.95, 0.99)
                             .register(registry);
    }
}
```

> ⚠️ **태그 카디널리티 주의** — `deliveryId` 를 태그로 넣으면 메트릭 시계열이 무한히 늘어
> 비용이 폭발하고 쿼리가 느려집니다. **높은 카디널리티 값은 태그가 아니라 로그·추적에** 넣습니다.

## 4. 로그 설계

### 4.1 구조화 로그 (JSON)

```json
{
  "timestamp": "2026-08-29T10:31:12.482Z",
  "level": "INFO",
  "service": "workflow",
  "instance": "workflow-7d9f4b-x2k",
  "correlationId": "req-abc123",
  "deliveryId": "dlv-7f3a9c",
  "logger": "com.fabrikam.workflow.SchedulerService",
  "message": "드론 할당 완료",
  "sagaStep": "DRONE_ASSIGNED",
  "durationMs": 142
}
```

| 필드 | 필수 | 이유 |
| --- | :---: | --- |
| `correlationId` | ✅ | 서비스 횡단 검색의 유일한 열쇠 (OPS‑04) |
| `service` · `instance` | ✅ | 어느 서비스·인스턴스인가 |
| `deliveryId` | ⚠️ 해당 시 | 도메인 관점 검색 |
| `level` | ✅ | 필터링 |
| `durationMs` | ⚠️ | 느린 구간 식별 |

### 4.2 로그 수준 정책

| 수준 | 언제 | 예 |
| --- | --- | --- |
| `ERROR` | **사람이 조치해야 함** | Saga 보상 실패 · DLQ 적재 |
| `WARN` | 자동 복구했지만 알아야 함 | 재시도 발생 · 회로 차단기 열림 |
| `INFO` | 주요 상태 전이 | 배달 생성 · 드론 할당 · 완료 |
| `DEBUG` | 개발·문제 해결용 | 요청/응답 본문 (dev 만) |
| `TRACE` | 사용 안 함 | — |

```
   ❌ 흔한 실수                            ✅ 올바른 사용
   ─────────────                          ──────────────
   재시도 성공을 ERROR 로 기록              WARN (복구됨)
   → 경고가 울려도 아무도 조치 안 함          ERROR 는 «진짜 문제»에만
   → «경고 피로» → 진짜 장애를 놓침
```

### 4.3 개인정보 마스킹

```java
// 로그 출력 전 필터 — 전화번호·이메일 자동 마스킹
public class PiiMaskingConverter extends ClassicConverter {
    private static final Pattern PHONE = Pattern.compile("(01[0-9])-?(\\d{3,4})-?(\\d{4})");
    private static final Pattern EMAIL = Pattern.compile("[\\w.+-]+@[\\w.-]+\\.[a-zA-Z]{2,}");

    @Override public String convert(ILoggingEvent event) {
        String msg = event.getFormattedMessage();
        msg = PHONE.matcher(msg).replaceAll("$1-****-$3");
        msg = EMAIL.matcher(msg).replaceAll("***@***");
        return msg;
    }
}
```

| 마스킹 대상 | 규칙 |
| --- | --- |
| 전화번호 | `010-****-1234` |
| 이메일 | `***@***` |
| 좌표 | ⚠️ 배달 주소는 개인정보 — **로그에 출력 금지** (필요 시 `deliveryId` 로 조회) |
| 토큰·키 | 절대 출력 금지 |

## 5. 분산 추적 설계

### 5.1 추적 범위

```
   [Front Door] ──▶ [App Gateway] ──▶ [Ingestion] ──▶ [Service Bus] ──▶ [Workflow]
                                          │                                  │
                                     span: HTTP                        span: 큐 소비
                                          │                                  ├─▶ [Package]  span: HTTP
                                          │                                  ├─▶ [Drone]    span: HTTP
                                          │                                  └─▶ [Delivery] span: HTTP
                                          │                                              │
                                          └────────── 하나의 trace ──────────────────────┘
```

| 구간 | 자동 계측 | 수동 작업 |
| --- | :---: | --- |
| HTTP 인/아웃 | ✅ Spring Apps 자동 | — |
| Service Bus 게시/소비 | ⚠️ | **`correlationId` 를 메시지 속성으로 전파** |
| Event Hubs 발행/구독 | ⚠️ | **이벤트 봉투에 `correlationId` 포함** |
| 데이터 저장소 호출 | ✅ | — |
| 도메인 로직 구간 | ❌ | 필요 시 `@Observed` |

> ❗ **메시징 구간의 전파가 빠지면 추적이 큐에서 끊깁니다.** 이것이 가장 흔한 실수입니다.

```java
// Service Bus 게시 시 상관 ID 전파
ServiceBusMessage msg = new ServiceBusMessage(payload);
msg.setMessageId(deliveryId);                                    // 중복 감지용
msg.getApplicationProperties().put("correlationId", MDC.get("correlationId"));
sender.sendMessage(msg);

// 소비 시 복원
String correlationId = (String) message.getApplicationProperties().get("correlationId");
MDC.put("correlationId", correlationId != null ? correlationId : UUID.randomUUID().toString());
```

### 5.2 샘플링

| 환경 | 샘플링 비율 | 예외 (항상 100 %) |
| --- | --- | --- |
| dev | 100 % | — |
| stg | 50 % | 오류 · 3초 초과 요청 |
| **prd** | **10 %** | **오류 · 3초 초과 요청 · Saga 보상 발생 요청** |

> 샘플링은 비용 통제 수단이지만, **오류를 샘플링하면 안 됩니다.** 오류는 드물고 가장 중요합니다.

## 6. SLI · SLO

| # | SLI (측정 지표) | SLO (목표) | 오류 예산 (30일) |
| --- | --- | --- | --- |
| 1 | 예약 API 성공률 (`2xx`/전체, `4xx` 제외) | **99.9 %** | 43분 |
| 2 | 예약 API 지연 p95 | **≤ 300 ms** | 5 % 초과 허용 |
| 3 | 추적 API 성공률 | **99.95 %** | 22분 |
| 4 | 추적 API 지연 p95 | **≤ 150 ms** | 5 % |
| 5 | 배달 처리 완결률 (접수 → 생성) | **99.5 %** | 0.5 % |
| 6 | 큐 처리 지연 (접수 → 소비 시작) p95 | **≤ 10초** | 5 % |
| 7 | 이벤트 전파 지연 (발행 → 이력 적재) p95 | **≤ 5초** | 5 % |

### 6.1 오류 예산 정책

```
   오류 예산 소진율
   ────────────────
    < 50 %  → 정상. 새 기능 배포 계속
   50~90 %  → 주의. 위험한 변경 보류 · 안정성 작업 우선
    > 90 %  → 🛑 기능 배포 동결. 안정화만 수행
   100 % 초과 → 사후 검토(postmortem) 필수
```

## 7. 경고 (Alert) 설계

> **경고 원칙 — «사람이 지금 조치해야 하는 것»만 경고합니다.** 나머지는 대시보드로.

| # | 경고 | 조건 | 심각도 | 조치 |
| --- | --- | --- | --- | --- |
| A‑01 | 예약 API 오류율 급증 | 5분간 `5xx` > 5 % | 🔴 Sev1 | 즉시 대응 |
| A‑02 | 추적 API 지연 악화 | 10분간 p95 > 300 ms | 🟠 Sev2 | 조사 |
| A‑03 | **큐 적체** | 활성 메시지 > 5,000 (10분 지속) | 🔴 Sev1 | Workflow 확장 확인 |
| A‑04 | **DLQ 적재** | DLQ 메시지 ≥ 1 | 🟠 Sev2 | 메시지 분석 |
| A‑05 | Saga 보상 급증 | 15분간 보상 > 10건 | 🟠 Sev2 | 어느 단계인지 확인 |
| A‑06 | 회로 차단기 열림 | 열림 상태 5분 지속 | 🟠 Sev2 | 대상 서비스 확인 |
| A‑07 | 인스턴스 재시작 반복 | 15분간 재시작 ≥ 3회 | 🔴 Sev1 | 활성 프로브·OOM 확인 |
| A‑08 | **드론 부족** | 15분간 `assignment.rejected` > 20 % | 🟡 Sev3 | 운영팀 통보 (기술 문제 아님) |
| A‑09 | Cosmos DB 스로틀링 | `429` 응답 > 1 % | 🟠 Sev2 | RU 상향 검토 |
| A‑10 | Redis 메모리 | 사용률 > 85 % | 🟠 Sev2 | TTL·SKU 확인 |
| A‑11 | 오류 예산 소진 | 90 % 도달 | 🟡 Sev3 | 배포 동결 검토 |
| A‑12 | 인증 실패 급증 | 5분간 `401` > 100 | 🟠 Sev2 | **보안 사건 가능성** |

### 7.1 경고 피로 방지

| 규칙 | 이유 |
| --- | --- |
| 심각도별 알림 채널 분리 (Sev1=호출, Sev2=채팅, Sev3=티켓) | 모든 것이 «급함»이면 아무것도 급하지 않다 |
| 자동 복구되는 것은 경고하지 않음 | 재시도 1회 성공은 WARN 로그로 충분 |
| 지속 시간 조건 필수 («5분간») | 순간 스파이크로 깨우지 않음 |
| 경고마다 **조치 절차(runbook) 링크** | 깨어난 사람이 무엇을 할지 알아야 함 |

## 8. 대시보드

| 대시보드 | 대상 | 주요 위젯 |

## 9. 상태 엔드포인트

| 엔드포인트 | 확인 항목 | 사용처 |
| --- | --- | --- |
| `/actuator/health/liveness` | 애플리케이션 프로세스 | 플랫폼 재시작 판단 |
| `/actuator/health/readiness` | + 데이터 저장소·큐 연결 | 트래픽 라우팅 판단 |
| `/actuator/health` | 전체 (내부만) | 운영 조회 |
| `/actuator/prometheus` | 메트릭 노출 | 스크레이핑 |

```java
// 사용자 정의 준비 상태 — 의존성 검사에 «관대한» 타임아웃
@Component
class ServiceBusHealthIndicator implements HealthIndicator {
    @Override public Health health() {
        try {
            senderClient.createMessageBatch();          // 가벼운 확인
            return Health.up().build();
        } catch (Exception e) {
            return Health.down().withDetail("reason", "Service Bus 연결 불가").build();
        }
    }
}
```

> ⚠️ **활성(liveness) 프로브에 외부 의존성을 넣지 마세요.** Service Bus 가 잠시 느려지면
> 모든 인스턴스가 «죽었다»고 판정되어 **동시에 재시작**합니다. 의존성은 **준비(readiness)** 에만.

## 10. 구성

```yaml
management:
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health:
    probes.enabled: true
    group:
      liveness.include: livenessState
      readiness.include: readinessState,serviceBus,redis
  metrics.tags:
    service: ${spring.application.name}
    env: ${ENVIRONMENT}
  tracing.sampling.probability: ${TRACE_SAMPLING:1.0}    # prd 는 0.1

logging:
  pattern.console: '{"timestamp":"%d{ISO8601}","level":"%level","service":"${spring.application.name}","correlationId":"%X{correlationId}","deliveryId":"%X{deliveryId}","logger":"%logger{36}","message":"%msg"}%n'
  level:
    root: INFO
    com.fabrikam: ${LOG_LEVEL:INFO}
```
