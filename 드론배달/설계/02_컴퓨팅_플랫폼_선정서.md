## 4. 결정 — **Azure Spring Apps**

### 4.1 Container Apps 와의 최종 비교

두 후보가 동점입니다. 결정 요인은 **«Spring 특화»** 입니다.

| 항목 | Container Apps | Azure Spring Apps | 승 |
| --- | --- | --- | --- |
| 서비스 등록 | Dapr 서비스 호출 (Dapr 학습 필요) | **Eureka 내장** — `@LoadBalanced RestTemplate` 만 쓰면 됨 | Spring Apps |
| 구성 관리 | 앱 설정 / App Configuration | **Spring Cloud Config Server 내장** — Git 리포지토리 연동 | Spring Apps |
| 분산 추적 | Dapr + OTel 구성 | **Spring Boot 애플리케이션 자동 계측** — 코드 변경 없음 | Spring Apps |
| 0으로 축소 | ✅ 가능 | ❌ 소비 계층 외 불가 | Container Apps |
| 언어 다양성 | 모든 언어 | Java/Spring 중심 | Container Apps |
| **CON‑02** (Java/Spring 고정) | 이점 없음 | **제약이 곧 장점** | Spring Apps |

> **CON‑02 가 «Java Spring Boot 로 한정»** 하고 있으므로, Container Apps 의 «언어 다양성»은 이 프로젝트에서
> 가치가 없습니다. 반면 Spring Apps 의 «Spring 특화»는 **그대로 이익**입니다.

### 4.2 AKS 를 선택하지 않은 이유

| AKS 의 강점 | 이 시나리오에서 필요한가 |
| --- | --- |
| Kubernetes API 직접 접근 | ❌ 애플리케이션이 K8s API 를 쓰지 않는다 |
| 노드/OS 수준 제어 | ❌ GPU·특수 커널 요구 없음 |
| 서비스 메시 (Istio/Linkerd) | ⚠️ 6개 서비스에는 과함. Spring Cloud 로 충분 |
| Cilium NetworkPolicy | ⚠️ 필요하지만 Spring Apps 의 **VNet 주입 + NSG** 로 대체 가능 |
| 상태 저장 워크로드 | ❌ 모든 상태는 PaaS 저장소에 |
| 세밀한 스케줄링 | ❌ |
| **운영 부담** | 🔴 노드 업그레이드·패치·용량 계획을 우리가 해야 함 |

> ❗ **ADR‑001 에서 «운영 복잡도»를 마이크로서비스의 대가로 인정했습니다.**
> AKS 를 고르면 그 대가가 커지고, Spring Apps 를 고르면 플랫폼이 상당 부분을 흡수합니다.

### 4.3 언제 AKS 로 옮겨야 하는가 (되돌릴 조건)

| 신호 | 조치 |
| --- | --- |
| Java 가 아닌 서비스가 필요해진다 (Python ML 등) | AKS 또는 Container Apps 로 이전 |
| Pod 수준 세밀한 네트워크 정책이 반드시 필요하다 | AKS + Cilium |
| 사이드카(Sidecar) 패턴이 여러 곳에 필요하다 | AKS |
| 서비스가 20개를 넘고 메시가 필요하다 | AKS + Istio 추가 기능 |
| 비용이 AKS 노드 풀 직접 운영보다 크게 높아진다 | 비용 재산정 후 결정 |

> 대비책 — **모든 서비스를 컨테이너 이미지로도 빌드**합니다. Spring Apps 는 소스/JAR 배포와
> **컨테이너 이미지 배포**를 모두 지원하므로, AKS 로 옮길 때 이미지가 그대로 재사용됩니다.

## 5. Azure Spring Apps 구성 설계

### 5.1 계층(Tier) 선택

| 계층 | 특징 | 이 프로젝트 |
| --- | --- | --- |
| 기본(Basic) | 개발·평가용. 인스턴스 제한 | ❌ prd 부적합 |
| **표준(Standard)** | 프로덕션. VNet 주입 · 블루그린 · 자동 확장 | ✅ **dev·stg·prd 모두** |
| 엔터프라이즈(Enterprise) | Tanzu 구성 요소(Build Service·API Portal·Spring Cloud Gateway) | ⚠️ 필요 시 prd 만 |

### 5.2 애플리케이션 구성

| 앱 이름 | 공개 엔드포인트 | 인스턴스 | CPU/메모리 | 지속 스토리지 |
| --- | --- | --- | --- | --- |
| `ingestion` | ✅ (App Gateway 뒤) | 2~10 | 1 vCPU / 2 Gi | ❌ |
| `workflow` | ❌ | 1~20 | 1 vCPU / 2 Gi | ❌ |
| `delivery` | ✅ (App Gateway 뒤) | 2~12 | 1 vCPU / 2 Gi | ❌ |
| `package` | ❌ | 2~8 | 0.5 vCPU / 1 Gi | ❌ |
| `drone-scheduler` | ❌ | 2~15 | 1 vCPU / 2 Gi | ❌ |
| `delivery-history` | ✅ (조회 API) | 1~6 | 1 vCPU / 2 Gi | ❌ |

> **공개 엔드포인트는 3개만** — 나머지는 내부 전용. 「API 게이트웨이」 원칙(§05 설계서)에 따라
> 외부에 노출되는 표면적을 최소화합니다.

### 5.3 플랫폼 구성 요소 사용

| 구성 요소 | 사용 | 용도 |
| --- | --- | --- |
| **서비스 레지스트리 (Eureka)** | ✅ | Workflow → Package/Drone/Delivery 호출 시 논리 이름 사용 |
| **구성 서버 (Config Server)** | ✅ | Git 리포지토리의 환경별 `application-{env}.yml` |
| **분산 추적 (App Insights)** | ✅ | 코드 변경 없이 요청 상관 추적 |
| **블루‑그린 배포** | ✅ | `production` / `staging` 배포 슬롯 |
| **VNet 주입** | ✅ (stg·prd) | 프라이빗 엔드포인트 접근 |
| **관리 ID** | ✅ | 앱별 사용자 할당 관리 ID |

### 5.4 자동 확장 규칙

| 앱 | 규칙 | 임계값 | 근거 |
| --- | --- | --- | --- |
| `ingestion` | CPU 사용률 | 70 % | 요청 처리량에 비례 |
| `workflow` | **Service Bus 큐 활성 메시지 수** | 인스턴스당 20건 | 큐 적체 = 처리 부족 |
| `delivery` | CPU 70 % **또는** 초당 요청 수 200 | — | 읽기 폭주 대응 |
| `package` | CPU 70 % | — | |
| `drone-scheduler` | CPU 70 % **또는** 초당 요청 수 300 | — | 텔레메트리 |
| `delivery-history` | **Event Hubs 소비자 지연** | 파티션당 1,000건 | 이벤트 적체 |

```
   ⚠️ 자동 확장과 수동 인스턴스 수 지정을 동시에 하지 않습니다.
      둘 다 인스턴스 수를 바꾸려 하면 «진동(flapping)»이 발생합니다.
```

## 6. 컨테이너화 전략 (이식성 확보)

Spring Apps 는 JAR 배포도 되지만, **AKS 이전 가능성**과 **로컬 재현성**을 위해 컨테이너 이미지를 함께 만듭니다.

```dockerfile
# 멀티스테이지 · 비루트 · 고정 태그 (SEC-09, SEC-10)
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B -q dependency:go-offline
COPY src ./src
RUN mvn -B -q package -DskipTests

FROM eclipse-temurin:17.0.13_11-jre-alpine
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-jar","/app/app.jar"]
```

| 규칙 | 이유 |
| --- | --- |
| 멀티스테이지 | 빌드 도구가 최종 이미지에 남지 않음 → 공격 표면 축소 |
| 비루트 사용자 | SEC‑09 |
| **베이스 이미지 태그 고정** (`latest` 금지) | SEC‑10 · 재현 가능한 빌드 |
| `MaxRAMPercentage` | 컨테이너 메모리 제한을 JVM 이 인식 |

## 7. ADR‑004 · 컴퓨팅 플랫폼 = Azure Spring Apps

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **맥락** | CON‑02 가 Java/Spring 으로 고정. 6개 마이크로서비스. 운영 인력 제한 |
| **결정** | Azure Spring Apps 표준 계층. 컨테이너 이미지도 함께 산출해 이식성 확보 |
| **근거** | 요구사항 매핑 §3 (8충족/0미충족) + Spring 특화 이점 §4.1 |
| **결과** | ➕ 서비스 검색·구성·추적을 플랫폼이 제공 → 개발 코드 감소 ➖ 0으로 축소 불가 · Java 외 언어 제약 |
| **대안** | AKS(운영 부담), Container Apps(Spring 이점 없음), Functions/App Service(서비스 검색 없음) |
| **되돌릴 조건** | §4.3 의 5가지 신호 |
