## 1. 통신 방식 결정 원칙

```
                    ┌─────────────────────────────────────┐
                    │ 호출자가 결과를 «지금» 알아야 하는가?  │
                    └──────────┬──────────────┬───────────┘
                          예   │              │  아니오
                               ▼              ▼
                    ┌──────────────┐   ┌──────────────────────┐
                    │  동기 (REST)  │   │ 수신자가 하나인가 여럿인가│
                    └──────────────┘   └────┬──────────┬──────┘
                                     하나   │          │  여럿
                                            ▼          ▼
                                    ┌───────────┐ ┌───────────┐
                                    │ 큐(명령)   │ │ 스트림(이벤트)│
                                    │Service Bus│ │ Event Hubs │
                                    └───────────┘ └───────────┘
```

| 방식 | 장점 | 단점 | 이 시스템의 사용처 |
| --- | --- | --- | --- |
| **동기 (REST)** | 단순 · 결과 즉시 확인 · 디버깅 쉬움 | **결합도 높음** · 지연 누적 · 연쇄 실패 위험 | Workflow → 도메인 서비스 |
| **비동기 큐** | 부하 평준화 · 발신자‑수신자 분리 · 유실 방지 | 최종 일관성 · 중복 처리 대비 필요 | Ingestion → Workflow |
| **비동기 스트림** | 다중 소비자 · 높은 처리량 · 재생 가능 | 순서 보장 제한 · 스키마 관리 필요 | 도메인 이벤트 전파 |

## 3. 동기 통신 설계

### 3.1 프로토콜 선택 — REST/JSON vs gRPC

| 기준 | REST/JSON | gRPC/Protobuf | 이 프로젝트 |
| --- | --- | --- | --- |
| 성능 | 보통 | **빠름** (이진, HTTP/2) | 내부 호출량이 «폭주 경로 밖»이라 결정적이지 않음 |
| 상호 운용성 | **매우 좋음** | 클라이언트 생성 필요 | Vue UI·드론·외부 파트너가 모두 REST |
| 도구·디버깅 | **매우 좋음** (curl·브라우저) | 별도 도구 필요 | 실습·교육 관점에서 중요 |
| 스키마 강제 | ⚠️ OpenAPI 로 보완 | ✅ 컴파일 시점 | **OpenAPI + 계약 테스트**로 보완 |
| 스트리밍 | ❌ | ✅ 양방향 | 필요 없음 (스트림은 Event Hubs 담당) |

> ✅ **결정: REST/JSON 전면 사용.** 내부 호출도 REST 로 통일합니다.
> gRPC 의 성능 이점은 이 시스템의 병목(외부 API·데이터 저장소)에 비해 미미하고,
> 도구·교육·상호 운용성의 손실이 더 큽니다.
>
> **되돌릴 조건** — Workflow 내부 호출이 병목으로 측정되면 Workflow↔도메인 서비스 구간만 gRPC 로 전환.

### 3.2 서비스 검색

Azure Spring Apps 의 **서비스 레지스트리(Eureka)** 를 사용합니다.

```java
// ❌ 하드코딩 — 환경마다 URL 이 다르고 인스턴스 변화에 대응 못 함
restTemplate.getForObject("http://10.1.2.15:8080/api/packages/" + id, ...);

// ✅ 논리 이름 — 레지스트리가 실제 인스턴스로 해석 + 부하 분산
@LoadBalanced RestTemplate restTemplate;
restTemplate.getForObject("http://package-service/api/packages/" + id, ...);
```

| 논리 이름 | 실제 앱 |
| --- | --- |
| `package-service` | Spring Apps 앱 `package` |
| `drone-service` | `drone-scheduler` |
| `delivery-service` | `delivery` |
| `account-service` | `account` |

### 3.3 시간 제한 예산 (Timeout Budget)

> ❗ **시간 제한이 없는 호출은 장애를 전파합니다.** 각 호출의 예산을 **미리** 정하고 합이 상위 예산을 넘지 않게 합니다.

```
   큐 메시지 처리 전체 예산: 30초 (Service Bus 락 지속 시간 5분 내)
   ├─ Account 검증        : 2초  (연결 1초 + 읽기 1초)
   ├─ Package 등록        : 5초  (연결 1초 + 쓰기 4초)
   ├─ Drone 할당          : 8초  (연결 1초 + 경합 재시도 포함)
   ├─ Delivery 생성       : 5초
   ├─ Third-party 위탁    : 10초 (외부 — 가장 관대)
   └─ 여유                : 나머지
```

| 호출 | 연결 시간 제한 | 읽기 시간 제한 | 재시도 | 총 최악 |
| --- | --- | --- | --- | --- |
| → Account | 1s | 1s | 2회 | 6s |
| → Package | 1s | 4s | 2회 | 15s |
| → Drone | 1s | 7s | 3회 | 24s |
| → Delivery | 1s | 4s | 2회 | 15s |
| → Third‑party | 2s | 8s | **1회** | 20s |

> **규칙** — 재시도 횟수 × (연결 + 읽기) 가 상위 예산을 넘지 않아야 합니다.
> 외부 호출은 재시도를 **적게** (실패가 오래 지속될 가능성이 높으므로 빨리 회로를 엽니다).

## 4. 복원력 설계 (핵심)

### 4.1 재시도 (Retry)

```yaml
# Resilience4j 구성 예
resilience4j.retry:
  instances:
    droneService:
      maxAttempts: 3
      waitDuration: 200ms
      exponentialBackoffMultiplier: 2      # 200ms → 400ms → 800ms
      randomizedWaitFactor: 0.5            # ★ 지터 — 재시도 폭풍 방지
      retryExceptions:
        - java.io.IOException
        - org.springframework.web.client.HttpServerErrorException   # 5xx
      ignoreExceptions:
        - org.springframework.web.client.HttpClientErrorException   # 4xx ← 재시도 무의미
```

| 규칙 | 이유 |
| --- | --- |
| **4xx 는 재시도하지 않는다** | 요청 자체가 잘못됐다. 재시도해도 같은 결과 |
| **429/503 은 `Retry-After` 를 존중한다** | 서버가 알려준 대기 시간을 무시하면 상황을 악화 |
| **지수 백오프 + 지터 필수** | 지터 없으면 모든 인스턴스가 동시에 재시도 → **재시도 폭풍** |
| **재시도 대상 연산은 멱등이어야 한다** | 아니면 중복 생성 발생 → [04 API 설계서](04_API_설계서.md) §멱등성 |

### 4.2 회로 차단기 (Circuit Breaker)

```
   [닫힘 CLOSED] ──실패율 50% 초과──▶ [열림 OPEN] ──30초 경과──▶ [반열림 HALF_OPEN]
        ▲                                  │                            │
        │                            즉시 실패 반환                       │
        └──────── 시험 호출 성공 ────────────────────────────────────────┘
                                           │
                                     시험 호출 실패
                                           ▼
                                      [열림 OPEN]
```

| 대상 | 실패율 임계값 | 열림 유지 | 슬라이딩 윈도 | 폴백 |
| --- | --- | --- | --- | --- |
| `packageService` | 50 % | 30s | 20회 | 메시지를 큐로 반환 (재처리) |
| `droneService` | 50 % | 30s | 20회 | **타사 위탁 경로로 전환** |
| `deliveryService` | 50 % | 30s | 20회 | 메시지를 큐로 반환 |
| `accountService` | 60 % | 20s | 20회 | 캐시된 계정 상태 사용 (5분 이내) |
| **`thirdPartyService`** | **30 %** | **60s** | 10회 | **즉시 실패 → 배달 실패 처리 → 보상** |

> ⚠️ **회로 차단기 없이 재시도만 하면 상황이 더 나빠집니다.** 이미 과부하인 서비스에 재시도가
> 쏟아지면 회복 기회를 뺏습니다. **재시도는 «일시적 실패» 용, 회로 차단기는 «지속적 실패» 용.**

### 4.3 Bulkhead (격벽)

```
   ❌ 공유 스레드 풀                      ✅ 서비스별 격벽
   ────────────────                      ─────────────────
   [200 스레드 풀]                        [Package: 20]
     ├ Package 호출                       [Drone:   30]
     ├ Drone 호출                         [Delivery:20]
     ├ Delivery 호출                      [Account: 10]
     └ Third-party 호출 ← 여기가 느려지면  [Third-party: 10] ← 여기가 막혀도
       200 스레드 전부 대기 → 전체 마비        나머지 80 스레드는 정상
```

| 대상 | 최대 동시 호출 | 대기 큐 | 근거 |
| --- | --- | --- | --- |
| `packageService` | 20 | 50 | 내부, 빠름 |
| `droneService` | 30 | 50 | 호출량 많음 |
| `deliveryService` | 20 | 50 | |
| `accountService` | 10 | 20 | 호출량 적음 |
| **`thirdPartyService`** | **10** | **0** | 외부 — **대기 없이 즉시 거부** |

### 4.4 복원력 패턴 조합 순서

```java
// 적용 순서가 중요합니다 (바깥 → 안쪽)
@Bulkhead(name = "droneService")            // ① 동시 호출 수 제한
@CircuitBreaker(name = "droneService",      // ② 지속 실패 시 즉시 차단
                fallbackMethod = "delegateToThirdParty")
@Retry(name = "droneService")               // ③ 일시적 실패만 재시도
@TimeLimiter(name = "droneService")         // ④ 개별 호출 시간 제한
public DroneAssignment assignDrone(DeliveryId id) { ... }
```

> **순서의 이유** — 재시도가 회로 차단기 **바깥**에 있으면, 회로가 열려 있어도 재시도가 반복됩니다.
> 회로 차단기가 바깥에 있어야 «열림 상태에서는 재시도조차 하지 않고 즉시 폴백»이 됩니다.

## 5. 비동기 통신 설계

### 5.1 Service Bus 큐 — 배달 요청

| 항목 | 설정 | 이유 |
| --- | --- | --- |
| 큐 이름 | `delivery-requests` | |
| 전달 모드 | **피어‑락(Peek‑Lock)** | 처리 완료를 확인한 뒤 삭제 → 유실 방지 (REL‑05) |
| 락 지속 시간 | 5분 | 처리 예산 30초의 충분한 여유 |
| 최대 전달 횟수 | 5회 | 초과 시 DLQ 로 이동 |
| **배달 못한 편지(DLQ)** | ✅ 사용 | 실패 메시지 보존 · 수동 분석 |
| 중복 감지 | ✅ 10분 창 | `MessageId` = `deliveryId` |
| 세션 | ❌ 미사용 | 배달 간 순서 의존 없음 |
| 소비 방식 | **경쟁 소비자** | 여러 Workflow 인스턴스가 병렬 처리 |

```
   Ingestion ──▶ [delivery-requests]
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     Workflow #1   Workflow #2   Workflow #3      ← 경쟁 소비자
          │  5회 실패
          ▼
     [delivery-requests/$deadletterqueue]          ← 수동 분석 · 재처리
```

### 5.2 Event Hubs — 도메인 이벤트

| 항목 | `DeliveryTracking` | `DroneStatus` |
| --- | --- | --- |
| 파티션 수 | 8 | **16** (텔레메트리 10,000/s) |
| 파티션 키 | `deliveryId` | `droneId` |
| 보존 기간 | 7일 | 3일 |
| 소비자 그룹 | `history`, `billing` | `eta`, `analytics` |
| 캡처 | ✅ → Data Lake | ❌ |

> **파티션 키를 애그리거트 ID 로 두는 이유** — 같은 배달의 이벤트가 **같은 파티션**에 들어가
> **순서가 보장**됩니다. 무작위 키를 쓰면 `Completed` 가 `Created` 보다 먼저 처리될 수 있습니다.

### 5.3 멱등 소비자 (Idempotent Consumer)

> 큐도 스트림도 «최소 1회 전달»입니다. **중복은 반드시 옵니다.**

```java
// 소비자는 eventId 를 기록하고 중복을 걸러낸다
public void handle(DeliveryEvent event) {
    if (!processedEvents.markIfAbsent(event.eventId(), Duration.ofHours(24))) {
        log.debug("중복 이벤트 무시: {}", event.eventId());
        return;                                    // ← 이미 처리함
    }
    apply(event);
}
```

| 중복 제거 저장소 | TTL | 근거 |
| --- | --- | --- |
| Redis `SET NX EX` | 24시간 | 최대 재전달 창보다 충분히 김 |

### 5.4 Spring Cloud Stream 바인더

```yaml
spring:
  cloud:
    stream:
      bindings:
        deliveryTracking-out-0:
          destination: delivery-tracking          # Event Hubs 이름
        droneStatus-in-0:
          destination: drone-status
          group: eta                              # 소비자 그룹
      eventhubs:
        bindings:
          droneStatus-in-0:
            consumer:
              checkpoint-mode: MANUAL             # ★ 처리 성공 후에만 체크포인트
  cloud.azure:
    credential:
      managed-identity-enabled: true              # ★ 연결 문자열 없음
    eventhubs:
      namespace: ${EVENTHUB_NAMESPACE}
```

> **`checkpoint-mode: MANUAL`** — 자동 체크포인트를 쓰면 «수신했지만 처리 실패»한 이벤트가 유실됩니다.
> 처리 성공 후 명시적으로 체크포인트를 찍어야 재시작 시 되감기가 가능합니다.

## 6. 상관 ID 전파 (OPS‑04)

```
   사용자 요청
      │  X-Correlation-Id: req-abc123  (없으면 게이트웨이가 생성)
      ▼
   Ingestion ──메시지 속성에 복사──▶ Service Bus
      │                                   │
      ▼                                   ▼
   로그: correlationId=req-abc123      Workflow ──HTTP 헤더로 전파──▶ Delivery
                                          │                            │
                                          ▼                            ▼
                                   로그: req-abc123            로그: req-abc123
                                          │
                                          └──이벤트 필드로 전파──▶ Event Hubs ──▶ History
```

| 전파 지점 | 수단 |
| --- | --- |
| HTTP | `X-Correlation-Id` 헤더 (MDC 필터로 자동) |
| Service Bus | `ApplicationProperties["correlationId"]` |
| Event Hubs | 이벤트 봉투(envelope)의 `correlationId` 필드 |
| 로그 | MDC → 구조화 로그의 `correlationId` 필드 |

> Azure Spring Apps 의 분산 추적이 **HTTP 구간은 자동**으로 처리하지만,
> **메시징 구간은 직접 전파**해야 합니다. 이 부분이 빠지면 추적이 큐에서 끊깁니다.

## 7. 서비스 메시를 쓰지 않은 이유

| 서비스 메시가 주는 것 | 이 시스템에서의 대체 |
| --- | --- |
| 재시도·회로 차단기 | **Resilience4j** (애플리케이션 수준) |
| mTLS | Spring Apps 플랫폼 TLS + VNet 격리 |
| 트래픽 분할(카나리) | **Spring Apps 블루‑그린 배포** |
| 분산 추적 | **Spring Apps 내장 App Insights 통합** |
| 서비스 검색 | **Eureka (Spring Apps 서비스 레지스트리)** |
| 관측성 | Micrometer + App Insights |

> 6개 서비스 규모에서 메시(사이드카·제어 평면)의 운영 비용이 이익보다 큽니다.
> **되돌릴 조건** — 서비스 20개 초과, 다중 언어 도입, 세밀한 트래픽 정책 요구 시 AKS + Istio 로 이전.
