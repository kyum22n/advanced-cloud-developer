## 1. 자격 증명 유형 — MECE 분류

> 「Azure 리소스에 접근하는 방법」은 정확히 네 가지뿐입니다. 이 분류가 모든 판단의 기준입니다.

| # | 유형 | 비밀 존재 | 이 시스템에서 |
| --- | --- | :---: | --- |
| ① | **워크로드 ID** (페더레이션 자격 증명) | ❌ 없음 | AKS 등 Kubernetes 워크로드. **본 시스템은 Spring Apps 이므로 ②를 사용** |
| ② | **관리 ID** (사용자 할당 / 시스템 할당) | ❌ 없음 | ✅ **1순위 — Spring Apps 앱마다 사용자 할당 관리 ID** |
| ③ | **플랫폼 내장 ID** | ❌ 없음 | ACR 이미지 풀 · 진단 로그 전송 |
| ④ | **시크릿** (키·연결 문자열·인증서) | ✅ 있음 | ⚠️ **2순위 — Entra 인증을 지원하지 않는 경로만.** Key Vault 에 보관 |

```
   판단 순서
   ─────────
   ① 이 리소스가 Entra ID 데이터 평면 인증을 지원하는가?
        예 → ② 관리 ID + 데이터 평면 RBAC        ← 여기서 끝내는 것이 목표
        아니오 ↓
   ② 대체 경로(예: 다른 API)가 지원하는가?
        예 → 그 경로를 쓴다
        아니오 ↓
   ③ Key Vault 에 넣고 앱이 관리 ID 로 Key Vault 에서 읽는다
        (비밀은 존재하지만 «코드·Git·이미지에는 없다»)
```

> 🔑 **③번도 «비밀이 없는」 것이 아닙니다.** 다만 **비밀의 노출 지점이 하나(Key Vault)로 줄고**,
> 회전·감사·접근 제어가 가능해집니다. 목표는 ③을 **최소화**하는 것입니다.

## 2. 워크로드 ID vs 관리 ID — 무엇이 다른가

| | **관리 ID (Managed Identity)** | **워크로드 ID (Workload Identity)** |
| --- | --- | --- |
| 대상 | Azure 리소스(VM·App Service·Spring Apps·Functions) | **Kubernetes 워크로드(Pod)** |
| 토큰 획득 | 인스턴스 메타데이터 서비스(IMDS) | **OIDC 페더레이션** — SA 토큰 → Entra 토큰 교환 |
| 필요 구성 | 리소스에 ID 할당 + 역할 부여 | ① OIDC 발급자 활성화 ② 페더레이션 자격 증명 ③ SA 주석 ④ Pod 레이블 |
| 세분성 | **리소스 단위** | **Pod(서비스 계정) 단위** |
| 이 시스템 | ✅ **채택** (Spring Apps = Azure 리소스) | ⚠️ AKS 이전 시 채택 |

### 2.1 워크로드 ID 성립 5조건 (AKS 이전 대비)

지금은 쓰지 않지만, [02 컴퓨팅 선정서](02_컴퓨팅_플랫폼_선정서.md) §4.3 의 «AKS 이전» 시 필요합니다.

| # | 조건 | 확인 방법 |
| --- | --- | --- |
| 1 | 클러스터에 **OIDC 발급자**가 활성화되어 있다 | `az aks show --query oidcIssuerProfile.issuerUrl` |
| 2 | 클러스터에 **워크로드 ID** 기능이 활성화되어 있다 | `az aks show --query securityProfile.workloadIdentity.enabled` |
| 3 | 관리 ID 에 **페더레이션 자격 증명**이 있고 subject 가 `system:serviceaccount:<ns>:<sa>` 와 정확히 일치한다 | `az identity federated-credential list` |
| 4 | **서비스 계정**에 `azure.workload.identity/client-id` 주석이 있다 | `kubectl get sa <sa> -o yaml` |
| 5 | **Pod 에 `azure.workload.identity/use: "true"` 레이블**이 있다 | `kubectl get pod -o yaml` |

> ❗ 5개 중 하나라도 빠지면 «인증 실패»가 나는데, 오류 메시지가 원인을 정확히 알려주지 않습니다.
> **이 5항목을 순서대로 확인하는 것이 유일하게 빠른 진단법입니다.**

## 3. 리소스별 암호 없는 접근

| 리소스 | Entra 데이터 평면 인증 | 필요 역할 | 이 시스템의 방식 |
| --- | :---: | --- | --- |
| **Service Bus** | ✅ | Azure Service Bus 데이터 보낸 사람 / 받는 사람 | ② 관리 ID |
| **Event Hubs** | ✅ | Azure Event Hubs 데이터 보낸 사람 / 받는 사람 | ② 관리 ID |
| **Azure Managed Redis** | ✅ | 데이터 접근 정책 (`Data Owner` 등) | ② 관리 ID |
| **Cosmos DB (NoSQL)** | ✅ | Cosmos DB 기본 제공 데이터 기여자 (데이터 평면 RBAC) | ② 관리 ID |
| **Cosmos DB (MongoDB API)** | ⚠️ 경로에 따라 제한 | — | ④ **Key Vault** (2순위) — 지원 확인 후 ②로 전환 |
| **Storage (Data Lake)** | ✅ | Storage Blob 데이터 기여자 | ② 관리 ID · **공유 키 접근 비활성화** |
| **Key Vault** | ✅ | Key Vault 비밀 사용자 | ② 관리 ID |
| **Container Registry** | ✅ | AcrPull | ③ 플랫폼 내장 (Spring Apps 이미지 풀) |
| **Application Insights** | ✅ | Monitoring Metrics Publisher | ③ 플랫폼 내장 |
| **PostgreSQL/MySQL** (미사용) | ✅ | Entra 관리자 + 역할 | — |

### 3.1 정직한 기록 — 완전히 «비밀 0」이 되지 않는 지점

| 지점 | 이유 | 완화 |
| --- | --- | --- |
| Cosmos DB for MongoDB 연결 | Mongo 와이어 프로토콜의 인증 경로 제약 | Key Vault + 관리 ID 로 읽기 · **회전 자동화** · 접근 감사 |
| TLS 인증서 개인 키 | 필연적으로 비밀 | **Key Vault 인증서** + App Gateway 가 참조 (파일로 내려받지 않음) |
| 외부 타사 운송사 API 키 | 우리가 통제하지 않는 시스템 | Key Vault + 회전 절차 + ACL 안에서만 사용 |

> ✅ **이 세 곳 외에는 시스템 어디에도 비밀이 없습니다.** 이것이 검증 목표입니다.
> "비밀이 하나도 없다"고 주장하는 대신 **어디에 왜 남는지를 명시**하는 것이 실제 보안입니다.

## 5. 애플리케이션 구성 — 인증 모드 결정

비밀이 있을 때와 없을 때 코드가 달라지면 안 됩니다. **런타임에 스스로 판단**합니다.

```java
/**
 * 인증 모드 결정 — 명시 설정 > 관리 ID 가용 > 비밀
 *
 *   1) DB_AUTH_MODE 가 명시되면 그대로 따른다 (테스트·긴급 상황)
 *   2) 관리 ID 를 쓸 수 있고 비밀이 주어지지 않았다면 → 관리 ID
 *   3) 그 외 → 비밀
 */
public static AuthMode resolve(Environment env) {
    String explicit = env.getProperty("auth.mode", "").toLowerCase();
    if ("entra".equals(explicit) || "secret".equals(explicit)) {
        return AuthMode.valueOf(explicit.toUpperCase());
    }
    boolean miAvailable = env.getProperty("AZURE_CLIENT_ID") != null;
    boolean secretGiven = env.getProperty("DB_PASSWORD") != null;
    return (miAvailable && !secretGiven) ? AuthMode.ENTRA : AuthMode.SECRET;
}
```

| 환경 | `AZURE_CLIENT_ID` | 비밀 | 결과 |
| --- | :---: | :---: | --- |
| 로컬 개발 | ❌ | ✅ (`.env`, Git 제외) | `SECRET` |
| dev/stg/prd | ✅ | ❌ | **`ENTRA`** |
| 긴급 우회 | ✅ | ✅ + `auth.mode=secret` | `SECRET` (감사 로그 경고) |

> 🔑 **로컬 개발에서도 가능하면 Entra 를 씁니다.** `az login` 후 `DefaultAzureCredential` 이
> 개발자 계정 토큰을 사용합니다. 비밀 경로는 **CI 컨테이너 테스트 등 부득이한 경우만**.

### 5.1 Spring Cloud Azure 구성

```yaml
spring:
  cloud:
    azure:
      credential:
        managed-identity-enabled: true
        client-id: ${AZURE_CLIENT_ID}          # 앱별 사용자 할당 관리 ID
      servicebus:
        namespace: ${SERVICEBUS_NAMESPACE}
        # connection-string 없음 ★
      eventhubs:
        namespace: ${EVENTHUB_NAMESPACE}
      cosmos:
        endpoint: ${COSMOS_ENDPOINT}
        database: dronedelivery
        # key 없음 ★
      keyvault.secret:
        endpoint: ${KEYVAULT_ENDPOINT}         # 2순위 경로 전용
```

> **`client-id` 를 명시하는 이유** — 하나의 리소스에 여러 사용자 할당 ID 가 붙어 있으면
> `DefaultAzureCredential` 이 어느 것을 쓸지 모릅니다. 반드시 명시합니다.

## 8. 비밀 회전

| 비밀 | 회전 주기 | 방법 |
| --- | --- | --- |
| Cosmos Mongo 연결 문자열 | 90일 | 보조 키로 전환 → 앱 재시작 → 기본 키 재생성 |

| 관리 ID | **회전 불필요** ✅ | 토큰이 자동 갱신됨 — 이것이 ②를 1순위로 두는 이유 |

## 10. 위협 모델 요약 (STRIDE)

| 위협 | 시나리오 | 대응 |
| --- | --- | --- |
| **S**poofing | 타인의 배달을 조회 | Entra 인증 + 소유권 검증(`@PreAuthorize`) |
| **T**ampering | 배달 상태를 임의 변경 | 내부 API 는 외부 미노출 + 관리 ID 인증 |
| **R**epudiation | «내가 안 했다» | 감사 로그 + `correlationId` + 이벤트 이력 |
| **I**nformation disclosure | 개인정보 유출 | 마스킹 저장 · 로그 필터 · TLS · 프라이빗 엔드포인트 |
| **D**enial of service | 예약 API 폭주 | 속도 제한 · WAF · 큐 부하 평준화 · Bulkhead |
| **E**levation of privilege | 앱 침해 후 구독 장악 | **최소 권한 · 리소스 범위 · 구독 범위 금지(A‑01)** |

## 11. ADR‑009 · 아이덴티티 전략

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
