# 11. SDD — 명세 주도 개발 계획서

> **목적** — DDD 가 만든 «무엇을»을 **AI 협업으로 코드로 옮기는 절차**를 정의합니다.
> SDD(Spec‑Driven Development)는 «프롬프트를 잘 쓰는 법»이 아니라 **검증 가능한 명세를 단계마다 남기는 방법**입니다.
> 앞: [10_관측성_설계서.md](10_관측성_설계서.md) · 다음: [12_MECE_추적성_매트릭스.md](12_MECE_추적성_매트릭스.md)

---

## 1. SDD 가 푸는 문제

```
   ❌ 프롬프트 주도 개발                      ✅ 명세 주도 개발
   ─────────────────────                     ──────────────────
   "배달 서비스 만들어줘"                       spec.md   — 무엇을·왜 (검증 가능한 인수 조건)
        ↓                                        ↓ 사람이 검토
   그럴듯한 코드가 나옴                          plan.md   — 어떻게 (기술 결정·근거)
        ↓                                        ↓ 사람이 검토
   "아니 그게 아니라..."                        tasks.md  — 작업 단위 (각각 검증 가능)
        ↓                                        ↓ 사람이 검토
   반복 · 요구사항이 어디 있었는지 아무도 모름     코드 + 테스트
                                                 ↓
                                            인수 조건으로 검증
```

| 문제 | SDD 의 처방 |
| --- | --- |
| «무엇을 만들려 했는지»가 대화 속에 흩어진다 | **`spec.md` 가 진실의 원천** |
| AI 가 그럴듯하지만 틀린 것을 만든다 | 각 단계마다 **사람이 검토하는 관문(gate)** |
| 완성 여부를 판단할 수 없다 | **인수 조건이 곧 테스트** |
| 왜 이렇게 만들었는지 나중에 모른다 | `plan.md` 에 **결정과 근거** 기록 |

## 2. 6단계 파이프라인

```
 ①명세      ②계획       ③작업분해    ④구현      ⑤검증       ⑥통합
spec.md → plan.md → tasks.md → 코드 → 테스트 → 배포
   ▲          ▲          ▲         ▲        ▲          ▲
   └── 사람 검토 관문 (각 단계 통과 전 반드시) ──────────┘
```

| 단계 | 산출물 | 누가 주도 | 통과 기준 |
| --- | --- | --- | --- |
| ① 명세 | `spec.md` | **사람** (AI 보조) | 인수 조건이 «자동 검증 가능»한가 |
| ② 계획 | `plan.md` | AI 초안 → **사람 결정** | 대안과 근거가 적혔는가 |
| ③ 작업 분해 | `tasks.md` | AI 초안 → 사람 검토 | 각 작업이 독립 검증 가능한가 |
| ④ 구현 | 코드 | **AI 주도** | 컴파일·정적 분석 통과 |
| ⑤ 검증 | 테스트 결과 | AI + 자동화 | 인수 조건 100 % 충족 |
| ⑥ 통합 | 배포 산출물 | 자동 + **사람 승인** | 통합·E2E 통과 |

## 3. DDD 산출물 → SDD 입력 매핑

> **SDD 의 명세는 백지에서 쓰지 않습니다.** DDD 분석 산출물이 그대로 입력입니다.

| DDD 산출물 | SDD 에서의 역할 |
| --- | --- |
| 기능 요구사항 (FR) | `spec.md` 의 **사용자 스토리** |
| 불변식 (INV) | `spec.md` 의 **인수 조건** → JUnit 테스트 |
| 애그리거트·값 개체 | `plan.md` 의 **도메인 모델 구조** |
| 도메인 이벤트 | `plan.md` 의 **통합 계약** |
| 아키텍처 결정 (ADR) | `plan.md` 의 **기술 결정** |
| 서비스 경계 | `tasks.md` 의 **작업 분할 단위** |
| API 설계 (OpenAPI) | `tasks.md` 의 **완료 정의** |
| 품질 속성 (NFR) | `tasks.md` 의 **비기능 검증 항목** |

```
   분석/04 애그리거트 ──▶ plan.md 도메인 모델 ──▶ tasks.md T-DLV-01 ──▶ Delivery.java
   분석/03 INV-01     ──▶ spec.md 인수조건 AC-3 ──▶ tasks.md T-DLV-05 ──▶ DeliveryTest#cancelAfterInTransitFails
```

## 4. `spec.md` 템플릿과 예

### 4.1 구조

```markdown
# SPEC: <기능 이름>

## 1. 목적 (Why)
   이 기능이 없으면 누가 무엇을 못 하는가

## 2. 사용자 스토리 (What)
   <역할> 로서 <목표> 를 원한다, <이유> 때문에

## 3. 인수 조건 (Acceptance Criteria)   ← ★ 가장 중요
   Given / When / Then 형식. 자동 검증 가능해야 함

## 4. 범위 밖 (Out of Scope)            ← ★ 두 번째로 중요
   이번에 하지 않는 것을 명시

## 5. 비기능 요구사항
   측정 가능한 숫자로

## 6. 미결 질문
```

### 4.2 실제 예 — 배달 예약

```markdown
# SPEC: 배달 예약

## 1. 목적
사용자가 드론 배달을 요청할 수 없으면 서비스가 존재하지 않는다.
요청이 몰려도(피크 500 req/s) 사용자가 기다리지 않아야 한다.

## 2. 사용자 스토리
- 기업 사용자로서 픽업 위치·배달 위치·희망 시각으로 배달을 예약하고 싶다,
  물품을 빠르게 보내기 위해.
- 기업 사용자로서 예약 즉시 배달 번호를 받고 싶다,
  나중에 추적하기 위해.

## 3. 인수 조건

AC-1  Given 유효한 계정과 예약 요청이 주어지고
      When  POST /api/v1/deliveries 를 호출하면
      Then  202 Accepted 와 deliveryId, statusUrl 을 반환한다
      And   응답 시간 p95 ≤ 300 ms 이다                        [NFR-01]

AC-2  Given 동일한 Idempotency-Key 로 같은 요청을 두 번 보내면
      When  두 번째 요청이 처리되면
      Then  첫 번째와 동일한 deliveryId 를 반환한다
      And   배달은 1건만 생성된다                              [멱등성]

AC-3  Given 배달이 IN_TRANSIT 상태이고
      When  DELETE /api/v1/deliveries/{id} 를 호출하면
      Then  409 Conflict 를 반환한다
      And   배달 상태는 변하지 않는다                          [INV-01]

AC-4  Given 패키지 무게가 0 이하이면
      When  예약을 요청하면
      Then  400 Bad Request 와 Problem Details 를 반환한다

AC-5  Given 가용 드론이 없으면
      When  Workflow 가 드론 할당을 시도하면
      Then  타사 운송으로 위탁한다                             [FR-B-05]
      And   배달 상태는 DELEGATED 가 된다

AC-6  Given Delivery 생성이 실패하면
      When  Saga 가 보상을 실행하면
      Then  할당된 드론이 해제되고 등록된 패키지가 삭제된다     [FR-E-02]
      And   DeliveryFailed 이벤트가 발행된다

## 4. 범위 밖
- 결제·청구 (청구서 컨텍스트)
- 실제 드론 비행 제어
- 다중 패키지 배달 (1 배달 = 1 패키지)
- 예약 일정 변경 (별도 스펙)

## 5. 비기능 요구사항
- 처리량: 500 req/s (피크)          [NFR-03]
- 응답: p95 ≤ 300 ms                [NFR-01]
- 메시지 유실: 0건                   [REL-05]
- 평문 비밀: 0건                     [SEC-01]

## 6. 미결 질문
- Q1. 드론 할당 재시도 횟수는? → plan.md 에서 3회로 결정
- Q2. 타사 위탁 실패 시? → 배달 실패 처리 + 사용자 알림
```

> 🔑 **인수 조건이 곧 테스트입니다.** AC‑3 은 `DeliveryTest#cancelAfterInTransitReturns409`,
> AC‑6 은 통합 테스트 `SagaCompensationTest` 가 됩니다. **명세를 쓰는 것이 테스트를 쓰는 것입니다.**

## 5. `plan.md` 템플릿과 예

```markdown
# PLAN: 배달 예약

## 1. 참조 명세
   spec.md (AC-1 ~ AC-6)

## 2. 아키텍처 결정
| 결정 | 선택 | 대안 | 근거 |
|---|---|---|---|
| 접수 방식 | 큐 기반 부하 평준화 | 동기 처리 | AC-1 의 p95 300ms 를 동기로 달성 불가 |
| 조정 방식 | 오케스트레이션 Saga | 안무 | AC-6 보상을 위해 진행 상태를 알아야 함 |
| 멱등성 | Idempotency-Key + Redis 24h | DB 유니크 제약 | AC-2. 큐 재전달에도 대응 |
| 드론 할당 동시성 | Cosmos ETag 조건부 쓰기 | 분산 잠금 | INV-03. 잠금 서비스는 SPOF |

## 3. 컴포넌트 분해
- Ingestion  : REST 수신 → 검증 → Service Bus 게시
- Workflow   : 큐 소비 → Scheduler(4단계) + Supervisor(감시)
- Delivery   : Delivery 애그리거트 · Redis
- Package    : Package 애그리거트 · Cosmos Mongo
- DroneSched : Drone 애그리거트 · Cosmos NoSQL

## 4. 데이터 흐름
   (시퀀스 다이어그램 — 분석/04 §10 참조)

## 5. 인터페이스 계약
   공통/openapi/*.yaml (계약 우선)

## 6. 위험과 완화
| 위험 | 완화 |
|---|---|
| 큐 소비자가 계속 죽으면 무한 재시도 | 최대 전달 5회 → DLQ |
| Saga 중간에 Workflow 사망 | Supervisor 5분 타임아웃 |
| 드론 할당 경합 | ETag 조건부 쓰기 + 재시도 3회 |

## 7. 테스트 전략
| 계층 | 대상 | 도구 |
|---|---|---|
| 단위 | 애그리거트 불변식 · 값 개체 | JUnit 5 |
| 계약 | OpenAPI ↔ 실제 응답 | 계약 테스트 |
| 통합 | 서비스 간 호출 · Saga 보상 | 스크립트 + Testcontainers |
| E2E | 예약 → 추적 → 완료 | 스크립트 |
```

## 6. `tasks.md` 템플릿과 예

> **각 작업은 «독립적으로 검증 가능»해야 합니다.** «구현한다»가 아니라 «무엇이 되면 끝인가»를 씁니다.

# TASKS: 배달 예약

## 도메인 계층
- [ ] T-DOM-01  Location · Eta · PackageWeight · PackageSize 값 개체

      완료: 직렬화/역직렬화 왕복 테스트 통과

## 7. AI 협업 역할 분담

| 활동 | 사람 | AI | 이유 |
| --- | :---: | :---: | --- |
| 도메인 이해·인터뷰 | ★ | 보조 | 도메인 지식은 사람에게 있다 |
| 서브도메인 분류 | ★ | 보조 | **사업 판단** — 무엇이 경쟁 우위인가 |
| 인수 조건 작성 | ★ | 초안 | 틀리면 전부 틀린다 |
| 기술 대안 조사 | 검토 | ★ | 넓게 빠르게 |
| 아키텍처 결정 | ★ | 초안 | **되돌리기 비싼 결정** |
| 작업 분해 | 검토 | ★ | 기계적 |
| 코드 구현 | 리뷰 | ★ | |
| 테스트 작성 | 검토 | ★ | 인수 조건에서 파생 |
| 보안 검토 | ★ | 보조 | 책임이 사람에게 |
| 배포 승인 | ★ | ❌ | **절대 자동화하지 않음** |

> ⛔ **AI 에게 맡기면 안 되는 것** — ① 무엇이 핵심 도메인인가 ② 어떤 대가를 지불할 것인가
> ③ 프로덕션 배포 승인 ④ 보안 예외 승인. 이것들은 **책임이 따르는 결정**입니다.

## 8. 프롬프트 5블록 구조

> 이 과정의 표준 프롬프트 구조를 SDD 각 단계에 적용합니다.

| 블록 | 내용 | 배달 예약 예 |
| --- | --- | --- |
| **① 역할·규칙** | AI 가 취할 관점과 제약 | "DDD 를 적용하는 Java 백엔드 설계자. 도메인 계층에 프레임워크 의존 금지." |
| **② 맥락** | 참조할 산출물 | "`분석/04_전술적_DDD_모델링.md` 의 Delivery 애그리거트와 INV‑01~06" |
| **③ 작업** | 무엇을 만들 것인가 | "`tasks.md` 의 T‑DOM‑02 를 구현" |
| **④ 형식** | 산출물 형태 | "`Delivery.java` + `DeliveryTest.java`. 각 INV 마다 테스트 1개 이상" |
| **⑤ 검증** | 완료 판단 기준 | "`mvn test` 통과 · 도메인 패키지에 `org.springframework` import 0건" |

```
   ⑤ 검증 블록이 SDD 의 핵심입니다.
   «검증 기준 없는 프롬프트»는 «인수 조건 없는 요구사항»과 같습니다.
```

## 9. 관문(Gate) 체크리스트

| 관문 | 통과 조건 |
| --- | --- |
| **명세 → 계획** | ① 인수 조건이 모두 자동 검증 가능한가 ② 범위 밖이 명시됐는가 ③ NFR 이 숫자인가 |
| **계획 → 작업** | ① 각 결정에 대안과 근거가 있는가 ② 위험과 완화가 적혔는가 ③ 테스트 전략이 계층별로 있는가 |
| **작업 → 구현** | ① 각 작업에 «완료 정의»가 있는가 ② 작업이 독립적으로 검증되는가 |
| **구현 → 검증** | ① 컴파일·정적 분석 통과 ② 도메인 계층 의존성 규칙 준수 |
| **검증 → 통합** | ① 모든 인수 조건 통과 ② 통합·E2E 통과 ③ 보안 검증 항목 통과 |
| **통합 → prd** | ① stg 검증 fail=0 ② **사람 승인** |

## 10. 이 프로젝트의 SDD 산출물 위치

```
드론배달/
├── 분석/ 설계/          ← spec.md · plan.md 에 해당 (더 상세한 형태)
├── 개발/SPEC.md         ← 서비스별 명세 요약
├── 개발/TASKS.md        ← 작업 목록과 완료 정의
└── 테스트/              ← 인수 조건의 실행 가능한 형태
```

> 본 프로젝트는 `spec.md`/`plan.md` 를 **분석/·설계/ 문서로 확장**했습니다.
> 소규모 기능이라면 3개 파일로 충분하지만, 시스템 전체 설계에서는 주제별로 나누는 것이 검토에 유리합니다.
> **형식이 아니라 «단계마다 검증 가능한 명세를 남긴다»는 원칙이 SDD 입니다.**
