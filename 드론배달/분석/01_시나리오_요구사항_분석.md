> **목적** — 서술형 시나리오를 «분해 가능하고 검증 가능한» 요구사항으로 바꿉니다.

## 1. 원문 시나리오

> 가상의 회사 **Fabrikam, Inc.** 는 드론 항공기를 관리합니다. 기업들이 서비스에 등록하며, 사용자는
> 배달할 상품을 드론이 픽업하도록 요청할 수 있습니다. 고객이 픽업을 예약할 때 백엔드 시스템은
> **드론을 할당하고 예상 배달 시간을 사용자에게 알립니다.** 배달이 진행되는 동안 고객은
> **드론의 위치를 추적**하고 지속적으로 업데이트된 예상 도착 시간을 볼 수 있습니다.

## 2. 분해 1단계 — 문장에서 «사실» 뽑아내기

서술문을 잘게 자르면 아래 12개 사실(F, Fact)이 나옵니다. 이후 모든 분석은 이 12개에서 파생됩니다.

| ID | 원문 근거 | 사실 |
| --- | --- | --- |
| F‑01 | "Fabrikam은 드론 항공기를 관리" | 드론은 회사의 **자산**이며 상태·위치가 관리된다 |
| F‑02 | "기업들이 서비스에 등록" | 이용 주체는 **개인이 아니라 기업(B2B)** 이다 |
| F‑03 | "사용자는 … 요청할 수 있다" | 등록 기업 소속 **사용자**가 실제 요청자다 |
| F‑04 | "배달할 상품을" | **패키지**는 배달과 별개의 개념이다 |
| F‑05 | "드론이 픽업하도록" | 픽업 위치와 배달 위치가 **둘 다** 필요하다 |
| F‑06 | "픽업을 예약할 때" | 배달은 **미래 시점 예약**이 가능하다 |
| F‑07 | "백엔드 시스템은 드론을 할당" | **할당**은 시스템의 자동 판단이다 |
| F‑08 | "예상 배달 시간을 … 알립니다" | **ETA 계산**과 **알림 발송**은 별개 책임이다 |
| F‑09 | "사용자에게 알립니다" | 알림 채널·수신자 관리가 필요하다 |
| F‑10 | "드론의 위치를 추적" | 드론이 **위치 이벤트를 지속 발신**한다 |
| F‑11 | "지속적으로 업데이트된" | ETA는 1회성이 아니라 **재계산**된다 |
| F‑12 | "배달이 진행되는 동안" | 배달에는 **수명 주기(상태)** 가 있다 |

> ⚠️ **여기서 이미 드러나는 것** — F‑10·F‑11은 «쓰기가 매우 잦고 수명이 짧은» 데이터를,
> F‑02·F‑03은 «변경이 드물고 참조가 잦은» 데이터를 암시합니다. **저장소 선택의 근거**가 여기서 시작됩니다.
> → [설계/06_데이터_설계서.md](../설계/06_데이터_설계서.md)

## 3. 분해 2단계 — 액터 · 시스템 경계

```
        ┌─────────────────────────────────────────────────────────┐
        │                    Fabrikam 배달 시스템                  │
        │                                                          │
  기업  │  ┌──────────┐   ┌──────────┐   ┌──────────┐            │
 관리자─┼─▶│  등록·계정 │   │  배달 예약 │   │ 추적·조회  │◀───────┼── 사용자
        │  └──────────┘   └──────────┘   └──────────┘            │
        │        │              │              ▲                  │
        │        ▼              ▼              │                  │
        │  ┌──────────┐   ┌──────────┐   ┌──────────┐            │
        │  │   청구    │   │ 드론 할당  │   │  ETA 계산 │            │
        │  └──────────┘   └──────────┘   └──────────┘            │
        └────────────────────┬──────────────┬─────────────────────┘
                             │              │
                        ┌────▼────┐   ┌─────▼──────┐
                        │  드론   │   │ 타사 운송사  │
                        │ (텔레메트리)│   │  (외부 API) │
                        └─────────┘   └────────────┘
```

| 액터 | 유형 | 시스템과의 상호작용 |
| --- | --- | --- |
| **기업 관리자** | 인간 | 회사 등록, 사용자 관리, 청구서 확인 |
| **사용자** | 인간 | 배달 예약, 취소, 추적 조회 |
| **드론** | 시스템 | 위치·상태 텔레메트리 **발신**, 명령 **수신** |
| **타사 운송사** | 외부 시스템 | 드론이 커버하지 못하는 구간 위탁 |
| **콜 센터 상담원** | 인간 | 고객 문의 처리 (읽기 위주) |

## 4. 기능 요구사항 (FR) — MECE 분해

**분해 기준**: *"누구의 요청으로, 어떤 개념에 대해, 무슨 상태 변화를 일으키는가"*
서로 겹치지 않도록(Mutually Exclusive) 5개 그룹, 빠짐없이(Collectively Exhaustive) 배치했습니다.

### 그룹 A — 계정 · 등록 (액터: 기업 관리자)

| ID | 요구사항 | 우선순위 | 검증 방법 |
| --- | --- | --- | --- |
| FR‑A‑01 | 기업은 서비스에 계정을 등록할 수 있다 | 必 | 통합 테스트 |
| FR‑A‑02 | 계정에 소속된 사용자를 추가·삭제할 수 있다 | 必 | 통합 테스트 |
| FR‑A‑03 | 계정 상태(활성/정지)에 따라 예약이 차단된다 | 必 | 단위 + 통합 |
| FR‑A‑04 | 계정별 청구 내역을 조회할 수 있다 | 選 | 통합 테스트 |

### 그룹 B — 배달 예약 (액터: 사용자)

| ID | 요구사항 | 우선순위 | 검증 방법 |
| --- | --- | --- | --- |
| FR‑B‑01 | 사용자는 픽업 위치·배달 위치·픽업 희망 시각으로 배달을 예약한다 | 必 | E2E |
| FR‑B‑02 | 예약 시 패키지 정보(무게·크기)를 함께 제출한다 | 必 | E2E |
| FR‑B‑03 | 시스템은 예약 접수 즉시 **배달 ID** 를 반환한다 (처리 완료를 기다리지 않음) | 必 | E2E · 응답시간 측정 |
| FR‑B‑04 | 시스템은 조건에 맞는 드론을 자동 할당한다 | 必 | 통합 테스트 |
| FR‑B‑05 | 드론 할당이 불가하면 타사 운송으로 위탁한다 | 選 | 통합 테스트 |
| FR‑B‑06 | 사용자는 배달 시작 전까지 예약을 취소할 수 있다 | 必 | E2E |
| FR‑B‑07 | 예약 일정을 변경할 수 있다 | 選 | 통합 테스트 |

### 그룹 C — 실행 · 추적 (액터: 드론 · 사용자)

| ID | 요구사항 | 우선순위 | 검증 방법 |
| --- | --- | --- | --- |
| FR‑C‑01 | 드론은 자신의 위치·상태를 주기적으로 보고한다 | 必 | 통합 테스트 |
| FR‑C‑02 | 사용자는 배달 ID로 현재 드론 위치를 조회할 수 있다 | 必 | E2E |
| FR‑C‑03 | 시스템은 위치 변경에 따라 ETA 를 재계산한다 | 必 | 단위 테스트 |
| FR‑C‑04 | 배달 상태 변화(생성·픽업·이동·완료)마다 이벤트를 발행한다 | 必 | 통합 테스트 |
| FR‑C‑05 | 배달 완료 시 수령 확인(Confirmation)을 기록한다 | 必 | E2E |
| FR‑C‑06 | 상태 변화 시 사용자에게 알림을 발송한다 | 選 | 통합 테스트 |

### 그룹 D — 이력 · 분석 (액터: 콜 센터 · 분석가)

| ID | 요구사항 | 우선순위 | 검증 방법 |
| --- | --- | --- | --- |
| FR‑D‑01 | 완료된 배달은 장기 보관소에 적재된다 | 必 | 통합 테스트 |
| FR‑D‑02 | 배달 ID 로 과거 배달 상세를 조회할 수 있다 | 必 | E2E |
| FR‑D‑03 | 기간·계정 기준으로 배달 통계를 집계할 수 있다 | 選 | 통합 테스트 |

### 그룹 E — 운영 (액터: 운영자 · 시스템)

| ID | 요구사항 | 우선순위 | 검증 방법 |
| --- | --- | --- | --- |
| FR‑E‑01 | 각 서비스는 상태 프로브 엔드포인트를 노출한다 | 必 | 스모크 테스트 |
| FR‑E‑02 | 처리 실패한 배달은 자동 보상(취소·롤백)된다 | 必 | 통합 테스트 |
| FR‑E‑03 | 처리 지연·정체를 감지하고 경고를 발생시킨다 | 必 | 관측성 검증 |

> **합계 — 기능 요구사항 23건** (必 16 · 選 7)

## 5. 비기능 요구사항 (NFR) — 측정 가능한 형태로

> ❗ *"빨라야 한다"* 는 요구사항이 아닙니다. **숫자와 측정 조건**이 있어야 요구사항입니다.

| ID | 분류 | 요구사항 | 목표값 | 측정 지점 |
| --- | --- | --- | --- | --- |
| NFR‑01 | 성능 | 배달 예약 API 응답 시간 | p95 ≤ 300 ms | 게이트웨이 |
| NFR‑02 | 성능 | 추적 조회 API 응답 시간 | p95 ≤ 150 ms | 게이트웨이 |
| NFR‑03 | 확장성 | 피크 시 예약 처리량 | ≥ 500 req/s | 부하 테스트 |
| NFR‑04 | 확장성 | 드론 텔레메트리 수집 | ≥ 10,000 msg/s | 메시징 계층 |
| NFR‑05 | 가용성 | 예약·추적 경로 가용성 | ≥ 99.9 %/월 | 가용성 테스트 |
| NFR‑06 | 복원력 | 단일 서비스 장애가 전체로 전파되지 않음 | 연쇄 실패 0건 | 카오스 시나리오 |
| NFR‑07 | 일관성 | 배달 상태의 최종 일관성 수렴 시간 | ≤ 5 초 | 통합 테스트 |
| NFR‑08 | 보안 | 저장 데이터 접근 시 평문 비밀 사용 | **0건** | 정적 검증 |
| NFR‑09 | 보안 | 클러스터 내 서비스 간 통신 기본 정책 | **전면 거부 후 허용** | 정책 검증 |
| NFR‑10 | 관측성 | 요청 1건의 서비스 횡단 추적 | 100 % 상관 ID 전파 | 분산 추적 |
| NFR‑11 | 운영 | 신규 버전 배포 시 다운타임 | 0 초 | 배포 검증 |
| NFR‑12 | 비용 | 유휴 시간대 컴퓨팅 비용 | 피크 대비 ≤ 40 % | 비용 분석 |

## 6. 제약사항 (CON)

| ID | 제약 | 근거 · 영향 |
| --- | --- | --- |
| CON‑01 | 배포 대상은 **Azure** 로 한정 | 과정 범위. 컴퓨팅·데이터·메시징 선택지가 Azure 서비스로 제한됨 |
| CON‑02 | 백엔드는 **Java / Spring Boot** | Azure Spring Apps · Spring Cloud Azure 활용 전제 |
| CON‑03 | 프런트엔드는 **Vue.js 3** | 3차시 실습과 기술 스택 일관성 유지 |
| CON‑04 | 인프라는 **Terraform** 으로 선언 | 재현 가능성·리뷰 가능성 확보 |
| CON‑05 | 단위 테스트는 **JUnit**, API 문서는 **Swagger(OpenAPI)** | 검증 가능한 산출물 기준 |
| CON‑06 | **실제 배포·실행을 수행하지 않음** | 본 과제는 «산출물 생성»이 목적. 모든 실행은 사람이 수동으로 |
| CON‑07 | 개인정보·실제 주소 사용 금지 | 가상 좌표·가명만 사용 |
| CON‑08 | 분산 트랜잭션(2PC) 사용 불가 | 서비스별 독립 저장소 전제 → **Saga** 로 대체 |

## 8. 이 단계에서 **일부러 결정하지 않은 것**

분석 단계에서 성급히 결정하면 나중에 되돌리기 어려운 것들입니다. 명시적으로 **미결**로 남깁니다.

| 미결 항목 | 결정 시점 | 결정 문서 |
| --- | --- | --- |
| 서비스를 몇 개로 쪼갤 것인가 | 도메인 모델 완성 후 | 분석/05 |
| AKS 인가 Container Apps 인가 | 요구사항 매핑 후 | 설계/02 |
| REST 인가 gRPC 인가 | 통신 패턴 확정 후 | 설계/03·04 |
| 어떤 데이터베이스를 쓸 것인가 | 애그리거트별 접근 패턴 확인 후 | 설계/06 |

> 🔑 **핵심** — *"기술은 도메인이 결정한다."* 지금 데이터베이스를 고르면 도메인이 데이터베이스에 맞춰집니다.
