## 1. 왜 5기둥으로 다시 정리하는가

[01](01_시나리오_요구사항_분석.md) 의 NFR 12건은 «요구사항 문장» 형태입니다.
설계 단계에서는 **트레이드오프를 판단**해야 하는데, 그러려면 요구사항이 **어느 기둥에 속하는지**
알아야 합니다. 기둥끼리는 반드시 충돌하기 때문입니다.

```
        신뢰성 ◀──── 충돌 ────▶ 비용 최적화
           │                       │
           │  다중 지역 = 2배 비용   │
           ▼                       ▼
        보안 ◀───── 충돌 ────▶ 성능 효율성
                 검사·암호화 = 지연 증가
```

## 2. 기둥 1 — 신뢰성 (Reliability)

| ID | 목표 | 측정 | 설계 대응 |
| --- | --- | --- | --- |
| REL‑01 | 예약·추적 경로 가용성 ≥ 99.9 %/월 (다운타임 ≤ 43분) | 가용성 테스트 · 합성 모니터링 | 다중 영역(Availability Zone) 배포 · 최소 2 복제본 |
| REL‑02 | 단일 서비스 장애가 전체로 전파되지 않음 | 카오스 시나리오 (서비스 강제 종료) | **회로 차단기 · Bulkhead · 시간 초과** |
| REL‑03 | 일시적 오류의 자동 복구 | 통합 테스트에서 오류 주입 | **재시도(지수 백오프 + 지터)** |
| REL‑04 | 처리 실패 시 데이터 일관성 회복 | Saga 보상 테스트 | **Saga + 보상 트랜잭션 + Supervisor** |
| REL‑05 | 메시지 유실 0건 | 큐 깊이 · 배달 못한 편지(DLQ) 모니터링 | Service Bus **피어‑락 + DLQ** · 멱등 소비자 |
| REL‑06 | 상태 이상 Pod 자동 교체 | 상태 프로브 응답 확인 | **활성·준비·시작 프로브** 3종 |
| REL‑07 | 배포 실패 시 자동 롤백 | 배포 파이프라인 검증 | 파란색‑녹색 / 카나리 · 자동 롤백 조건 |

### 2.1 상태 프로브 설계 (REL‑06)

| 프로브 | 엔드포인트 | 무엇을 확인하나 | 실패 시 |
| --- | --- | --- | --- |
| **시작(startup)** | `/actuator/health/liveness` | 애플리케이션 초기화 완료 여부 | 아직 죽이지 않음 (최대 대기) |
| **활성(liveness)** | `/actuator/health/liveness` | 프로세스가 살아 있고 응답 가능한가 | **Pod 재시작** |
| **준비(readiness)** | `/actuator/health/readiness` | 의존 자원(DB·큐) 연결이 준비됐는가 | **트래픽 제외** (재시작 안 함) |

> ⚠️ **준비 프로브에 외부 의존성을 넣을 때 주의** — DB 가 잠시 느려지면 모든 Pod 가 동시에 «준비 안 됨»이
> 되어 서비스 전체가 트래픽을 못 받습니다. 의존성 검사는 **활성이 아니라 준비**에만, 그리고 **관대한 임계값**으로.

## 3. 기둥 2 — 보안 (Security)

| ID | 목표 | 측정 | 설계 대응 |
| --- | --- | --- | --- |
| SEC‑01 | 코드·이미지·Git 에 평문 비밀 **0건** | 정적 검증 스캔 | **워크로드 ID (암호 없는 연결)** |
| SEC‑02 | 각 서비스가 **고유 ID** 로 최소 권한만 가짐 | 역할 할당 감사 | 서비스별 사용자 할당 관리 ID · 리소스 범위 역할 |
| SEC‑03 | 클러스터 내부 통신 기본 정책 = **전면 거부** | 네트워크 정책 검증 | **제로 트러스트 NetworkPolicy** (기본 deny → 명시 allow) |
| SEC‑04 | 외부 송신은 승인된 FQDN 만 | 방화벽 로그 | Azure Firewall / FQDN 기반 송신 필터링 |
| SEC‑05 | 공개 엔드포인트에 WAF 검사 적용 | WAF 로그 | **Application Gateway + WAF** |
| SEC‑06 | PaaS 접근은 **프라이빗 엔드포인트** 경유 | 네트워크 구성 검증 | Private Link (ACR·Key Vault·Cosmos·Redis) |
| SEC‑07 | 전송 중 데이터 암호화 (외부·내부 모두) | TLS 스캔 | End‑to‑end TLS · (옵션) WireGuard Pod 간 암호화 |
| SEC‑08 | 컨테이너 이미지 취약점 심각도 High 이상 **0건** | 이미지 스캔 | CI 파이프라인 스캔 · Defender for Containers |
| SEC‑09 | 컨테이너는 **비루트**로 실행 | 매니페스트 정적 검증 | `runAsNonRoot: true` · 읽기 전용 루트 FS |
| SEC‑10 | `latest` 태그 사용 **0건** | 매니페스트 정적 검증 | 이미지 태그 = 커밋 SHA |

### 3.1 «비밀이 없는» 상태의 정의

```
   ❌ 금지                                ✅ 목표
   ────────────────────                   ──────────────────────────
   application.yml:                       application.yml:
     datasource:                            azure:
       password: P@ssw0rd!    ← 평문           credential:
                                                managed-identity-enabled: true
   env: DB_PASSWORD=...       ← 환경변수      # 비밀번호 자체가 존재하지 않음
   K8s Secret: cGFzc3dvcmQ=   ← base64
                              (암호화 아님)   Azure 리소스 접근 =
                                            워크로드 ID → Entra 토큰 → 리소스
```

| 계층 | 수단 | 비고 |
| --- | --- | --- |
| **1순위** | 워크로드 ID (암호 없는 연결) | Cosmos DB · Redis · Service Bus · Event Hubs · Storage 모두 지원 |
| **2순위** | Key Vault + Secrets Store CSI 드라이버 | Entra 를 지원하지 않는 서비스·타사 API 키 |
| **금지** | 코드 하드코딩 · 평문 환경변수 · Git 커밋 | 정적 검증에서 차단 |

## 4. 기둥 3 — 비용 최적화 (Cost Optimization)

| ID | 목표 | 측정 | 설계 대응 |
| --- | --- | --- | --- |
| COST‑01 | 유휴 시간대 컴퓨팅 비용 ≤ 피크 대비 40 % | 비용 분석 | 자동 확장 하한 축소 · KEDA 0 스케일(해당 서비스) |
| COST‑02 | dev 환경 월 비용 ≤ stg 의 30 % | 비용 분석 | 최소 SKU · 단일 복제본 · 개발 계층 |
| COST‑03 | 사용하지 않는 리소스 **0건** | 태그 기반 감사 | 모든 리소스에 `env`·`owner`·`expiry` 태그 필수 |
| COST‑04 | 데이터 저장 비용의 자동 계층화 | 스토리지 비용 추이 | 핫(Cosmos 1개월) → 콜드(Data Lake) 자동 이동 |
| COST‑05 | 예약 인스턴스·절감 플랜 검토 | 비용 권장 사항 | prd 안정화 후 적용 (본 과정 범위 밖) |

### 4.1 환경별 비용 전략

| 항목 | dev | stg | prd |
| --- | --- | --- | --- |
| 컴퓨팅 복제본 | 1 | 2 | 2~12 (자동 확장) |
| Redis SKU | 개발/테스트 최소 | 표준 | 프리미엄 (영역 중복) |
| Cosmos DB | 서버리스 | 프로비저닝(자동 확장) | 프로비저닝(자동 확장) |
| Service Bus | 기본 | 표준 | 프리미엄 |
| Firewall / Bastion | ❌ 없음 | ❌ 없음 | ✅ 있음 (허브) |
| 다중 영역 | ❌ | ❌ | ✅ |

> ⚠️ **비용 절감의 함정** — dev 에서 prd 와 다른 SKU 를 쓰면 «dev 에서는 되는데 prd 에서 안 되는» 문제가
> 생깁니다. **기능 차이가 아닌 규모 차이**만 두는 것이 원칙입니다. (예: Redis 개발 계층은 영역 중복만 없고 API 는 동일)

## 6. 기둥 5 — 성능 효율성 (Performance Efficiency)

| ID | 목표 | 측정 | 설계 대응 |
| --- | --- | --- | --- |
| PERF‑01 | 예약 API p95 ≤ 300 ms | 부하 테스트 | **큐 기반 부하 평준화** (처리를 응답에서 분리) |
| PERF‑02 | 추적 API p95 ≤ 150 ms | 부하 테스트 | **Redis 읽기 모델** (조인 없음) |
| PERF‑03 | 피크 500 req/s 처리 | 부하 테스트 | HPA + 클러스터 자동 확장 |
| PERF‑04 | 텔레메트리 10,000 msg/s 수집 | 부하 테스트 | Event Hubs 파티션 분산 |
| PERF‑05 | 확장 반응 시간 ≤ 60초 | 확장 이벤트 로그 | HPA 짧은 주기 · 워밍업된 노드 풀 |
| PERF‑06 | 데이터 접근이 파티션을 넘지 않음 | 쿼리 진단 | 파티션 키 = 애그리거트 ID |

### 6.1 성능 안티패턴 자가 점검

> 「성능 안티패턴」 문서의 10개 항목을 이 설계에 적용해 확인합니다.

| 안티패턴 | 이 설계에서의 위험 | 대응 |
| --- | --- | --- |
| 사용량이 많은 데이터베이스 | 드론 텔레메트리가 DB 를 포화시킴 | 이벤트 스트림으로 흡수 · 최신값만 캐시 |
| 바쁜 프런트 엔드 | Ingestion 이 무거운 처리를 함 | ✅ Ingestion 은 큐에 넣기만 함 |
| 수다스러운 I/O | Workflow 가 4회 동기 호출 | ✅ 비동기 경로라 사용자 지연과 무관. 5회 초과 시 재검토 |
| 불필요한 데이터 가져오기 | 배달 조회 시 패키지·드론까지 조인 | ✅ 읽기 모델에 필요한 필드만 비정규화 |
| 부적절한 인스턴스화 | 요청마다 HTTP 클라이언트 생성 | 커넥션 풀·클라이언트 재사용 |
| 단일 구조의 지속성 | 모든 데이터를 한 저장소에 | ✅ 폴리글랏 저장소 |
| 캐싱 없음 | 매 조회마다 원본 접근 | ✅ Redis 를 상태 저장소 겸 캐시로 |
| 시끄러운 이웃 | 한 서비스가 노드 자원을 독점 | 리소스 할당량 · 요청/제한 설정 |
| 재시도 폭풍 | 장애 시 모든 서비스가 동시 재시도 | **지수 백오프 + 지터 + 회로 차단기** |
| 동기 입출력 | 블로킹 I/O 로 스레드 고갈 | 논블로킹 클라이언트 · 시간 제한 필수 |

## 7. 트레이드오프 결정표

| 충돌 | 선택 | 근거 |
| --- | --- | --- |
| 신뢰성(다중 영역) ↔ 비용 | **prd 만 다중 영역** | dev·stg 는 가용성 SLA 대상이 아님 |
| 보안(WAF·프라이빗 링크) ↔ 성능(지연) | **보안 우선** | 추가 지연 약 10~20 ms 는 NFR‑01·02 예산 안 |
| 성능(캐시) ↔ 일관성 | **최종 일관성 허용 (≤5초)** | 배달 상태는 «즉시 정확»보다 «빠르고 곧 정확»이 사용자 가치 |
| 일관성(단일 DB) ↔ 확장성(폴리글랏) | **폴리글랏 + Saga** | NFR‑02·04 가 단일 DB 로 달성 불가 |
| 운영 단순성 ↔ 독립 배포 | **Azure Spring Apps 로 절충** | 마이크로서비스를 쓰되 플랫폼이 운영 부담을 흡수 |
| 관측성(전량 추적) ↔ 비용 | **샘플링 (prd 10 % · dev 100 %)** | 오류·느린 요청은 100 % 수집 |
