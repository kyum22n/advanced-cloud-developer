## 1. 세 가지 후보 스타일

### 1.1 N‑계층 (N‑tier)

```
   ┌────────────────────────────────────────────┐
   │  프레젠테이션 계층  (웹 서버)                 │
   ├────────────────────────────────────────────┤
   │  비즈니스 계층      (애플리케이션 서버)        │
   ├────────────────────────────────────────────┤
   │  데이터 계층        (관계형 데이터베이스)      │
   └────────────────────────────────────────────┘
   · 각 계층은 바로 아래 계층만 호출 (닫힌 계층) 또는 아래 아무 계층이나 (열린 계층)
   · Azure: VM 또는 App Service + Azure SQL / PostgreSQL
```

| 장점 | 단점 |
| --- | --- |
| 이해·구축이 쉽다. 기존 온프레미스 앱 이전(lift‑and‑shift)에 적합 | 계층 전체가 함께 배포된다 |
| 단일 데이터베이스 → **ACID 트랜잭션 자연스러움** | 부분 확장 불가 — 하나가 느리면 전체를 키워야 함 |
| 팀이 익숙하다 | 단일 실패 지점이 되기 쉽다 |
| 개발·운영 비용이 낮다 | 변경 파급이 크다 (모놀리식) |

**이 시나리오에 적용하면**

```
   웹 계층 ──▶ 비즈니스 계층 ──▶ SQL DB
                  ├ 배달 처리
                  ├ 드론 할당
                  ├ 패키지 관리
                  ├ ETA 계산
                  └ 이력 조회
```
- ✅ 초기 개발이 가장 빠르다
- ❌ **드론 텔레메트리 10,000 msg/s(NFR‑04)** 가 같은 DB 를 때린다 → 추적 조회(NFR‑02)까지 함께 느려짐
- ❌ 배달 예약이 폭주하면 **이력 조회까지 함께 확장**해야 한다 (NFR‑03·12 위반)

### 1.2 웹‑큐‑워커 (Web‑Queue‑Worker)

```
   ┌──────────┐     ┌────────┐     ┌──────────┐
   │  웹 프런트 │────▶│   큐    │────▶│  워커     │
   │  엔드     │     └────────┘     │ (백그라운드)│
   └────┬─────┘                     └─────┬────┘
        │                                 │
        └────────────┬────────────────────┘
                     ▼
              ┌─────────────┐
              │ 데이터베이스  │  + 캐시 + CDN
              └─────────────┘
   · Azure: App Service(웹) + Service Bus/Storage Queue + Functions/WebJobs(워커)
```

| 장점 | 단점 |
| --- | --- |
| 비교적 단순하면서 **부하 평준화**를 얻는다 | 웹과 워커가 **하나의 큰 덩어리**로 커지기 쉽다 |
| 웹과 워커를 **독립 확장** | 여전히 공유 데이터베이스 → 스키마 결합 |
| 관리형 서비스만으로 구성 가능 | 도메인이 복잡해지면 워커가 «만능 처리기»가 됨 |

**이 시나리오에 적용하면**

```
   Ingestion(웹) ──▶ Service Bus ──▶ Workflow(워커) ──▶ 공유 DB
```
- ✅ FR‑B‑03(즉시 응답)·NFR‑03(500 req/s) 충족
- ✅ 관리 대상이 적어 초기 운영 비용이 낮다
- ❌ 배달·패키지·드론이 **한 DB 를 공유** → 폴리글랏 저장소 불가 (Redis + Cosmos + Data Lake 를 각각 쓸 수 없음)
- ❌ 워커 하나가 4개 도메인 로직을 모두 가짐 → **팀 병렬 개발 어려움**

### 1.3 마이크로서비스

```
   API 게이트웨이
        │
   ┌────┼────┬────────┬────────┬────────┐
   ▼    ▼    ▼        ▼        ▼        ▼
  IN   DL   PK       DS       DH       WF
   │    │    │        │        │        │
   ─    RD   Mongo   NoSQL   DL+NoSQL   ─
   · 서비스별 독립 배포·확장·저장소
```

| 장점 | 단점 |
| --- | --- |
| 서비스별 **독립 배포·확장·기술 선택** | 운영 복잡도 급증 (오케스트레이션·관측성·네트워크) |
| **장애 격리** | 분산 트랜잭션 불가 → 최종 일관성을 설계해야 함 |
| 팀별 병렬 개발 | 서비스 간 통신 지연·실패 처리 필요 |
| 폴리글랏 저장소 | 초기 비용이 높다 |

## 3. 결정과 그 대가

### ✅ 결정 — **마이크로서비스**, 단 «웹‑큐‑워커의 골격을 그 안에 유지»

이 아키텍처는 **순수 마이크로서비스가 아니라 하이브리드**입니다.

```
   ┌──────────────── 웹-큐-워커 골격 (예약 경로) ────────────────┐
   │  Ingestion(웹) ──▶ Service Bus(큐) ──▶ Workflow(워커)      │
   └────────────────────────────┬───────────────────────────────┘
                                │ 워커가 «하나의 덩어리»가 아니라
                                ▼ 여러 마이크로서비스를 조정한다
   ┌──────────── 마이크로서비스 (도메인 경로) ──────────────────┐
   │   Delivery      Package      Drone       History          │
   │   (Redis)       (Mongo)      (NoSQL)     (Lake+NoSQL)     │
   └────────────────────────────────────────────────────────────┘
```

| 왜 이 조합인가 |
| --- |
| **웹‑큐‑워커** 에서 «부하 평준화와 즉시 응답»을 가져온다 → FR‑B‑03, NFR‑01·03 |
| **마이크로서비스** 에서 «독립 확장·장애 격리·폴리글랏»을 가져온다 → NFR‑02·04·06·12 |
| 웹‑큐‑워커의 약점(공유 DB, 만능 워커)을 마이크로서비스가 해소 |
| 마이크로서비스의 약점(동기 호출 지연)을 큐가 사용자 응답 경로에서 제거 |

### 3.1 지불하는 대가 (명시적으로 기록)

| 대가 | 크기 | 완화 방법 |
| --- | --- | --- |
| 운영 복잡도 | 높음 | **Azure Spring Apps** 로 서비스 등록·구성·모니터링을 플랫폼에 위임 |
| 분산 트랜잭션 불가 | 중간 | **Saga + 보상 트랜잭션** (설계/07) |
| 통합 테스트 난이도 | 높음 | 계약 테스트 + 스크립트 기반 E2E (테스트/) |
| 초기 개발 시간 | 높음 | **SDD** 로 명세→계획→작업 분해를 자동화 (설계/11) |
| 비용 | 중간 | dev 는 최소 SKU, 자동 확장 하한 축소 (설계/08) |

### 3.2 언제 이 결정을 되돌려야 하는가

> 아키텍처 결정은 **되돌릴 조건**을 함께 적어야 합니다.

| 신호 | 의미 | 조치 |
| --- | --- | --- |
| 두 서비스를 **항상 함께 배포**하고 있다 | 경계가 잘못됐다 | 두 서비스를 합친다 |
| 한 유스케이스가 **5회 이상 동기 호출**한다 | 지나치게 잘게 쪼갰다 | 합치거나 비동기로 전환 |
| 이벤트 스키마를 **자주 깨뜨린다** | 컨텍스트 경계가 틀렸다 | 컨텍스트 맵 재검토 |
| 운영 인력이 **서비스 수를 감당 못 한다** | 조직 규모 대비 과설계 | 웹‑큐‑워커로 축소 |

## 5. 아키텍처 결정 기록 (ADR)

### ADR‑001 · 마이크로서비스 + 웹‑큐‑워커 하이브리드 채택

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **일자** | 2026‑08‑29 |
| **맥락** | 예약은 폭주하고 추적은 초저지연이 필요하며, 도메인별로 저장소 요구가 완전히 다르다 |
| **결정** | 예약 경로에 큐 기반 부하 평준화를 두고, 도메인은 6개 마이크로서비스로 분리한다 |
| **근거** | 요구사항 판정표 §2 — 마이크로서비스 11충족 vs 웹‑큐‑워커 6충족 |
| **결과** | ➕ 독립 확장·장애 격리·폴리글랏 확보 ➖ 운영 복잡도·최종 일관성 설계 부담 |
| **대안** | ① 순수 N‑계층 — NFR 7건 미충족으로 기각 ② 순수 웹‑큐‑워커 — 폴리글랏 불가로 기각 |
| **되돌릴 조건** | §3.2 의 4가지 신호 |

### ADR‑002 · Supervisor 를 별도 배포 단위로 분리하지 않음

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 (재검토 가능) |
