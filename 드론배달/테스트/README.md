# 테스트 — 스크립트 기반 통합 · E2E

> 단위 테스트(JUnit·Vitest)는 [`개발/`](../개발/) 에 있습니다.
> 이 폴더는 **여러 서비스가 실제로 함께 동작하는가**를 확인합니다.

---

## 1. 테스트 계층

```
          단위          «한 클래스 안»이 옳은가            개발/ · JUnit 117 + Vitest 12
            ↓
          계약          «API 가 약속대로 응답하는가»       테스트/integration/20_contract
            ↓
          통합          «서비스 사이가 맞물리는가»         테스트/integration/30_saga
            ↓
          E2E           «사용자가 할 일을 할 수 있는가»    테스트/e2e/50_delivery_journey
```

| 계층 | 잡는 문제 | 놓치는 문제 |
| --- | --- | --- |
| **단위** | 도메인 규칙 위반 · 상태 전이 오류 | 서비스 간 계약 불일치 |
| **계약** | 문서와 실제의 차이 · 상태 코드 오용 | 여러 서비스에 걸친 흐름 |
| **통합** | Saga 보상 미실행 · 최종 일관성 미수렴 | 사용자 관점의 사용성 |
| **E2E** | 여정 자체의 단절 | 원인 위치 (느리고 범인을 못 짚는다) |

> 🔑 **E2E 를 많이 만들면 안 됩니다.** 느리고, 불안정하고, 실패했을 때 어디가 문제인지 알려 주지 않습니다.
> «가장 중요한 여정 몇 개»만 두고, 나머지는 아래 계층에서 잡습니다.

---

## 2. 구조

```
테스트/
├── scripts/
│   ├── testlib.ps1              공통 — 단언 · HTTP · 폴링 · 결과 기록
│   └── run_tests.ps1            전체 실행 (스모크 → 계약 → 통합 → E2E)
├── integration/
│   ├── 10_smoke.ps1             서비스가 살아 있는가          (8~9건)
│   ├── 20_contract.ps1          API 계약                      (9건)
│   └── 30_saga.ps1              Saga · 불변식 · 성능           (10건)
├── e2e/
│   └── 50_delivery_journey.ps1  예약 → 추적 → ETA → 이력      (6건)
└── 결과/                        JSON 기록 (실행 시 생성)
```

## 3. 실행

```bash
cd 드론배달/테스트/scripts

# 배포된 환경 대상 — 구축/출력/env.{env}.json 에서 주소를 읽는다
pwsh ./run_tests.ps1 -Env dev

# 로컬에서 서비스를 직접 띄운 경우
pwsh ./run_tests.ps1 -BaseUrl http://localhost:8081

# 실패해도 끝까지 (전체 상태를 볼 때)
pwsh ./run_tests.ps1 -Env dev -ContinueOnFailure

# E2E 제외 (빠른 확인)
pwsh ./run_tests.ps1 -Env dev -SkipE2E
```

개별 실행:

```bash
pwsh ../integration/10_smoke.ps1   -Env dev
pwsh ../integration/30_saga.ps1    -Env dev -ConvergenceTimeoutSec 60
pwsh ../e2e/50_delivery_journey.ps1 -Env dev
```

> ⚠️ **이 테스트들은 실제 API 를 호출합니다.** 배포된 환경이 있어야 하며,
> 본 과제에서는 «실제 실행하지 않음»이 전제이므로 **아직 실행되지 않았습니다**.
> 스크립트는 PowerShell 파서로 구문 검증만 마친 상태입니다(6개 파일 · 오류 0).

## 4. 무엇을 검증하는가

### 4.1 스모크 (`10_smoke`)

| ID | 검증 |
| --- | --- |
| SM‑01~04 | 4개 공개 서비스의 **활성 프로브** 응답 |
| SM‑01R~04R | **준비 프로브** — 의존 자원(DB·큐) 연결까지 준비됐는가 |
| SM‑SEC | prd 에서 **Swagger UI 차단** (SEC‑15) |

> 여기서 실패하면 나머지를 돌릴 이유가 없습니다. 그래서 가장 먼저 돌립니다.

### 4.2 계약 (`20_contract`)

| ID | 검증 | 근거 |
| --- | --- | --- |
| CT‑01 | 멱등 키 없는 `POST` → **400** | 설계/04 §4.1 |
| CT‑02 | 필수 필드 누락 → 400 + **필드 오류 목록** | |
| CT‑03·04 | 무게 0 이하 · 좌표 범위 초과 → 400 | |
| CT‑05 | 접수 → **202** + `Location` + `Retry-After` + `statusUrl` | 설계/04 §3.1 |
| CT‑06 | 없는 배달 → 404 + **`application/problem+json`** | RFC 9457 |
| CT‑07 | **상관 ID 가 그대로 돌아온다** | OPS‑04 |
| CT‑08 | 같은 멱등 키 → **같은 배달 ID** | **AC‑2** |
| CT‑09 | 같은 키 · 다른 본문 → **422** (400 아님) | 설계/04 §4.1 |

### 4.3 통합 (`30_saga`)

| ID | 검증 | 근거 |
| --- | --- | --- |
| IT‑01 | 접수한 배달이 **결국 생성된다** · 수렴 시간 측정 | NFR‑07 |
| IT‑02 | 드론 배정 또는 타사 위탁으로 진행된다 | POL‑01·03 |
| IT‑03 | **이력이 적재된다** — 이벤트가 실제로 전파된다 | FR‑D‑01 |
| IT‑04 | **INV‑01** — 이동 시작 후 취소 시 409 | 분석/03 |
| IT‑05 | 6kg 패키지는 드론에 배정되지 않는다 | 드론 용량 5kg |
| IT‑06 | 대형 패키지는 드론에 배정되지 않는다 | |
| IT‑07 | 중복 취소가 상태를 망가뜨리지 않는다 | 멱등성 |
| IT‑08 | **보상용 삭제는 대상이 없어도 204** | Saga 보상 멱등성 |
| IT‑09 | 접수 API 응답 시간 p50/p95 측정 | NFR‑01 |
| IT‑10 | 추적 API 응답 시간 p50/p95 측정 | NFR‑02 |

### 4.4 E2E (`50_delivery_journey`)

```
 ① 예약한다        POST /api/v1/deliveries → 202 + 배달 번호
 ② 추적된다        GET  /deliveries/{id}/status → 200
 ③ 배정된다        상태가 PENDING 을 벗어난다
 ④ ETA 가 나온다   미래 시각 + 신뢰도
 ⑤ 이력이 보인다   GET /history/{id} → 이정표 목록
 ⑥ 취소 여정       취소 가능 상태면 200, 아니면 409 (둘 다 «올바름»)
```

여정 전체가 **하나의 상관 ID** 를 공유합니다. 실패하면 그 ID 로
Application Insights 를 한 번에 검색할 수 있습니다.

## 5. 설계 원칙

### 5.1 «될 때까지 기다린다» — 고정 대기 금지

```powershell
# ❌ 고정 대기 — 느린 환경에서 깨지고 빠른 환경에서 느리다
Start-Sleep -Seconds 5
$status = Get-Status $id

# ✅ 조건 폴링 — 되면 즉시 진행, 안 되면 명확한 오류
Wait-Until -TimeoutSec 30 -Description '배달 생성' -Condition {
    $null -ne (Get-Status $id)
}
```

이 시스템은 **최종 일관성**을 씁니다. «접수 직후 조회하면 없을 수 있다»가 정상 동작이므로,
테스트도 그 전제로 써야 합니다.

### 5.2 4xx·5xx 를 예외가 아니라 «응답»으로

```powershell
Invoke-WebRequest -SkipHttpErrorCheck   # ★
```

«409 가 나와야 한다»를 검증해야 하는데, 기본 동작은 예외를 던집니다.

### 5.3 실패해도 멈추지 않는다 (스위트 안에서)

한 테스트의 실패가 나머지를 가리면 «무엇이 깨졌는지» 전체 그림을 볼 수 없습니다.
`Test-Case` 는 실패를 기록하고 다음으로 넘어갑니다.

단, **스위트 사이**는 멈춥니다 — 스모크가 실패했는데 E2E 를 돌리는 것은 시간 낭비입니다.

### 5.4 «올바른 결과»가 하나가 아닐 수 있다

```powershell
# 취소 요청의 결과는 상태에 따라 200 또는 409 — 둘 다 올바르다
Assert-True ($r.StatusCode -in @(200, 409))
```

실행 시점의 배달 상태를 테스트가 통제할 수 없으므로,
«상태에 따라 달라지는 올바름»을 그대로 표현합니다.
하나로 고정하면 **불안정한 테스트(flaky test)** 가 됩니다.

## 6. 결과 기록

모든 스위트가 `결과/` 에 JSON 을 남깁니다.

```json
{
  "name": "saga_dev",
  "timestamp": "2026-08-29T09:15:00.000Z",
  "pass": 10,
  "fail": 0,
  "tests": [
    { "suite": "통합 — Saga 정상 경로", "id": "IT-01",
      "name": "접수한 배달이 결국 생성된다", "passed": true, "ms": 4210, "detail": "" }
  ]
}
```

| 쓰임 | 설명 |
| --- | --- |
| **prd 승격 근거** | `구축/scripts/10_prereq.ps1 -Env prd` 가 stg 결과의 `fail = 0` 을 확인 |
| 성능 추이 | `ms` 값을 모으면 회귀를 발견할 수 있다 |
| 실패 재현 | `detail` 에 단언 실패 메시지가 그대로 남는다 |

## 7. 아직 하지 않은 것

> 범위 밖으로 두었고, 나중에 필요해지면 추가할 것들입니다.

| 항목 | 왜 지금은 안 하는가 | 언제 필요한가 |
| --- | --- | --- |
| **부하 테스트** | 500 req/s 를 만들려면 별도 도구(k6·JMeter)와 부하 생성 환경이 필요 | NFR‑03 을 실제로 판정할 때 |
| **카오스 테스트** | 서비스를 강제 종료해 연쇄 실패를 확인 — 운영 환경 통제가 필요 | NFR‑06 판정 · 운영 안정화 후 |
| **UI E2E (Playwright)** | Vue 컴포넌트 테스트로 주요 로직은 덮임 | 화면 흐름이 복잡해지면 |
| **계약 소비자 테스트 (Pact)** | 서비스가 6개라 OpenAPI 대조로 충분 | 팀·서비스가 늘어 계약 협상이 잦아지면 |
| **보안 스캔 (DAST)** | WAF 와 정적 검증이 1차 방어 | 외부 공개 전 |

## 8. 문제가 났을 때

| 증상 | 확인 |
| --- | --- |
| 스모크 전부 실패 | 서비스가 떠 있는가 · `-BaseUrl` 이 맞는가 · 방화벽 |
| 준비 프로브만 실패 | 의존 자원(Redis·Cosmos·Service Bus) 연결 — 관리 ID 역할 부여 확인 |
| 계약 CT‑05 실패 (202 가 아님) | Ingestion 이 큐에 넣지 못하고 있을 수 있다 → 503 이면 Service Bus 권한 |
| 통합 IT‑01 시간 초과 | Workflow 가 큐를 소비하지 못한다 → 큐 깊이 · DLQ 확인 |
| 통합 IT‑03 실패 (이력 없음) | Event Hubs 구독이 연결되지 않았다 |
| E2E 만 실패 | 개별 스위트를 돌려 어느 단계인지 좁힌다 |

각 실패의 상관 ID 로 Application Insights 를 검색하면 서비스 횡단 추적을 볼 수 있습니다
→ [설계/10 관측성 설계서](../설계/10_관측성_설계서.md)
