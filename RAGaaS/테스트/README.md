## 3. 평가 세트 — 함정에서 «역으로» 만든다

```
   ❌ 보통의 방법
      질의를 먼저 쓰고 → 정답 문서를 손으로 찾는다
      · 라벨링이 오래 걸리고 틀릴 수 있다
      · «찾기 쉬운 질의»만 모인다

   ✅ 이 프로젝트
      코퍼스 생성 시 «함정»을 심는다 → 정답 ID 를 이미 안다
      · 라벨링 불필요, 정확하다
      · 틀리기 쉬운 경우가 «의도적으로» 들어간다
```

| 유형 | 건수 | 검증 대상 | 판정 |
| --- | ---: | --- | --- |
| A 사실 조회 | 10 | 기본 성능 | 느슨 (주제 일치) |
| B 숫자 정밀도 | 5 | BM25 · 권위 가중 | 엄격 (문서 ID) |
| C 버전 충돌 | 5 | 최신성 | **상대 순서** |
| D 다중 홉 | 3 | 쿼리 분해 | 엄격 (전체 재현) |
| E 동의어·구어 | 6 | 벡터 · 동의어 맵 | 느슨 |
| F 권한 제한 | 4 | 보안 필터 | **위반 0건** |
| G 범위 밖 | 5 | 거절 응답 | 근거 임계값 |

### 4.2 이 표에서 읽어야 할 것

```
   ① 단일 전략이 «모든 유형»을 이기지 못한다
        boosted        전체 최고 (0.793) 이지만 다중홉 0.333
        agentic+boost  다중홉 최고 (0.556) 이지만 전체 0.713

   ② «하이브리드가 항상 낫다»는 거짓이다
        숫자 정밀도에서 keyword(1.000) > hybrid(0.400)

   ③ 가장 큰 개선은 «모델»이 아니라 «도메인 지식»이었다
        문서 유형 권위 가중 하나로
          Recall  0.609 → 0.793  (+30 %)
          MRR     0.605 → 0.801  (+32 %)
          nDCG    0.451 → 0.667  (+48 %)
```

## 5. ★ 측정하다가 배운 것

### 5.1 잘못된 지표가 «없는 문제»를 만들었다

처음에는 C 버전 충돌도 **Recall@5** 로 쟀습니다.

```
   결과: Recall@5 = 0.000     → "버전 처리가 완전히 실패했다"

   실제로 확인해 보니
     현행 문서 순위:  15위
     구버전 문서 순위: 58위      ← 이미 한참 아래

   → 구버전이 현행을 이긴 적이 «없었다»
   → 진짜 문제는 «FAQ 3,600건이 규정을 덮는 것»이었다
```

**고친 지표**

```python
if case["유형"] == "C_버전충돌":
    stale_wins = (현행 순위 없음) or (구버전 순위 < 현행 순위)
```

**결과: 전 7개 전략에서 구버전 우선 0건** ✅
진짜 문제(FAQ 노이즈)는 **권위 가중**으로 해결했습니다.

> 🔑 **지표를 정할 때는 «이 숫자가 나쁘면 무엇이 문제인가»를 먼저 물어야 합니다.**

### 5.2 재순위가 «질문 어투»를 보상하고 있었다

```
   질의  "연차휴가 일수 기준이 어떻게 되나요?"
   토큰  [연차, 차휴, 휴가, 가일, 일수, 어떻, 떻게, 게되, 되나, 나요]
                                     └──── 5개가 «질문 어투» ────┘

   «어떻게 되나요?»로 끝나는 FAQ 제목이 이 5개를 전부 맞힌다.
   정작 답이 있는 «연차휴가 일수 기준표»는 그 어투가 없어 진다.
```

→ **IDF 가중** 도입. 숫자 정밀도 Recall **0.000 → 1.000**

### 5.3 청크가 아니라 «문서» 단위로 접어야 한다

```
   같은 문서의 청크 3개가 상위 3개를 차지해도 «정답 문서 1개»를 찾은 것이다.
   청크 단위로 세면 그것이 «정답 3개»로 부풀려져 지표가 거짓말을 한다.
```

### 5.4 «짧은 FAQ»를 과소 청크로 세면 안 된다

```
   140자 FAQ 는 «파편»이 아니라 «완결된 답»이다.
   → chunk_strategy != "atomic" 인 것만 파편으로 센다
```

## 6. ⚠️ 이 측정의 한계

| 한계 | 영향 | 대응 |
| --- | --- | --- |
| **로컬 LSA 임베딩** | vector·hybrid·semantic 의 절대 수치가 실제와 다르다 | Azure 임베딩으로 재측정 |
| **합성 코퍼스** | 실사용 질의와 다르다 | 실제 문의 로그로 세트 재구성 |
| **규칙 기반 쿼리 분해** | Azure LLM 분해보다 유연성이 낮다 | 배포 후 재측정 |
| **생성 단계 미측정** | 환각·거절 정확도를 모른다 | LLM 호출 필요 |
| 38건은 적다 | 통계적 신뢰구간이 넓다 | 실 데이터로 300~500건 |

> 특히 **E 동의어에서 vector(0.500) < keyword(0.667)** 는 예상과 반대입니다.
> LSA 가 «법카 ↔ 법인카드»를 모르기 때문으로 보이지만,
> **측정하지 않았으므로 단정하지 않습니다.**
