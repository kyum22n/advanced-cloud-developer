# 09. 평가 설계서

> **목적** — "잘 되는 것 같다"를 **숫자**로 바꿉니다.
> 평가 세트가 없으면 튜닝이 «감»이 되고, 되돌릴 근거도 남지 않습니다.

## 1. 두 층의 평가

```
   ① 검색 평가 (Retrieval)     «옳은 근거를 찾았는가»
        Recall@K · Precision@K · MRR · nDCG@K
        → LLM 없이 측정 가능. 빠르고 싸다. ✅ 이 프로젝트에서 수행

   ② 생성 평가 (Generation)    «근거로 옳게 답했는가»
        근거성 · 관련성 · 완전성 · 거절 정확도
        → LLM 호출 필요. 느리고 비싸다. ⚠️ 설계만 수행
```

> 🔑 **검색이 틀리면 생성은 볼 필요가 없습니다.** 순서가 중요합니다.

## 2. 평가 세트 — 함정에서 «역으로» 만든다

### 2.1 보통의 방법과 무엇이 다른가

```
   ❌ 보통의 방법
      질의를 먼저 쓰고 → 정답 문서를 손으로 찾는다
      · 라벨링이 오래 걸린다
      · «찾기 쉬운 질의»만 모인다 (쓰는 사람이 아는 문서 위주)
      · 라벨이 틀릴 수 있다

   ✅ 이 프로젝트
      코퍼스 생성 시 «함정»을 심는다 → 정답 ID 를 이미 안다
      · 라벨링 불필요
      · 틀리기 쉬운 경우가 «의도적으로» 들어간다
      · 라벨이 정확하다
```

### 2.2 구성 (38건)

| 유형 | 건수 | 검증 대상 | 판정 방식 |
| --- | ---: | --- | --- |
| A 사실 조회 | 10 | 기본 성능 | 느슨 (주제 일치) |
| B 숫자 정밀도 | 5 | BM25 · 권위 가중 | 엄격 (문서 ID) |
| C 버전 충돌 | 5 | 최신성 | **상대 순서** |
| D 다중 홉 | 3 | 쿼리 분해 | 엄격 (전체 재현) |
| E 동의어·구어 | 6 | 벡터 · 동의어 맵 | 느슨 |
| F 권한 제한 | 4 | 보안 필터 | **위반 0건** |
| G 범위 밖 | 5 | 거절 응답 | 근거 임계값 |

### 2.3 유형마다 판정이 다른 이유

```
   A·E  «주제»가 맞으면 정답      → 답할 수 있는 문서가 여러 개다
   B·D  «문서 ID»가 맞아야 정답   → 특정 문서에만 답이 있다
   C    «상대 순서»로 판정        → 아래 §3.1 참조
   F    «없어야» 통과            → 노출 자체가 실패
   G    «근거 없음»이 정답        → 검색 지표로는 잴 수 없다
```

## 3. 지표 설계 — 잘못 잡으면 없는 문제를 만든다

### 3.1 ★ 실제로 겪은 착시

**처음 설계한 지표: C 버전 충돌도 Recall@5 로 측정**

```
   결과: Recall@5 = 0.000     → "버전 처리가 완전히 실패했다"

   실제로 확인해 보니
     현행 문서 순위:  15위
     구버전 문서 순위: 58위      ← 이미 한참 아래

   → 구버전이 현행을 이긴 적이 «없었다»
   → 진짜 문제는 «FAQ 3,600건이 규정을 덮는 것»이었다
```

**고친 지표: «구버전이 현행보다 위에 오는가»**

```python
if case["유형"] == "C_버전충돌":
    cur = 현행 문서의 순위
    old = 구버전 문서의 순위
    stale_wins = (cur is None) or (old < cur)     # ← 이것이 실패다
```

**결과: 전 7개 전략에서 «구버전 우선» 0건** ✅

> 🔑 **잘못된 지표는 «없는 문제»를 만들고 «있는 문제»를 감춥니다.**
> 지표를 정할 때는 «이 숫자가 나쁘면 무엇이 문제인가»를 먼저 물어야 합니다.

### 3.2 문서 단위로 접는 이유

```python
# 청크 → 문서로 접기 (순서 유지, 중복 제거)
seen, docs = set(), []
for i in order:
    pid = chunks[i]["parent_id"]
    if pid not in seen:
        seen.add(pid); docs.append(pid)
```

```
   같은 문서의 청크 3개가 상위 3개를 차지해도 «정답 문서 1개»를 찾은 것이다.
   청크 단위로 세면 그것이 «정답 3개»로 부풀려져 지표가 거짓말을 한다.
```

## 4. 검색 지표

| 지표 | 의미 | 언제 보나 |
| --- | --- | --- |
| **Recall@K** | 정답 중 상위 K 에 들어온 비율 | «찾았는가» |
| **Precision@K** | 상위 K 중 정답인 비율 | «노이즈가 섞였는가» |
| **MRR** | 첫 정답의 순위 역수 | «맨 위에 있는가» |
| **nDCG@K** | 순위 가중 정확도 | 위쪽 정답에 더 큰 점수 |
| **보안 위반** | 제한 문서 노출 수 | ★ **0이어야 한다** |
| **구버전 우선** | 폐지가 현행보다 위 | ★ **0이어야 한다** |
| **범위밖 근거찾음** | 답 없는데 근거 반환 | 환각 위험 지표 |

### 4.1 Recall 과 MRR 을 함께 보는 이유

```
   Recall@5 = 1.000, MRR = 0.200
     → 정답이 5위 안에 «있긴 있다». 그런데 5위다.
     → LLM 에 근거 5건을 넣으면 들어가지만, 3건만 넣으면 빠진다

   Recall@5 = 0.600, MRR = 1.000
     → 정답 일부만 찾았지만 «맨 위»에 있다
     → 사용자 체감은 더 좋을 수 있다
```

### 4.2 nDCG 를 쓰는 이유

```
   Recall 은 «1위에 있든 5위에 있든» 같게 본다.
   nDCG 는 위쪽 정답에 더 큰 점수를 준다.
     1위 정답 → 1/log2(2) = 1.000
     5위 정답 → 1/log2(6) = 0.387
```

## 6. 생성 평가 (설계만)

### 6.1 지표

| 지표 | 질문 | 측정 방법 |
| --- | --- | --- |
| **근거성 (Groundedness)** | 답변이 근거에 «있는» 내용인가 | Content Safety Groundedness 또는 LLM‑judge |
| **관련성 (Relevance)** | 답변이 질문에 답하는가 | LLM‑judge |
| **완전성 (Completeness)** | 필요한 내용이 다 있는가 | 다중 홉에서 중요 |
| **거절 정확도** | 모를 때 «모른다»고 하는가 | G 유형으로 측정 |
| **인용 정확도** | 인용한 문서에 그 내용이 있는가 | 문자열 대조 |
| **유해성** | 부적절한 표현이 없는가 | Content Safety |

### 6.2 거절 정확도 — G 유형 전용

```
   질의 5건 (답이 없는 질문)
     → 봇이 «찾지 못했습니다»라고 답한 비율 = 거절 정확도

   목표: 100 %
   실패: 그럴듯한 답을 지어냄 → «환각»
```

### 6.3 왜 이 프로젝트에서 하지 못했나

```
   생성 평가에는 다음이 필요하다
     · Azure OpenAI 배포와 자격 증명
     · 실제 LLM 호출 (과금)
     · Content Safety 리소스

   이 프로젝트는 «실제 Azure 배포·과금은 별도 판단»(CON-07)이 전제이므로
   검색 평가까지만 수행했다.
```

> ⚠️ **운영 도입 전에 반드시 생성 평가를 수행해야 합니다.**
> 검색이 완벽해도 LLM 이 근거를 무시하면 소용없습니다.

## 7. 회귀 방지 — 언제 다시 재는가

```
   ① 청킹 파라미터 변경     → 전체 재평가
   ② 임베딩 모델·차원 변경  → 전체 재평가
   ③ 권위 가중치 조정       → 전체 재평가
   ④ 시스템 프롬프트 변경   → 생성 평가만
   ⑤ 코퍼스 대량 추가       → 전체 재평가
   ⑥ 정기 (월 1회)          → 전체 재평가 + 실사용 로그 반영
```

### 7.1 평가 결과를 «기록»한다

```json
{
  "K": 5, "사례수": 38, "청크수": 12863, "임베딩": "local-lsa",
  "요약": { "boosted": { "Recall@5": 0.793, "MRR": 0.801, … } },
  "상세": { … 사례별 결과 … },
  "주의": [
    "로컬 LSA 임베딩 기준. Azure OpenAI 로 재측정 필요",
    "합성 코퍼스 기준. 실제 문서로 옮기면 다시 평가해야 함",
    "범위밖 지표는 생성 단계 대책이 있어야 의미가 있음"
  ]
}
```

> **«주의» 필드를 결과 파일에 넣는 이유** — 나중에 이 숫자를 보는 사람이
> 전제를 모른 채 인용하는 것을 막습니다.

## 8. 실제 도입 시 평가 세트 재구성

```
   ⚠️ 이 평가 세트는 «합성 데이터»에서 만들어졌습니다.
      실제 문서로 옮길 때는 반드시 다시 만들어야 합니다.

   방법
     ① 기존 문의 로그에서 «실제 질의» 300~500건 추출
     ② 유형별로 분류 (A~G)
     ③ 담당자가 정답 문서를 라벨링
     ④ 함정 유형(버전 충돌·권한)은 «의도적으로» 추가
     ⑤ 분기마다 갱신 (제도 개정 반영)
```

> 합성 질의는 사용자가 실제로 묻는 방식과 다릅니다.
> 예: 실제 사용자는 "연차 며칠?"처럼 훨씬 짧게 묻습니다.
