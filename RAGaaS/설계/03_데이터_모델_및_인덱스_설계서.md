# 03. 데이터 모델 · 인덱스 설계서

> **목적** — [분석/02](../분석/02_도메인_지식체계_분석.md) 의 5축 택소노미를 **Azure AI Search 인덱스 스키마**로 확정합니다.

## 1. 필드 속성의 의미 — 잘못 켜면 생기는 일

| 속성 | 켜면 | 켜지 않으면 | 비용 |
| --- | --- | --- | --- |
| `searchable` | BM25 대상. 분석기로 토큰화 | 전문 검색에 걸리지 않음 | 역색인 저장 |
| `filterable` | `$filter` 사용 가능. **정확 일치** | 필터 불가 | 필터 인덱스 |
| `facetable` | 집계(개수) 가능 | 팩싯 불가 | 추가 인덱스 |
| `sortable` | `$orderby` 가능 | 정렬 불가 | 정렬 인덱스 |
| `retrievable` | 응답에 포함 | 응답에서 제외 | 응답 크기 |

```
   ❌ 전부 켜기
      · 인덱스 크기가 불필요하게 커진다
      · 색인 시간이 늘어난다
      · 벡터를 retrievable 로 두면 응답이 수 MB 가 된다

   ❌ searchable 과 filterable 을 혼동
      searchable  "인사" 로 검색하면 «인사팀», «인사이동» 도 걸린다 (분석됨)
      filterable  "인사" 는 정확히 «인사» 인 것만 (분석 안 됨)
      → 분류 필터에 searchable 을 쓰면 의도치 않은 것이 걸린다
```

## 2. 인덱스 스키마 — `hr-ga-chunks`

### 2.1 키 · 부모 참조

| 필드 | 타입 | key | search | filter | facet | sort | retrieve | 설계 의도 |
| --- | --- | :---: | :---: | :---: | :---: | :---: | :---: | --- |
| `chunk_id` | String | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ | 청크 고유 ID |
| `parent_id` | String | | ❌ | ✅ | ❌ | ❌ | ✅ | **원문으로 되돌아가는 열쇠** |
| `chunk_index` | Int32 | | ❌ | ✅ | ❌ | ✅ | ✅ | 문서 내 순번 |

> **`parent_id` 가 왜 중요한가**
> ① 인덱스 프로젝션이 부모‑자식을 연결한다
> ② 평가에서 «문서 단위»로 접을 때 쓴다 (같은 문서 청크 3개 = 정답 1개)
> ③ 답변에서 «원문 보기» 링크를 만든다

### 2.2 본문

| 필드 | 타입 | search | filter | retrieve | analyzer |
| --- | --- | :---: | :---: | :---: | --- |
| `title` | String | ✅ | ❌ | ✅ | **`ko.microsoft`** |
| `content` | String | ✅ | ❌ | ✅ | **`ko.microsoft`** |

#### ★ 한국어 분석기를 반드시 지정해야 하는 이유

```
   기본 분석기(standard) 사용 시
     "연차휴가를 신청하려면"  →  [연차휴가를, 신청하려면]
     "연차휴가는 며칠"        →  [연차휴가는, 며칠]
     → «연차휴가를» 과 «연차휴가는» 이 서로 다른 토큰
     → 조사 하나 다르면 BM25 가 매칭하지 못한다

   ko.microsoft (형태소 분석)
     "연차휴가를 신청하려면"  →  [연차, 휴가, 신청]
     "연차휴가는 며칠"        →  [연차, 휴가, 며칠]
     → 어간이 일치한다
```

| 분석기 | 방식 | 비고 |
| --- | --- | --- |
| **`ko.microsoft`** | Microsoft 형태소 분석 | 이 프로젝트 채택 |
| `ko.lucene` | Lucene 한국어 분석 | 대안. 직접 비교 권장 |
| `standard` | 공백·구두점 분리 | ❌ 한국어에 부적합 |

> ⚠️ **두 분석기를 직접 비교하지 않았습니다.**
> 코퍼스에 따라 결과가 다르므로, 실제 도입 시 평가 세트로 A/B 측정을 권합니다.

### 2.3 벡터

| 필드 | 타입 | search | retrieve | dimensions | profile |
| --- | --- | :---: | :---: | ---: | --- |
| `content_vector` | Collection(Single) | ✅ | **❌** | 1536 | `hnsw-profile` |

#### ★ `retrievable: false` 인 이유

```
   1536개 float × 4바이트 = 6,144 바이트/청크
   상위 50건 반환 시 = 307 KB  ← 순수 벡터만

   클라이언트는 벡터를 쓰지 않는다. 점수만 필요하다.
   → 응답에서 빼면 대역폭과 파싱 비용이 사라진다
```

### 2.4 분류 (필터 · 팩싯)

| 필드 | 타입 | search | filter | facet | 용도 |
| --- | --- | :---: | :---: | :---: | --- |
| `category` | String | ❌ | ✅ | ✅ | 인사/총무 |
| `subcategory` | String | ❌ | ✅ | ✅ | 24개 중분류 |
| `topic` | String | **✅** | ✅ | ✅ | 165개 세부주제 |
| `doc_type` | String | ❌ | ✅ | ✅ | **권위 가중의 기준** |
| `doc_group` | String | ❌ | ✅ | ✅ | 문서군 (인사규정 등) |

> `topic` 만 `searchable` 인 이유 — 사용자가 "연차휴가"라고 물으면 주제명 자체가 매칭 신호가 됩니다.
> 반면 `category`("인사")는 너무 일반적이라 검색어로 쓰면 노이즈가 됩니다.

### 2.5 수명 주기 — 최신성의 근거

| 필드 | 타입 | filter | sort | 용도 |
| --- | --- | :---: | :---: | --- |
| `status` | String | ✅ | ❌ | **현행/개정예정/폐지** — 가장 중요한 필터 |
| `version` | String | ✅ | ❌ | 세대 구분 |
| `effective_date` | DateTimeOffset | ✅ | ✅ | 시행일 정렬 |
| `expiry_date` | DateTimeOffset | ✅ | ✅ | 공지 만료 |
| `updated_at` | DateTimeOffset | ✅ | ✅ | 최종 갱신 |

**대표 필터**

```odata
// 현행 문서만
status eq '현행'

// 유효한 공지만 (만료일이 없거나 아직 안 지난 것)
status eq '현행' and (expiry_date eq null or expiry_date ge 2026-08-29T00:00:00Z)

// 2026년 이후 시행된 규정
doc_type eq '규정' and effective_date ge 2026-01-01T00:00:00Z
```

### 2.6 접근 제어 — ★ 보안의 실체

| 필드 | 타입 | filter | facet | 용도 |
| --- | --- | :---: | :---: | --- |
| `security_level` | String | ✅ | ✅ | 공개/사내/제한 |
| `audience` | Collection(String) | ✅ | ✅ | 대상 (전직원·인사담당자 …) |
| `owner_dept` | String | ✅ | ✅ | 소관 부서 |

```odata
// 일반 직원 (사내 등급까지)
security_level ne '제한'

// 공개 문서만 (외부 공유 시)
security_level eq '공개'

// 인사담당자 (전체 + 대상 확인)
audience/any(a: a eq '전직원' or a eq '인사담당자')
```

> ★ **이 필터는 «코드»가 조립합니다. 사용자 입력이 닿지 않습니다.**
> 필터 문자열을 사용자 질의로 조립하면 SQL 주입과 같은 구조가 됩니다.

## 3. 벡터 검색 구성

```json
"vectorSearch": {
  "algorithms": [{
    "name": "hnsw-config",
    "kind": "hnsw",
    "hnswParameters": { "m": 4, "efConstruction": 400, "efSearch": 500, "metric": "cosine" }
  }],
  "profiles": [{
    "name": "hnsw-profile",
    "algorithm": "hnsw-config",
    "vectorizer": "openai-vectorizer"
  }],
  "vectorizers": [{ "name": "openai-vectorizer", "kind": "azureOpenAI", ... }],
  "compressions": [{
    "name": "scalar-quantization",
    "kind": "scalarQuantization",
    "rerankWithOriginalVectors": true,
    "defaultOversampling": 4
  }]
}
```

### 3.1 HNSW 파라미터

| 파라미터 | 값 | 크면 | 작으면 |
| --- | ---: | --- | --- |
| `m` | 4 | 재현율↑ 메모리↑ | 재현율↓ 메모리↓ |
| `efConstruction` | 400 | 그래프 품질↑ 색인 시간↑ | 품질↓ 색인 빠름 |
| `efSearch` | 500 | 재현율↑ 검색 지연↑ | 재현율↓ 빠름 |
| `metric` | cosine | — | — |

> 12,863 청크 규모에서는 기본값으로 충분합니다.
> ⚠️ **파라미터를 «감»으로 올리지 마세요.** 평가 세트로 재현율 변화를 확인한 뒤 조정합니다.

### 3.2 ★ 벡터라이저 — 없으면 쿼리 시 벡터화가 안 된다

```
   벡터라이저 없음
     클라이언트가 직접 Azure OpenAI 를 호출해 쿼리 벡터를 만들고
     그 배열을 검색 요청에 담아 보내야 한다
     → 클라이언트가 임베딩 모델·차원을 알아야 한다
     → 모델을 바꾸면 클라이언트도 바꿔야 한다
     → 플레이그라운드에서 «텍스트로» 검색할 수 없다

   벡터라이저 있음
     검색 요청에 텍스트만 넣으면 Search 가 알아서 벡터화한다
     → 클라이언트는 모델을 모른다
     → 플레이그라운드 연결이 가능해진다  ★ CON-04 충족의 전제
```

> 🔑 **색인에 쓴 모델과 벡터라이저의 모델이 반드시 같아야 합니다.**
> 다르면 «다른 공간의 벡터»를 비교하게 되어 검색 결과가 무의미해집니다.

### 3.3 스칼라 양자화

```
   float32 (4바이트) → int8 (1바이트)   저장 75 % 절감

   품질 손실 보상
     rerankWithOriginalVectors: true   최종 순위는 원본 벡터로 다시 계산
     defaultOversampling: 4            후보를 4배 뽑아 손실을 흡수
```

| 환경 | 압축 | 이유 |
| --- | :---: | --- |
| dev | ❌ | 데이터가 작아 이득이 없다 |
| stg·prd | ✅ | 저장 비용 절감 |

## 4. 시맨틱 구성 (L2 랭커)

```json
"semantic": {
  "defaultConfiguration": "semantic-config",
  "configurations": [{
    "name": "semantic-config",
    "prioritizedFields": {
      "titleField": { "fieldName": "title" },
      "prioritizedContentFields": [{ "fieldName": "content" }],
      "prioritizedKeywordsFields": [{ "fieldName": "topic" }, { "fieldName": "keywords" }]
    }
  }]
}
```

> ★ **에이전트 검색은 이 구성을 «내부적으로» 사용합니다.**
> 시맨틱 구성이 없으면 지식 베이스가 동작하지 않습니다.
> 하위 쿼리마다 의미 재순위를 거치는 것이 에이전트 파이프라인의 핵심입니다.

## 5. BM25 유사도 파라미터

```json
"similarity": {
  "@odata.type": "#Microsoft.Azure.Search.BM25Similarity",
  "k1": 1.2,
  "b": 0.75
}
```

| 파라미터 | 값 | 의미 | 조정 방향 |
| --- | ---: | --- | --- |
| `k1` | 1.2 | 용어 빈도 포화점 | 크면 반복 등장의 가치가 오래 유지 |
| `b` | 0.75 | 문서 길이 정규화 | 1이면 완전 정규화, 0이면 길이 무시 |

> 이 코퍼스는 길이 편차가 큽니다(73자 ~ 8,203자).
> `b=0.75` 는 «긴 문서가 단순히 길다는 이유로 유리해지는 것»을 막습니다.
> `b=0` 으로 두면 규정전문이 모든 질의에서 상위를 차지합니다.

## 6. 동의어 맵 (선택)

```
   "법카" → "법인카드"
   "육휴" → "육아휴직"
   "WFH" → "재택근무"
```

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **동의어 맵** | BM25 가 약어를 잡는다. 색인 재생성 불필요 | 수동 관리. 신조어를 못 따라간다 |
| **벡터 검색** | 학습된 의미로 자동 처리 | 코퍼스에 없는 약어는 못 잡을 수 있다 |

> **둘 다 쓰는 것이 맞습니다.** 동의어 맵은 «확실히 아는 것»을, 벡터는 «모르는 것»을 담당합니다.
> ⚠️ 이 프로젝트에서는 동의어 맵을 **구성에 포함하지 않았습니다.**
> [분석/02 §8](../분석/02_도메인_지식체계_분석.md) 의 사전을 Azure 동의어 맵으로 등록하는 것이 다음 단계입니다.

## 7. 인덱스 프로젝션 — 청크가 «독립 문서»가 되게 한다

```json
"indexProjections": {
  "selectors": [{
    "targetIndexName": "hr-ga-chunks",
    "parentKeyFieldName": "parent_id",
    "sourceContext": "/document/pages/*",
    "mappings": [ ... 메타데이터 전부 복사 ... ]
  }],
  "parameters": { "projectionMode": "skipIndexingParentDocuments" }
}
```

### 7.1 ★ 메타데이터를 청크마다 «복사»하는 이유

```
   검색은 «청크 단위»로 이루어진다.
   청크가 자기 category·status·security_level 을 모르면 필터할 수 없다.

   ❌ 부모 문서에만 메타데이터
      → 청크를 찾은 뒤 부모를 조회해 필터해야 한다 (2단계)
      → 보안 필터가 «검색 후»가 되어 이미 노출된 뒤다

   ✅ 청크마다 복사
      → 검색 단계에서 바로 필터된다
      → 저장 중복이 늘지만, 메타데이터는 작다 (벡터에 비해 무시 가능)
```

## 8. 스키마 진화 — 필드를 추가·변경할 때

| 변경 | 재색인 필요? | 방법 |
| --- | :---: | --- |
| 필드 추가 (신규) | ❌ | 인덱스 업데이트 후 새 문서부터 채워짐 |
| 필드 추가 (기존 문서에도) | ✅ | 전체 재색인 |
| `filterable` 켜기 | ✅ | **필드 속성 변경은 재생성 필요** |
| `analyzer` 변경 | ✅ | 역색인을 다시 만들어야 함 |
| 벡터 차원 변경 | ✅ | 전부 다시 임베딩 (비용 발생) |
| 동의어 맵 추가·수정 | ❌ | **검색 시 적용** — 재색인 불필요 |

> ⚠️ **필드 속성 변경은 인덱스 재생성**입니다. 처음에 신중히 정해야 합니다.
> 특히 `analyzer` 와 벡터 `dimensions` 는 바꾸면 전체 재색인 + 재임베딩 비용이 듭니다.
