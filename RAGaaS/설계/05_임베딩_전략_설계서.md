## 1. 모델 선정

| 모델 | 기본 차원 | 축소 | 최대 입력 | 판정 |
| --- | ---: | :---: | ---: | :---: |
| **text-embedding-3-large** | 3072 | ✅ MRL | 8,191 | ✅ **채택** |
| text-embedding-3-small | 1536 | ✅ | 8,191 | 대안 (비용 우선 시) |
| text-embedding-ada-002 | 1536 | ❌ | 8,191 | ❌ 구세대 |

### 1.1 채택 근거

```
   ① 차원 축소(MRL) 지원
        3072 → 1536 으로 줄여도 품질 저하가 작다고 알려져 있다
        저장·연산 비용이 절반이 된다

   ② 입력 한계 여유
        우리 청크 최대 1,261 토큰 vs 한계 8,191 토큰 → 6배 여유
        장문 문서가 늘어도 당분간 문제없다

   ③ ada-002 대비 다국어 개선
```

### 1.2 ⚠️ 검증하지 않은 것

```
   «한국어에서 large 가 small 보다 나은가»를 직접 비교하지 않았다.

   · 공개 벤치마크는 대부분 영어 기준이다
   · 비용 차이가 있으므로, 한국어에서 그 차이가 정당화되는지 확인해야 한다
   · 평가 세트가 있으므로 A/B 측정이 가능하다

   → 다음 단계 실험
       python embed.py --backend azure --model text-embedding-3-large --dim 1536
       python eval_retrieval.py --k 5      # 기록
       python embed.py --backend azure --model text-embedding-3-small --dim 1536
       python eval_retrieval.py --k 5      # 기록 후 비교
```

## 2. 차원 선택 — 1536

| 차원 | 벡터당 바이트 | 12,863청크 총량 | 상대 비용 |
| ---: | ---: | ---: | ---: |
| 3072 (기본) | 12,288 | 약 158 MB | 100 % |
| **1536 (채택)** | 6,144 | **약 79 MB** | **50 %** |
| 1024 | 4,096 | 약 53 MB | 33 % |
| 256 | 1,024 | 약 13 MB | 8 % |

### 2.1 MRL(Matryoshka Representation Learning) 이란

```
   보통의 임베딩:  차원을 자르면 정보가 «무작위로» 사라진다
   MRL 학습 모델:  앞쪽 차원에 «중요한 정보»가 몰리도록 학습되어 있다
                   → 뒤를 잘라도 손실이 완만하다

   그래서 3072 → 1536 으로 «그냥 자르는» 것이 가능하다
   (API 의 dimensions 파라미터가 이것을 한다)
```

> ⚠️ **«품질 저하가 작다»는 것도 영어 기준입니다.**
> 한국어에서 1536 과 3072 의 차이를 측정하지 않았습니다.
> 비용이 문제가 되지 않는다면 3072 로 시작해 «줄여도 되는지» 확인하는 것이 안전합니다.

## 3. 비용 추정 — 인덱싱 «전»에 한다

### 3.1 왜 미리 추정하는가

```
   임베딩은 «한 번 실행하면 되돌릴 수 없는 비용»이다.
   1만 건을 다 임베딩한 뒤 "생각보다 비싸네" 는 늦다.

   → --estimate-only 로 규모를 먼저 확인한다
```

### 3.2 측정 결과

| 항목 | 값 |
| --- | ---: |
| 청크 수 | 12,863 |
| **총 토큰 (추정)** | **3,117,319** |
| 청크당 평균 | 242 토큰 |
| 청크당 중앙값 | 251 토큰 |
| 청크당 p99 | 461 토큰 |
| 청크당 최대 | 1,261 토큰 |
| 모델 한계 초과 | **0건** |

```
   초기 색인 비용 = 3,117,319 ÷ 1,000,000 × 단가(USD/1M)
```

> ⚠️ **단가를 이 문서에 적지 않았습니다.**
> 지역·계약·시점에 따라 다르며, 임의의 숫자를 적으면 예산이 틀어집니다.
> `MODELS` 에 `단가_USD_per_1M: None` 으로 두고,
> 실행 시 **«확인 필요»라고 출력**하도록 했습니다.

```
 ⚠️ 단가가 «확인 필요» 상태입니다.
    지역·계약·시점에 따라 다르므로 임의의 값을 넣지 않았습니다.
    Azure OpenAI 가격 페이지에서 확인한 뒤 MODELS 에 채우세요.
    계산식: 3,117,319 토큰 ÷ 1,000,000 × 단가(USD/1M)
```

### 3.3 토큰 추정 방법

| 방법 | 정확도 | 조건 |
| --- | --- | --- |
| **tiktoken** | 정확 | 패키지 설치 필요 |
| **문자 기반 추정** | ±20 % | 항상 가능 (채택) |

```python
KO_TOKENS_PER_CHAR = 1.5    # 한글 음절당 약 1.5 토큰
EN_CHARS_PER_TOKEN = 4.0    # 영문·숫자 4자당 약 1 토큰
```

> tiktoken 이 있으면 그것을 쓰고, 없으면 문자 기반으로 추정합니다.
> **±20 % 오차를 명시**하므로 «주문 전 대략의 청구서»로는 충분합니다.

## 4. 재색인 비용 — 이것이 더 중요하다

```
   초기 색인은 «한 번»이다. 재색인은 «계속»이다.

   전체 재색인 유발 요인
     · 임베딩 모델 변경        → 전부 다시
     · 차원 변경              → 전부 다시
     · 청킹 파라미터 변경      → 전부 다시
     · analyzer 변경          → BM25 만 (임베딩은 유지)

   증분 재색인 (정상 운영)
     · 문서 추가·수정         → 변경분만
     · 인덱서 고수위 감지로 자동
```

| 시나리오 | 임베딩 토큰 | 빈도 |
| --- | ---: | --- |
| 초기 색인 | 3,117,319 | 1회 |
| 문서 100건 수정 | 약 28,000 | 주 단위 |
| 청킹 파라미터 변경 | 3,117,319 | **실험 때마다** ⚠️ |
| 모델 변경 | 3,117,319 | 드묾 |

> ⚠️ **청킹 A/B 실험이 매번 전체 재임베딩을 유발합니다.**
> 그래서 이 프로젝트는 **로컬 LSA 임베딩**으로 파이프라인을 먼저 검증했습니다.
> Azure 호출 없이 «배관이 이어졌는지»를 확인한 뒤, 확정된 파라미터로 한 번만 임베딩하는 것이 경제적입니다.

## 5. 두 개의 백엔드

### 5.1 목적이 다르다

| 백엔드 | 목적 | 비용 | 의미 품질 |
| --- | --- | --- | --- |
| **azure** | 운영 | 과금 | 실제 의미 벡터 |
| **local-lsa** | 오프라인 검증 | 0 | **제한적** |

### 5.2 local-lsa 는 무엇인가

```
   TF-IDF → 무작위 투영 기반 SVD → 잠재 의미 벡터 (numpy 만으로 구현)

   할 수 있는 것
     · 파이프라인의 «배관» 검증 (청크 → 벡터 → 검색 → 융합)
     · RRF 가 실제로 어떻게 동작하는지 눈으로 확인
     · 전략 간 «상대 비교»

   할 수 없는 것
     · «법카 ↔ 법인카드» 같은 외부 지식 기반 유사도
       LSA 는 이 코퍼스 안의 단어 공기(共起)만 본다
     · 절대 품질 판정
```

> ⚠️ **local-lsa 를 «임베딩 모델의 대용»으로 오해하면 안 됩니다.**
> [분석/03 §3 E](../분석/03_질의_유형_분석.md) 에서 동의어 유형 Recall 이 0.500 인 것은
> **LSA 의 한계**이지 시스템의 한계가 아닐 가능성이 큽니다.
> Azure 임베딩으로 재측정해야 합니다.

### 5.3 쿼리와 문서를 «같은 공간»에 두기

```python
def embed_query_local(text, vocab, idf, components):
    """쿼리를 문서와 «같은 공간»으로 투영한다.

    ⚠️ 문서와 다른 방식으로 벡터를 만들면 유사도가 무의미해진다.
       토큰화·IDF·성분을 그대로 재사용해야 한다.
    """
```

> 🔑 **이것이 벡터 검색의 가장 흔한 버그입니다.**
> 색인 때와 검색 때 다른 모델·다른 전처리를 쓰면, 벡터가 «다른 공간»에 있어 유사도가 무작위가 됩니다.
> Azure 에서는 **벡터라이저가 색인 스킬과 같은 모델을 가리키도록** 구성해 이것을 방지합니다.

## 6. Azure 통합 벡터화 구성

### 6.1 색인 시 — AzureOpenAIEmbeddingSkill

```json
{
  "@odata.type": "#Microsoft.Skills.Text.AzureOpenAIEmbeddingSkill",
  "context": "/document/pages/*",
  "resourceUri": "https://{리소스}.openai.azure.com",
  "deploymentId": "{배포명}",
  "modelName": "text-embedding-3-large",
  "dimensions": 1536,
  "inputs":  [{ "name": "text", "source": "/document/pages/*" }],
  "outputs": [{ "name": "embedding", "targetName": "vector" }]
}
```

> ⚠️ `apiKey` 가 **없습니다.** 검색 서비스의 관리 ID 로 인증합니다.
> 검색 서비스에 **Cognitive Services OpenAI User** 역할이 부여되어 있어야 합니다.

### 6.2 검색 시 — 벡터라이저

```json
{
  "name": "openai-vectorizer",
  "kind": "azureOpenAI",
  "azureOpenAIParameters": {
    "resourceUri": "https://{리소스}.openai.azure.com",
    "deploymentId": "{배포명}",
    "modelName": "text-embedding-3-large"
  }
}
```

> **두 곳의 `modelName` 과 `dimensions` 가 반드시 같아야 합니다.**

## 7. 속도 제한 대응

```
   Azure OpenAI 는 «분당 토큰(TPM)» 제한이 있다.
   1만 청크를 한꺼번에 보내면 429 가 쏟아진다.

   대응
     ① 배치 크기      64건씩 (embed.py)
     ② 인덱서 주기    PT5M — 제한에 걸린 호출을 다음 실행에서 재시도
     ③ 내장 재시도    AI Search 가 자체 재시도 정책을 갖는다
     ④ 워크로드 분리  색인용·질의용 배포를 나누면 서로 방해하지 않는다
```

> ⚠️ **④가 실무에서 중요합니다.**
> 대량 색인 중에 사용자 질의가 속도 제한에 걸려 «검색이 안 되는» 사고가 흔합니다.
> 배포를 나누거나, 색인을 업무 시간 외로 돌려야 합니다.
