## 1. 청킹이 결정하는 것

```
   청크 = 검색 단위 = LLM 에 들어가는 근거 단위

   너무 크면
     · 관련 없는 내용이 섞여 벡터가 «평균화»된다 → 유사도가 흐려진다
     · LLM 컨텍스트를 낭비한다 → 비용↑, 지연↑
     · 답과 무관한 문장이 환각의 재료가 된다

   너무 작으면
     · 답에 필요한 맥락이 잘려 나간다
     · "제3항의 경우" 같은 참조가 끊긴다
     · 청크 수가 늘어 임베딩 비용과 인덱스 크기가 커진다
```

> 🔑 **«한 청크에 하나의 답»** 이 기준입니다.

## 3. 핵심 결정 — 문서 «유형별»로 다르게 자른다

### 3.1 왜 고정 크기가 틀렸는가

```
   모든 문서를 800자로 자른다면?

   FAQ (140자)        → 안 잘린다. 문제없음
   규정 조문 (200자)   → 안 잘린다. 문제없음
   안내서 (473자)      → 안 잘린다. 문제없음
   매뉴얼 (2,600자)    → 3~4조각. ★ 절 경계를 무시하고 잘린다
   규정전문 (8,000자)  → 10조각. ★ 조문 중간이 잘린다

   문제는 «잘리는 위치»다.
     "제12조(연차유급휴가)
      ① 연차휴가는 …
      ② 제1항에 따른 신청은 …"
                    ↑ 여기서 잘리면 «제1항»이 무엇인지 알 수 없는 청크가 생긴다
```

### 3.2 채택한 전략

| 문서 유형 | 전략 | 근거 |
| --- | --- | --- |
| FAQ · 문의이력 · 공지 · 서식안내 · 규정 | **자르지 않음 (atomic)** | 이미 하나의 완결된 의미 단위 |
| 안내서 · 지침 | 크기 이하 → 자르지 않음 | 평균 473자 / 364자 |
| **매뉴얼** | **절 경계 우선 → 크기 초과 시 재분할** | 7절 구성이 명확 |
| **규정전문** | **조·장 경계 우선 → 재분할** | 조문이 법적 단위 |

```python
ATOMIC_DOC_TYPES = {"FAQ", "문의이력", "공지", "서식안내", "규정"}
```

### 3.3 절 경계 인식 패턴

```python
SECTION_PATTERNS = [
    r"^\s*\d+\.\s+\S.*$",          # "1. 제도 개요"
    r"^\s*■\s*\S.*$",               # "■ 목적"
    r"^\s*제\d+장\s+\S.*$",         # "제2장 휴가"
    r"^\s*제\d+조\([^)]+\)\s*$",    # "제12조(연차유급휴가)"
    r"^\s*부칙\s*$",
]
```

경계가 2개 이상 있으면 그것으로 나누고, 없으면 빈 줄(문단)로 나눕니다.

## 4. 파라미터 — 각각의 근거

| 파라미터 | 값 | 근거 |
| --- | ---: | --- |
| **목표 크기** | **800자** | 한국어 800자 ≈ 500~600 토큰. 임베딩 한계(8,191)의 7 %. 답변 1건에 5청크 넣어도 3,000 토큰 |
| **최대 크기** | **1,200자** | 경계를 지키려다 목표를 넘길 때의 상한 |
| **중첩** | **120자** | 한국어 문장 평균 40~60자 → 2~3문장이 겹친다 |
| **최소 크기** | **120자** | 이보다 짧은 파편은 앞 청크에 흡수. 파편은 검색 노이즈 |

### 4.1 «목표 800자»를 임베딩 한계까지 키우지 않은 이유

```
   text-embedding-3-large 입력 한계 = 8,191 토큰 ≈ 13,000자

   한계까지 채우면?
     · 한 벡터에 여러 주제가 섞인다
     · 코사인 유사도가 «평평»해진다 — 모든 질의와 어중간하게 가까워진다
     · LLM 에 넣을 때 관련 없는 문장이 대부분

   → 검색 «정밀도»를 위해 훨씬 작게 잡는다.
     임베딩 한계는 «넘지 말아야 할 선»이지 «목표»가 아니다.
```

### 4.2 중첩의 비용

```
   중첩 120자 = 청크당 약 15 % 중복

   비용    임베딩 토큰 +15 %, 인덱스 크기 +15 %
   이득    문단 경계에서 잘린 문장이 양쪽에 남아 재현율이 오른다

   중첩 0  → 경계에 걸친 답을 놓칠 수 있다
   중첩 400 → 비용 +50 %. 이득은 체감이 작다
```

> ⚠️ **중첩의 최적값을 측정하지 않았습니다.** 120자는 «문장 2~3개»라는 근거로 정한 값입니다.
> 평가 세트로 0 / 120 / 240 을 비교하는 것이 다음 단계입니다.

## 5. 발견한 함정 두 가지 — 실패 기록

### 5.1 함정 1 — 병합이 상한을 넘겼다

```python
# ❌ 처음 구현
for p in pieces:
    if merged and len(p) < MIN_CHARS:
        merged[-1] = merged[-1] + "\n" + p     # 파편을 앞에 붙인다
```

**결과: 상한 1,200자를 넘는 청크가 7건 발생.** 파편을 없애려다 상한을 깼습니다.

```python
# ✅ 수정
if (merged and len(p) < MIN_CHARS
        and len(merged[-1]) + len(p) + 1 <= maximum):   # ← 상한 확인
```

> 🔑 «파편 제거»가 «상한 위반»을 만들면 얻는 것보다 잃는 것이 큽니다.

### 5.2 함정 2 — 제목 머리말이 예산에 없었다

각 청크에는 **문서 제목을 머리말로** 붙입니다.

```
   [연차휴가 운영기준 (현행)]
   [현행] 연차휴가 운영기준 v2.0 …
   └────── 이 부분이 추가된다 (약 15~30자)
```

처음에는 **본문만** 기준으로 자르고 «그 뒤에» 머리말을 붙였습니다.
→ 최종 청크가 1,211자로 상한 초과.

```python
# ✅ 수정 — 실제 임베딩 대상은 «머리말 + 본문»이다
prefix_len = len(f"[{title}]\n")
budget_target = max(target - prefix_len, MIN_CHARS)
budget_max = max(maximum - prefix_len, MIN_CHARS * 2)
```

> 🔑 **«상한을 지킨다»는 말이 참이 되려면, 실제로 임베딩되는 것을 기준으로 예산을 잡아야 합니다.**

### 5.3 제목 머리말을 붙이는 이유

```
   ❌ 머리말 없음
      "① 연차휴가는 팀장의 승인을 받아 시행한다."
      → 이것이 무슨 문서의 어느 조항인지 알 수 없다
      → 임베딩도 «맥락 없는 문장»의 벡터가 된다
      → LLM 이 인용할 때 출처를 말할 수 없다

   ✅ 머리말 있음
      "[인사규정 제12조(연차휴가)]
       ① 연차휴가는 팀장의 승인을 받아 시행한다."
```

## 7. Azure SplitSkill 과의 대응

| 항목 | 로컬 청커 | Azure SplitSkill |
| --- | --- | --- |
| 단위 | 문자 | **문자** (`maximumPageLength`) 또는 토큰 |
| 최대 | 1,200 | `maximumPageLength: 1200` |
| 중첩 | 120 | `pageOverlapLength: 120` |
| 언어 | — | `defaultLanguageCode: ko` |
| **유형별 분기** | ✅ | **❌ 불가** |
| 절 경계 인식 | ✅ | ❌ (문장 단위까지만) |

```json
{
  "@odata.type": "#Microsoft.Skills.Text.SplitSkill",
  "textSplitMode": "pages",
  "maximumPageLength": 1200,
  "pageOverlapLength": 120,
  "defaultLanguageCode": "ko"
}
```

> 🔑 **단위가 «문자»로 같습니다.** 그래서 로컬 실험 결과를 그대로 Azure 에 옮길 수 있습니다.
> (토큰 단위 옵션도 있지만, 로컬에서 토큰을 정확히 세려면 tiktoken 이 필요합니다.)

### 7.1 유형별 분기를 Azure 에서 하려면

| 방법 | 구성 |
| --- | --- |
| **(가) 유형별 인덱서 분리** | Blob 컨테이너를 유형별 폴더로 나누고, 폴더마다 다른 SplitSkill 파라미터 |
| **(나) 로컬 청킹 후 푸시** | 청킹 결과를 그대로 인덱스에 업로드 (이 프로젝트 기본) |

## 8. 평가 — 청킹이 검색에 미친 영향

⚠️ **청크 크기를 바꿔 가며 A/B 측정하지 않았습니다.**

현재 파라미터(800/1200/120)로만 평가했고, 그 결과가 [테스트/](../테스트/)에 있습니다.
«800자가 최적»이라고 말할 근거는 아직 없습니다.

**다음 단계로 해야 할 실험**

```bash
# 청크 크기별 비교
python chunker.py --target 500 --max 800  --overlap 80
python embed.py && python eval_retrieval.py --k 5   # → 기록

python chunker.py --target 800 --max 1200 --overlap 120   # 현재
python embed.py && python eval_retrieval.py --k 5   # → 기록

python chunker.py --target 1200 --max 1800 --overlap 200
python embed.py && python eval_retrieval.py --k 5   # → 기록
```

> 유형별로 결과가 다를 것으로 예상됩니다.
> 특히 **다중 홉**은 청크가 작을수록 조각을 각각 찾기 쉬워질 수 있고,
> **사실 조회**는 청크가 클수록 맥락이 살아 유리할 수 있습니다.
