## 1. 하이브리드로 부족한 지점

```
   질문: "3년차 개발직이 육아휴직을 쓰면 급여와 평가는 어떻게 되나요?"

   답에 필요한 문서 3개 — 서로 다른 중분류에 흩어져 있다
     ① 육아휴직 급여 처리     (인사>휴직)
     ② 휴직자 인사평가 처리   (인사>평가)   ← 다른 중분류
     ③ 육아휴직 신청 자격     (인사>휴직)

   하이브리드는 질문 «전체»를 하나의 벡터로 만든다
     → «급여»와 «평가»와 «자격»의 평균 지점
     → 어느 문서와도 특별히 가깝지 않다
     → 상위 결과가 애매해진다
```

**실제 실행 결과 (수동 비교)**

```
   단일 하이브리드 질의 상위 5
     1. 육아휴직 한도가 어떻게 되나요?              (FAQ)
     2. 신입사원인데 육아휴직 한도가…               (FAQ)
     3. 퇴사 예정인데 육아휴직 관련 규정이…          (FAQ)
     4. 입사 6개월차인데 육아휴직 관련 규정이…       (FAQ)
     5. 휴직 중인데 급여지급일 한도가…              (FAQ)
     → 필요 문서 3개 중 0개

   에이전트 검색 (2개 하위 쿼리로 분해)
     하위쿼리 1 "육아휴직 급여"     → 육아휴직 급여 처리      ★
     하위쿼리 2 "육아휴직 인사평가" → 휴직자 인사평가 처리    ★
     → 필요 문서 3개 중 2개

   공통 문서: 0건   ← 두 방식이 «완전히 다른» 것을 찾았다
```

## 2. Azure 에이전트 검색의 구조

### 2.1 구성 요소

| 구성 요소 | 서비스 | 역할 |
| --- | --- | --- |
| **지식 베이스** (Knowledge Base) | AI Search | 파이프라인 오케스트레이션 |
| **지식 원본** (Knowledge Source) | AI Search | «무엇을» 검색할지 정의 |
| 검색 인덱스 | AI Search | 실제 콘텐츠 (시맨틱 구성 필수) |
| 시맨틱 랭커 | AI Search | 하위 쿼리마다 L2 재순위 |
| LLM | Azure OpenAI | 쿼리 계획 · 답변 합성 |

> 📌 **용어가 바뀌었습니다.** 초기에는 «지식 에이전트(knowledge agent)»였으나
> 현재는 **«지식 베이스(knowledge base)»** 입니다. 오래된 예제 코드를 참고할 때 주의하세요.

### 2.2 동작 순서

```
   ① 워크플로 시작
        애플리케이션이 «검색 작업(retrieve)»으로 지식 베이스를 호출
        질의 + 대화 이력을 함께 전달

   ② 쿼리 계획
        LLM 이 복잡한 질문을 «집중된 하위 쿼리»로 분해
        ⚠️ retrievalReasoningEffort = minimal 이면 이 단계를 «건너뛴다»

   ③ 쿼리 실행
        하위 쿼리를 «병렬»로 실행
        각 하위 쿼리는 키워드·벡터·하이브리드 중 하나
        각각 시맨틱 재순위를 거친다
        참조(citation)를 추출·보존

   ④ 결과 합성
        모든 결과를 «통합 응답»으로 결합
        병합된 콘텐츠는 항상 반환
        원본 참조 · 활동 로그는 선택
```

### 2.3 검색 추론 노력 (retrievalReasoningEffort)

| 수준 | LLM 계획 | 반복 | 비용 | 적합 |
| --- | :---: | :---: | --- | --- |
| `minimal` | ❌ 생략 | ❌ | 최소 | 단순 사실 조회 |
| `low` (기본) | ✅ | ❌ | 중간 | 대부분의 질의 |
| `medium` | ✅ | ✅ | **높음** | 다중 홉 |

> ⚠️ **이 파라미터는 미리 보기(2026‑05‑01‑preview)입니다.**
> SLA 가 없고 운영 워크로드에 권장되지 않습니다. 도입 전 GA 여부를 확인하세요.

## 3. 지식 원본 설계

### 3.1 종류 선택 — `searchIndex`

| 종류 | 인덱싱/원격 | 이 프로젝트 |
| --- | --- | :---: |
| **검색 인덱스** | 인덱싱됨 | ✅ **채택** |
| Azure Blob | 인덱싱됨 (자동 생성) | ❌ |
| Azure SQL (미리 보기) | 인덱싱됨 | ❌ |
| 파일 (미리 보기) | 인덱싱됨 | ❌ |
| OneLake | 인덱싱됨 | ❌ |
| SharePoint (인덱싱/원격) | 둘 다 (미리 보기) | ⚠️ 실제 도입 시 |
| Fabric 데이터 에이전트 | 원격 (미리 보기) | ❌ |
| MCP 서버 | 원격 (미리 보기) | ❌ |
| 웹 (Bing) | 원격 | ❌ **사내 규정에 외부 웹은 위험** |

**`searchIndex` 를 고른 이유**

```
   Blob·SQL 종류를 쓰면 Azure 가 인덱서 파이프라인을 «자동 생성»한다.
   → 우리가 설계한 청킹·필드·분석기를 쓸 수 없다
   → status·security_level·doc_type 필터가 사라진다

   이미 설계한 인덱스가 있으므로 그것을 «감싸는» 것이 맞다.
```

### 3.2 ★ `description` 이 중요한 이유

```json
"description": "누리컴퍼니 인사·총무 지식 베이스. 인사(채용·평가·휴가·급여·퇴직)와
                총무(비품·출장·경비·계약·복리후생) 규정·지침·FAQ·문의이력·공지를 포함한다."
```

> 추론 노력이 `low`/`medium` 일 때 **LLM 이 이 설명을 읽고 «이 지식 원본을 쓸지» 판단**합니다.
> 설명이 부실하면 관련 질의에서도 이 원본을 건너뛸 수 있습니다.

### 3.3 `alwaysQuery`

```json
"knowledgeSources": [{ "name": "hr-ga-knowledge-source", "alwaysQuery": true }]
```

| 값 | 동작 | 언제 |
| --- | --- | --- |
| `true` | 추론 노력과 무관하게 **항상** 조회 | 지식 원본이 하나뿐일 때 |
| `false` | LLM 이 필요하다고 판단할 때만 | 원본이 여럿일 때 |

> ⚠️ 원본이 여러 개인데 전부 `true` 면 **팬아웃이 커져 토큰이 낭비**됩니다.

## 4. 검색 지침 (retrievalInstructions)

**LLM 에게 «어떻게 검색할지» 알려 줍니다. 프롬프트처럼 동작합니다.**

```
인사·총무 규정 질의에 답하기 위한 근거를 찾는다.
규칙:
1. status 가 '폐지'인 문서는 근거로 쓰지 않는다.
   개정 이력을 묻는 질문일 때만 예외로 참고한다.
2. 같은 주제에 여러 버전이 있으면 effective_date 가 가장 최근인 것을 우선한다.
3. 숫자(일수·금액·기한)를 묻는 질문은 '규정' 또는 '안내서' 유형을 우선한다.
   FAQ 와 문의이력은 요약이라 수치가 다를 수 있다.
4. 절차를 묻는 질문은 '지침' 또는 '서식안내' 유형을 우선한다.
5. 여러 조건이 걸린 질문(예: 직급 + 상황 + 제도)은 조건별로 하위 쿼리를 나눈다.
```

> 🔑 **3·4번이 [설계/06 §6](06_Hybrid_검색_설계서.md) 의 «권위 가중»을 지식 베이스에서 구현한 것입니다.**
> 다만 이것은 **LLM 에 대한 «지시»** 이므로 확률적입니다.
> 결정적 보장이 필요하면 클라이언트 후처리에서 다시 가중해야 합니다.

## 5. 로컬 시뮬레이션 — 비용 없이 검증

### 5.1 규칙 기반 쿼리 분해

Azure 는 LLM 이 분해하지만, 로컬 구현은 **규칙**으로 흉내 냅니다.

```python
_MULTI_ASPECT = [
    ("급여", "급여"), ("평가", "인사평가"), ("수당", "수당"),
    ("대체휴무", "대체휴무"), ("퇴직금", "퇴직금"), …
]

_CONDITION_PATTERNS = [
    (r"(\d+)\s*년차", "근속"),
    (r"(개발직|기획직|영업직|…)", "직군"),
    (r"(정규직|계약직|…)", "고용형태"),
]
```

```
   "3년차 개발직이 육아휴직을 쓰면 급여와 평가는 어떻게 되나요?"

   ① 조건 추출     {근속: 3, 직군: 개발직}     ← 필터 후보
   ② 측면 식별     [급여, 인사평가]
   ③ 주제어 추출   "육아휴직"
   ④ 하위 쿼리     "육아휴직 급여" / "육아휴직 인사평가"
```

> ⚠️ **규칙의 한계** — 표현이 예상 밖이면 분해하지 못합니다.
> Azure 의 LLM 분해는 훨씬 유연합니다.
> 로컬 구현의 목적은 «분해하면 왜 좋아지는지»를 비용 없이 보여 주는 것입니다.

### 5.2 결과 합성

하위 쿼리 결과를 **다시 RRF 로** 합칩니다.

```
   하위쿼리1 결과 → 순위
   하위쿼리2 결과 → 순위
        └──── RRF (k=60) ────┘
                 ↓
            통합 결과
```

## 6. ★ 에이전트 검색은 만능이 아니다 — 측정 결과

| 전략 | 전체 Recall@5 | 다중홉 Recall@5 | MRR |
| --- | ---: | ---: | ---: |
| boosted (하이브리드+권위) | **0.793** | 0.333 | **0.801** |
| agentic | 0.540 | 0.222 | 0.543 |
| **agentic+boost** | 0.713 | **0.556** | 0.707 |

### 6.1 읽어야 할 것

```
   ① 에이전트만 쓰면 «전체»가 나빠진다 (0.540 < 0.793)
        단일 주제 질문을 억지로 분해하면 결과가 흩어진다

   ② 에이전트+권위가 «다중 홉»에서 최고다 (0.556)
        분해가 필요한 질문에서는 확실한 이득

   ③ 분해와 권위 가중은 «다른 문제»를 푼다
        분해 — 여러 주제가 섞인 질문에서 각 주제의 근거를 찾는다
        가중 — 같은 주제 안에서 권위 있는 문서를 위로 올린다
        → 경쟁하지 않으므로 함께 쓸 수 있다
```

> 🔑 **결론: 단일 전략으로 통일하지 말고 «라우팅»한다.**

## 7. 질의 라우팅 설계

```
        사용자 질의
             │
             ▼
      ┌──────────────────┐
      │  복잡도 판별      │
      │  ① 여러 측면?     │  "급여«와» 평가"
      │  ② 조건 여럿?     │  "3년차 «AND» 개발직"
      │  ③ 접속 표현?     │  "~하고", "~와"
      └────┬─────────┬───┘
           │         │
      단순 │         │ 복잡
           ▼         ▼
      boosted    agentic+boost
      minimal    medium
```

| 라우팅 | Azure 대응 | 비용 | 적합 유형 |
| --- | --- | --- | --- |
| 단순 | `retrievalReasoningEffort: minimal` | 최소 | A · B · E |
| 보통 | `low` (기본) | 중간 | C · F |
| 복잡 | `medium` | 높음 | D |

### 7.1 ⚠️ 이 라우팅은 아직 검증되지 않았다

```
   측정하지 않은 것
     · 복잡도 판별의 «정확도»
     · 오판 시 손실 (단순을 복잡으로 → 비용 낭비 / 복잡을 단순으로 → 품질 저하)
     · 라우팅 오버헤드

   → «라우팅이 이득»이라고 말하려면 이것을 먼저 재야 한다
```

## 8. 비용 구조

### 8.1 두 곳에서 과금된다

```
   Azure AI Search    하위 쿼리 실행 + 시맨틱 재순위의 «검색 토큰»
                      무료 계층에 월별 토큰 할당량이 있다
   Azure OpenAI       쿼리 계획 + 답변 합성의 «입출력 토큰»
                      항상 종량제
```

### 8.2 비용을 좌우하는 것

| 요인 | 영향 | 통제 |
| --- | --- | --- |
| 하위 쿼리 수 | 선형 증가 | 분해 개수 제한 (max 4) |
| 지식 원본 수 | **팬아웃** | 하나로 통합 |
| 추론 노력 | `medium` 은 반복 | 라우팅 |
| 재순위 청크 수 | 하위 쿼리 × 청크 수 | `top` 제한 |

```
   예시 계산 구조 (Azure 문서의 방식)
     에이전트 검색 2,000회 × 하위 쿼리 3개 = 6,000 쿼리
     쿼리당 50청크 재순위 = 300,000 청크
     청크당 500토큰 = 1억 5천만 토큰
     → 검색 토큰 비용

     + 쿼리 계획: 2,000 × (입력 2,000 + 출력 350) 토큰
     → LLM 비용
```

> ⚠️ **단가를 이 문서에 적지 않았습니다.** 지역·시점에 따라 다릅니다.
> 위 «구조»에 실제 단가를 대입해 계산하세요.

### 8.3 비용 통제 수칙

```
   ① 활동 로그를 본다      실제 실행된 하위 쿼리를 확인해 낭비를 찾는다
   ② 지식 원본을 줄인다    팬아웃 감소
   ③ 추론 노력을 낮춘다    단순 질의는 minimal
   ④ 콘텐츠를 정리한다     큐레이팅된 요약·기준표가 있으면 적은 문서로 답이 나온다
```

> ④가 **가장 근본적인 통제**입니다.
> 이 프로젝트에서 «기준표» 문서를 별도로 둔 것이 그 예입니다 —
> 흩어진 FAQ 20건을 뒤지는 대신 기준표 1건으로 답이 나옵니다.

## 9. Azure 호출 코드

```python
class AzureAgenticSearch:
    def retrieve(self, messages, security_filter=None, reasoning_effort=None):
        url = f"{endpoint}/knowledgeBases/{kb}/retrieve?api-version=2026-04-01"
        body = {"messages": messages}
        if security_filter:
            # ★ 보안 강제는 여기서 한다.
            body["knowledgeSourceParams"] = [{
                "knowledgeSourceName": ks,
                "kind": "searchIndex",
                "filterAddOn": security_filter,      # security_level ne '제한'
            }]
        if reasoning_effort:
            body["retrievalReasoningEffort"] = reasoning_effort
        ...
```

> ⚠️ **인증은 관리 ID(`DefaultAzureCredential`)로만** 합니다. API 키를 쓰지 않습니다.
> ⚠️ 이 호출은 **실제로 과금**됩니다.

## 10. 결정

### ADR‑007 · 에이전트 검색을 «다중 홉 질의에만» 적용

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 (라우팅 미검증) |
| **맥락** | 에이전트만 쓰면 전체 성능이 하락한다 (0.540 < 0.793) |
| **결정** | 복잡도 판별로 라우팅하고, 복잡 질의에만 에이전트를 쓴다 |
| **근거** | §6 측정 결과 — 다중홉 0.556 vs 전체 0.713 |
| **결과** | ➕ 유형별 최적 · 비용 통제 ➖ 판별 로직 필요 · **오판 위험** |
| **⚠️ 미검증** | 복잡도 판별 정확도를 측정하지 않았다 |
| **되돌릴 조건** | 다중 홉 질의 비중이 1 % 미만이면 에이전트 경로 제거 |
