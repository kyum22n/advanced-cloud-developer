# 02. Azure 서비스 선정서

> **목적** — "Azure AI 서비스를 최대한 활용한다"는 요구를 **근거 있는 선택**으로 바꿉니다.
> "Azure 가 제공하니까"는 근거가 아닙니다. 각 서비스가 **어떤 요구사항을 충족하는지** 적습니다.

## 2. Azure AI Search — 왜 이것이 핵심인가

### 2.1 이 하나로 되는 일

| 기능 | 이것이 없다면 |
| --- | --- |
| BM25 키워드 검색 | Elasticsearch 등 별도 구축 |
| HNSW 벡터 검색 | 벡터 DB(Pinecone·Qdrant) 별도 구축 |
| **RRF 융합** | 두 결과를 직접 합치는 코드 작성·유지 |
| **시맨틱 랭커** | 교차 인코더 모델 직접 호스팅 |
| 통합 벡터화 | 청킹·임베딩 파이프라인 직접 구축 |
| **에이전트 검색** | 쿼리 분해·병렬·합성 오케스트레이션 직접 구현 |
| 필터·팩싯 | 벡터 DB 의 제한적 메타 필터로 감당 |

> 🔑 **«키워드 + 벡터 + 재순위 + 필터»를 한 서비스에서 하는 것**이 선택의 핵심입니다.
> 벡터 DB 를 따로 쓰면 하이브리드를 직접 구현해야 하고, 두 저장소의 동기화 문제가 생깁니다.

### 2.2 계층(SKU) 선택

| 계층 | 벡터 | 시맨틱 랭커 | 에이전트 검색 | 이 프로젝트 |
| --- | :---: | :---: | :---: | --- |
| 무료 | ✅ | 제한 | ⚠️ | 학습·실습용 |
| **기본** | ✅ | 무료 할당 | ✅ | **dev** |
| **표준 S1** | ✅ | ✅ | ✅ | **stg · prd** |
| 저장소 최적화 | ✅ | ✅ | ✅ | 문서 수백만 건 시 |

> ⚠️ **2019년 이전 생성된 서비스는 벡터를 지원하지 않습니다.**
> 기존 서비스를 재사용하려다 실패하는 흔한 사례입니다. 새로 만드는 것이 안전합니다.

### 2.3 에이전트 검색 — API 버전 주의

| API 버전 | 상태 | 포함 |
| --- | --- | --- |
| **2026‑04‑01** | **일반 공급(GA)** | 지식 베이스·지식 원본의 상당 부분 |
| 2026‑05‑01‑preview | 미리 보기 | `retrievalReasoningEffort` 등 |

```
   ⚠️ retrievalReasoningEffort(minimal/low/medium)는 미리 보기입니다.
      · SLA 가 없습니다
      · 운영 워크로드에 권장되지 않습니다
      · 운영 도입 전에 GA 여부를 다시 확인해야 합니다

   → 이 프로젝트는 GA API(2026-04-01)를 기본으로 하고,
     미리 보기 기능은 «있으면 쓰고 없어도 동작»하도록 구성했습니다.
```

## 3. Azure OpenAI — 모델 선택

### 3.1 임베딩 모델

| 모델 | 기본 차원 | 축소 가능 | 최대 입력 | 선택 |
| --- | ---: | :---: | ---: | :---: |
| **text-embedding-3-large** | 3072 | ✅ MRL | 8,191 | ✅ |
| text-embedding-3-small | 1536 | ✅ | 8,191 | 대안 |
| text-embedding-ada-002 | 1536 | ❌ | 8,191 | ❌ 구세대 |

**선택 근거**

```
   ① 차원 축소(MRL) 지원      3072 → 1536 으로 줄여 저장·연산 비용 절반
   ② 다국어 성능이 ada-002 대비 개선   (단, 한국어는 직접 비교 필요)
   ③ 입력 한계 8,191 토큰      우리 청크 최대 1,261 토큰 → 여유 6배
```

> ⚠️ **한국어 성능을 직접 비교하지 않았습니다.**
> 영어 벤치마크에서 large > small 이지만, 한국어에서 그 차이가 비용을 정당화하는지는
> **평가 세트로 A/B 측정해야** 합니다. 이 프로젝트에서는 하지 못했습니다.

### 3.2 채팅 모델

| 용도 | 요구 | 권장 |
| --- | --- | --- |
| **쿼리 계획** (에이전트) | 빠르고 저렴. 구조화 출력 | 소형·고속 모델 |
| **답변 생성** | 근거 준수·한국어 품질 | 중대형 모델 |

```
   ⚠️ 구체적 모델명을 이 문서에 고정하지 않았습니다.
      Azure OpenAI 의 모델 가용성은 지역·시점에 따라 다르고,
      새 모델이 빠르게 나옵니다.

   → 구성에서 «배포 이름»으로 참조하도록 했습니다.
      config/.env.example:  AZURE_OPENAI_CHAT_DEPLOYMENT=<채팅 배포명>
      모델 교체 시 코드 변경이 없습니다.
```

### 3.3 쿼리 계획과 답변 생성을 «다른 모델»로 두는 이유

| | 쿼리 계획 | 답변 생성 |
| --- | --- | --- |
| 출력 | 하위 쿼리 3~4개 (짧다) | 답변 문단 (길다) |
| 요구 능력 | 질문 분해 | 근거 준수·한국어 문장력 |
| 호출 빈도 | 복잡 질의만 | 모든 질의 |
| 지연 민감도 | **높음** (검색 앞단) | 중간 (스트리밍 가능) |

> 계획에 큰 모델을 쓰면 **검색이 시작되기 전에** 지연이 쌓입니다.
> 작고 빠른 모델로 충분한 작업입니다.

## 4. 데이터 원본 — Blob 선택 근거

| 후보 | 장점 | 단점 | 판정 |
| --- | --- | --- | --- |
| **Blob Storage** | 가장 단순. 인덱서 네이티브 지원 | 권한 동기화 없음 | ✅ 채택 |
| Azure SQL | 구조화 데이터에 적합 | 문서 저장에는 부적합 | ❌ |
| SharePoint (인덱싱) | 실제 사내 문서 위치 | 미리 보기. 권한 동기화 복잡 | ⚠️ 실제 도입 시 |
| OneLake | 분석 파이프라인 연계 | 이 프로젝트에 과함 | ❌ |
| 파일 직접 업로드 | 인덱서 불필요 | 증분 반영·자동화 부족 | ❌ |

> **실제 도입 시**에는 SharePoint 인덱싱 지식 원본이 유력합니다.
> 다만 미리 보기이고 **민감도 레이블·권한 동기화** 설정이 까다로우므로,
> 초기에는 «Blob 으로 내보내기 → 색인»이 안전합니다.

## 5. 통합 벡터화 vs 로컬 청킹 — 실제로 부딪힌 문제

### 5.1 통합 벡터화(SplitSkill)의 한계

```
   SplitSkill 은 «문서 유형»을 구분하지 못한다.
     maximumPageLength: 1200 으로 전부 자른다.

   그런데 우리 코퍼스는:
     FAQ (140자)       → 자르면 안 된다. 이미 완결된 질문-답이다
     규정 조문 (200자)  → 자르면 안 된다. «조»가 법적 단위다
     매뉴얼 (2,600자)   → 반드시 잘라야 한다
     규정전문 (8,000자) → 반드시 잘라야 한다

   1,200자 기준이면 앞의 둘은 어차피 안 잘리므로 «결과적으로» 맞다.
   하지만 «의도해서» 맞은 것이 아니라 «우연히» 맞은 것이다.
```

### 5.2 두 갈래

| 방식 | 장점 | 단점 | 이 프로젝트 |
| --- | --- | --- | --- |
| **(가) 통합 벡터화** | 파이프라인 자동화·유지보수 최소 | 유형별 분기 불가 | 구성 산출 |
| **(나) 로컬 청킹 후 푸시** | 유형별 전략 완전 제어 | 파이프라인 직접 관리 | **기본** |

**결정: (나)를 기본으로, (가) 구성도 함께 산출**

```
   근거
     · 유형별 청킹이 이 도메인의 핵심 설계 결정이다 (분석/02 §4)
     · 로컬 청킹으로 파라미터를 «실험»한 뒤 확정했다
     · 통합 벡터화 구성도 만들어 두어, 유형별 인덱서 분리로 전환할 수 있게 했다

   되돌릴 조건
     · 문서 유형이 하나로 수렴하면 (가)가 단순하고 낫다
     · 운영 인력이 파이프라인을 유지할 수 없으면 (가)로 전환
```

## 6. 채택하지 «않은» Azure 서비스

| 서비스 | 무엇인가 | 왜 안 쓰는가 | 재검토 조건 |
| --- | --- | --- | --- |
| **Document Intelligence** | PDF 표·레이아웃 추출 | 이 코퍼스는 텍스트(JSONL). PDF 가 없다 | 실제 사규 PDF 를 색인할 때 **필수** |
| **Azure AI Language** | PII 감지·핵심구 추출 | 가상 데이터라 PII 가 없다 | 실제 문서 이관 시 **필수** |
| **Azure Cosmos DB** | 벡터 저장 대안 | AI Search 하나로 충분. 두 저장소 동기화 부담 | 트랜잭션 데이터와 결합 필요 시 |
| **Azure Machine Learning** | 커스텀 임베딩 모델 | Azure OpenAI 로 충분 | 한국어 특화 모델이 필요하다고 «측정»되면 |
| **Semantic Kernel / LangChain** | 오케스트레이션 프레임워크 | 지식 베이스가 오케스트레이션을 대신한다 | 복잡한 도구 호출 체인이 필요하면 |
| **Azure Functions** | 커스텀 스킬 호스팅 | 커스텀 스킬을 쓰지 않는다 | 사내 시스템 조회(잔여 연차 등) 연동 시 |
| **Fabric Data Agent** | 원격 지식 원본 | 데이터 웨어하우스 연계가 없다 | 인사 데이터 마트와 결합 시 |

> 🔑 **Document Intelligence 와 AI Language 는 «지금 안 쓰지만 실제 도입 시 필수»** 입니다.
> 이 프로젝트가 가상 텍스트 데이터를 쓰기 때문에 빠진 것이지, 필요 없어서가 아닙니다.

## 7. Foundry 플레이그라운드 — 시연 경로

| 방법 | 절차 | 이 프로젝트 |
| --- | --- | --- |
| **기존 인덱스 연결** | 채팅 플레이그라운드 → 데이터 추가 → 기존 AI Search 인덱스 선택 | ✅ 권장 |
| 파일 업로드 | 로컬 파일 → 자동 인덱스 생성 | ❌ 우리 스키마를 못 쓴다 |
| Blob 연결 | Blob → 자동 인덱스 생성 | ❌ 동일 |

```
   ⚠️ «파일 업로드»나 «Blob 연결»을 쓰면 Foundry 가 «자동으로» 인덱스를 만듭니다.
      그러면 우리가 설계한 필드(status·security_level·doc_type)가 없어지고,
      필터·권위 가중을 쓸 수 없습니다.

   → 반드시 «기존 인덱스 선택»으로 연결해야 합니다.
```

상세 절차 → [`개발/playground/`](../개발/playground/)

> 📌 **명칭 변화** — Azure AI Studio 는 **Microsoft Foundry** 로 이름이 바뀌었습니다.
> 문서·포털에서 «Foundry (classic)» 과 새 포털이 함께 보일 수 있습니다.
> 이 프로젝트는 **채팅 플레이그라운드 + 기존 인덱스 연결** 경로를 기준으로 합니다.

## 8. ADR

### ADR‑004 · Azure AI Search 를 검색 기반으로 채택

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **맥락** | 키워드·벡터·재순위·필터·에이전트가 모두 필요하다 |
| **결정** | Azure AI Search 단일 서비스로 구성한다 |
| **근거** | §2.1 — 별도 구축 시 6개 구성 요소를 직접 만들고 동기화해야 한다 |
| **결과** | ➕ 통합 운영·하이브리드 내장 ➖ Azure 종속 · 계층별 비용 |
| **대안** | 벡터 DB + Elasticsearch — 하이브리드·동기화를 직접 구현해야 해 기각 |

### ADR‑005 · 로컬 청킹 우선, 통합 벡터화 병행

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **맥락** | SplitSkill 은 문서 유형별 분기를 표현할 수 없다 |
| **결정** | 로컬 청킹으로 유형별 전략을 적용하고, 통합 벡터화 구성도 산출한다 |
| **근거** | §5 — 유형별 청킹이 이 도메인의 핵심 설계 결정 |
| **결과** | ➕ 완전한 제어 ➖ 파이프라인 직접 관리 |
| **되돌릴 조건** | 문서 유형 단순화 또는 운영 인력 제약 |

### ADR‑006 · 미리 보기 기능 사용 제한

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **맥락** | `retrievalReasoningEffort` 등 일부 에이전트 기능이 미리 보기 |
| **결정** | GA API(2026‑04‑01)를 기본으로 하고, 미리 보기는 «있으면 쓰고 없어도 동작»하게 구성 |
| **근거** | 미리 보기는 SLA 가 없고 운영 워크로드에 권장되지 않는다 |
| **결과** | ➕ 안정성 ➖ 최신 기능 일부 미사용 |
| **되돌릴 조건** | 해당 기능 GA 전환 시 |
