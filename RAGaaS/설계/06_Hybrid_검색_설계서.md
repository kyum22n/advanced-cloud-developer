## 1. 왜 합쳐야 하는가 — 실패 지점이 다르다

| | BM25 (키워드) | 벡터 (의미) |
| --- | --- | --- |
| 강한 곳 | **정확한 용어 · 숫자 · 고유명사** | **동의어 · 구어체 · 표현 차이** |
| 약한 곳 | 표기가 다르면 못 찾는다 | **숫자를 구분 못 한다** |
| 예 | "연차유급휴가" ✅ / "쉬는 날" ❌ | "쉬는 날" ✅ / "15일 vs 25일" ❌ |

```
   "법카 정산 어떻게 해요?"
     BM25   «법카» 토큰이 문서에 없다 → ❌
     벡터   «법인카드 경비정산» 과 의미가 가깝다 → ✅

   "연차휴가 한도가 며칠인가요?"
     BM25   «한도», «일수» 정확 일치로 기준표를 찾는다 → ✅
     벡터   «15일»과 «25일»이 의미 공간에서 거의 같은 위치 → ❌
```

**측정 결과** (Recall@5, 평가 세트 38건)

| 유형 | keyword | vector | 차이 |
| --- | ---: | ---: | --- |
| B 숫자 정밀도 | **1.000** | 0.400 | 키워드 압승 |
| D 다중 홉 | 0.444 | **0.556** | 벡터 우세 |
| E 동의어·구어 | 0.667 | 0.500 | ⚠️ 예상과 다름 |

> ⚠️ **E 동의어에서 벡터가 더 낮습니다.** 예상과 반대입니다.
> 원인은 **로컬 LSA 임베딩의 한계**로 보입니다 — 코퍼스 안의 공기만 보므로 «법카 ↔ 법인카드»를 모릅니다.
> Azure 임베딩으로 재측정하면 달라질 가능성이 큽니다. **단정하지 않습니다.**

## 2. RRF — 상호 순위 융합

### 2.1 왜 «점수»가 아니라 «순위»를 쓰는가

```
   BM25 점수    상한 없음 (0 ~ ∞)
   코사인 유사도 -1 ~ 1

   → 점수를 그냥 더하면 BM25 가 항상 이긴다
   → 정규화하려 해도 분포가 질의마다 달라 기준이 없다

   RRF: 순위만 쓴다
     score(d) = Σ  1 / (k + rank_i(d))
                i
```

### 2.2 Azure 와 동일한 구현

```python
RRF_K = 60
#   Azure AI Search 가 쓰는 값.
#   ⚠️ 벡터 검색의 k(이웃 개수)와 «전혀 다른» 값이다. 이름만 같다.

def reciprocal_rank_fusion(result_sets, k=RRF_K, weights=None):
    fused = defaultdict(float)
    contrib = defaultdict(dict)
    for set_no, (results, w) in enumerate(zip(result_sets, weights)):
        for rank, (doc_idx, _score) in enumerate(results, start=1):
            fused[doc_idx] += w * (1.0 / (k + rank))
            contrib[doc_idx][set_no] = rank        # ★ 기여도를 남긴다
    ...
```

> **기여도를 함께 반환하는 이유** — «왜 이 문서가 위로 왔는가»를 설명할 수 있어야 튜닝이 가능합니다.

```
   실행 예
     1. [0.03226] 육아휴직 사용하면 불이익이 있나요?
        ← 쿼리1 2위, 쿼리2 2위        ← 양쪽에서 높아 1위
     2. [0.03178] 육아휴직 급여 처리
        ← 쿼리1 1위, 쿼리2 5위        ← 한쪽에서만 1위
```

### 2.3 k=60 의 의미

```
   k 가 작으면 (예: 1)    1위와 2위의 차이가 크다 → 상위 순위가 지배
   k 가 크면 (예: 1000)   순위 차이가 희석 → 여러 집합에 «등장하는 것»이 중요해진다

   k=60 은 «상위 순위 존중»과 «양쪽 등장 보상»의 절충점으로 알려져 있다
```

> ⚠️ Azure 에서는 **k 를 조정할 수 없습니다.** 고정값입니다.
> 조정 가능한 것은 **벡터 가중치**(`weight`)입니다.

## 3. 벡터 가중치

```
   기본값 1.0 — 키워드와 벡터를 동등하게 본다

   weight = 0.5   벡터의 기여를 절반으로 → 키워드 쪽이 강해진다
   weight = 2.0   벡터의 기여를 2배로   → 의미 검색이 강해진다
```

| 질의 유형 | 권장 가중치 | 근거 |
| --- | ---: | --- |
| 숫자·기준 조회 | **0.5** | 키워드가 결정적 (측정: keyword 1.000 vs hybrid 0.400) |
| 동의어·구어 | **1.5~2.0** | 벡터가 필요 |
| 일반 | 1.0 | 기본 |

> ⚠️ **질의 유형별 가중치 자동 조정을 구현하지 않았습니다.**
> 이것은 «질의 분류»가 먼저 필요하고, 그 정확도를 측정해야 합니다.
> 현재는 고정 1.0 을 씁니다.

## 4. ★ «하이브리드가 항상 낫다»는 거짓이다

```
   숫자 정밀도 유형 Recall@5

     keyword   1.000   ████████████████████
     hybrid    0.400   ████████
                       ↑ 하이브리드가 «더 나쁘다»
```

**왜 이런 일이 생기는가**

```
   질의: "연차휴가 일수 기준이 어떻게 되나요?"

   BM25 결과       1위 연차휴가 일수 기준표  ← 정답
   벡터 결과       1위 연차휴가 FAQ
                  2위 연차휴가 관련 규정
                  … 기준표는 20위권

   RRF 융합
     기준표     = 1/(60+1)  + 1/(60+20) = 0.0164 + 0.0125 = 0.0289
     연차휴가FAQ = 1/(60+8)  + 1/(60+1)  = 0.0147 + 0.0164 = 0.0311  ← 이긴다

   → 벡터가 «잘못 짚은» 문서가 양쪽에 걸쳐 있어 정답을 밀어냈다
```

> 🔑 **RRF 는 «두 방식이 비슷하게 좋을 때» 이득입니다.**
> 한쪽이 명백히 옳을 때는 다른 쪽이 **희석 요인**이 됩니다.
> → 대책: 벡터 가중치를 낮추거나, **권위 가중을 얹는다**.

## 5. 시맨틱 재순위 (L2)

### 5.1 Azure 시맨틱 랭커

```
   RRF 로 융합한 결과를 «교차 인코더»로 다시 순위 매긴다.
   질의와 문서를 «함께» 보므로 벡터 유사도보다 정확하다.

   @search.rerankerScore  0.00 ~ 4.00  (@search.score 와 별도로 반환)
```

> ★ **에이전트 검색이 내부적으로 이것을 사용합니다.**
> 시맨틱 구성이 없으면 지식 베이스가 동작하지 않습니다.

### 5.2 로컬 근사 구현과 그 한계

이 프로젝트의 `naive_rerank` 는 Azure 랭커가 **아닙니다.**
«재순위 단계가 붙으면 결과가 어떻게 달라지는지»를 비용 없이 보여 주는 교육용 근사입니다.

```python
score = (overlap * 2.0 + title_hit * 3.0 + density * 0.3) * recency
```

| 요소 | 의미 |
| --- | --- |
| `overlap` | **IDF 가중** 용어 재현율 |
| `title_hit` | 제목 일치 |
| `density` | 짧은 문서 우대 |
| `recency` | 현행 1.0 / 개정예정 0.3 / **폐지 0.05** |

### 5.3 ★ IDF 가중이 없어서 실패했던 기록

```
   ❌ 처음 구현 — 단순 토큰 겹침 수

   질의  "연차휴가 일수 기준이 어떻게 되나요?"
   토큰  [연차, 차휴, 휴가, 가일, 일수, 어떻, 떻게, 게되, 되나, 나요]
                                     └──── 5개가 «질문 어투» ────┘

   «어떻게 되나요?»로 끝나는 FAQ 제목이 이 5개를 전부 맞힌다.
   정작 답이 있는 «연차휴가 일수 기준표»는 그 어투가 없어 진다.

   → 재순위가 «답의 관련성»이 아니라 «질문 어투의 유사성»을 보상했다
```

**결과: 숫자 정밀도 Recall@5 = 0.000**

```python
# ✅ 수정 — IDF 로 가중한다
weights = {t: idf.get(t, 0.0) for t in query_tokens}
overlap = sum(w for t, w in weights.items() if t in chunk_tokens) / sum(weights.values())
```

`어떻`·`나요` 는 수천 문서에 나타나 IDF ≈ 0 → 기여가 사라집니다.
`일수`·`연차` 가 점수를 지배합니다.

**수정 후: 숫자 정밀도 Recall@5 = 1.000**

> 🔑 **이 실패는 «고빈도 토큰을 걸러야 한다»는 정보 검색의 기본을 잊어서 생겼습니다.**
> Azure 시맨틱 랭커는 학습된 모델이라 이런 실수를 하지 않습니다.

## 6. ★ 문서 유형 권위 가중 — 최대 개선

### 6.1 문제

```
   코퍼스 구성
     FAQ + 문의이력  7,600건 (69 %)
     규정 + 안내서   1,432건 (13 %)

   질의: "연차휴가 한도가 며칠인가요?"

    1위  연차휴가 한도가 어떻게 되나요?              (FAQ)
    2위  수습 기간인데 연차휴가 한도가 어떻게 되나요?  (FAQ)
    3위  해외근무 중인데 연차휴가 한도가…            (FAQ)
    …
   15위  연차휴가 운영기준 (현행)                    (규정)  ← 정답
   58위  연차휴가 운영기준 (폐지)                    (규정)
```

> **구버전이 현행을 이긴 적은 없습니다** (58위 vs 15위).
> 진짜 문제는 «FAQ 변형이 권위 문서를 덮는 것»이었습니다.

### 6.2 해법 — 유형별 가중치

```python
AUTHORITY_BOOST = {
    "규정": 2.0,        # 사규 — 최종 근거
    "규정전문": 1.8,
    "안내서": 1.7,      # 기준표·한도표가 여기 있다
    "지침": 1.5,
    "매뉴얼": 1.4,
    "서식안내": 1.2,
    "공지": 1.1,
    "FAQ": 1.0,         # 편의 요약 — 수치가 다를 수 있다
    "문의이력": 0.8,    # 개별 사례. 일반화하면 위험하다
}
```

> **이 가중치는 «도메인 지식»입니다.** 검색 엔진은 «규정이 FAQ보다 권위 있다»를 스스로 알 수 없습니다.
> 사람이 알려 줘야 합니다.

### 6.3 효과 (측정)

| 지표 | 가중 없음 | **가중 적용** | 변화 |
| --- | ---: | ---: | --- |
| Recall@5 | 0.609 | **0.793** | **+30 %** |
| Precision@5 | 0.283 | 0.352 | +24 % |
| MRR | 0.605 | **0.801** | **+32 %** |
| nDCG@5 | 0.451 | **0.667** | **+48 %** |
| **버전충돌 Recall@5** | 0.000 | **1.000** | — |
| 숫자정밀도 Recall@5 | 1.000 | 1.000 | 유지 |

> 🔑 **이 프로젝트에서 가장 큰 단일 개선이었습니다.**
> 임베딩 모델을 바꾸거나 청크 크기를 조정하는 것보다 효과가 컸습니다.

### 6.4 Azure 에서 구현하는 방법

| 방법 | 설명 |
| --- | --- |
| **scoringProfile** | 필드 값에 따라 점수를 곱한다 (`tagBoostingParameters`) |
| **retrievalInstructions** | 에이전트 검색에서 LLM 에게 «규정을 우선하라»고 지시 |
| 클라이언트 후처리 | 결과를 받아 직접 재정렬 (이 프로젝트 로컬 구현) |

이 프로젝트는 **지식 베이스의 `retrievalInstructions`** 에 명시했습니다.

```
3. 숫자(일수·금액·기한)를 묻는 질문은 '규정' 또는 '안내서' 유형을 우선한다.
   FAQ 와 문의이력은 요약이라 수치가 다를 수 있다.
4. 절차를 묻는 질문은 '지침' 또는 '서식안내' 유형을 우선한다.
```

## 7. 필터 — 검색 «전»에 배제한다

### 7.1 보안 필터 (항상 적용)

```python
def apply_filter(chunks, filters, security_clearance=None):
    """★ 보안 등급은 «필터»가 아니라 «강제»다.
      사용자가 요청하지 않아도 항상 적용해야 한다.
      LLM 프롬프트로 «제한 문서는 보여 주지 마»라고 지시하는 것은 방어가 아니다.
      검색 단계에서 아예 제외해야 한다.
    """
```

```odata
security_level ne '제한'
```

**측정: 전 7개 전략에서 제한 문서 노출 0건** ✅

### 7.2 상태 필터 (선택 적용)

```odata
status eq '현행'
```

> ⚠️ **측정 결과 상태 필터가 «아무것도 바꾸지 않았습니다».**
> 폐지 문서가 이미 58위로 밀려 있어 상위 40 후보에 들어오지 않았기 때문입니다.
> 그래도 필터를 두는 이유 — **결정적**이기 때문입니다.
> 재순위는 «점수 경쟁»이라 상황에 따라 밀릴 수 있지만, 필터는 «후보에서 아예 뺍니다».

## 8. 최종 파이프라인

```
   질의
    │
    ├─ ① 보안 필터 조립      security_level ne '제한'   ★ 코드가 만든다
    │
    ├─ ② BM25 검색           상위 recall 건
    ├─ ③ 벡터 검색           상위 recall 건
    │
    ├─ ④ RRF 융합            k=60, vector_weight=1.0
    │
    ├─ ⑤ 시맨틱 재순위       IDF 가중 + 최신성
    │
    ├─ ⑥ 권위 가중           doc_type 별 × 0.8 ~ 2.0
    │
    └─ ⑦ 상위 K 반환         K=5
```

### 8.1 `recall` 을 `top` 보다 크게 잡는 이유

```
   recall = 융합 «전»에 각 방식에서 뽑는 후보 수

   recall = top   한쪽에서만 잡힌 문서가 살아남지 못한다
   recall = top×8 후보가 충분해 융합이 의미를 갖는다

   Azure 대응: maxTextRecallSize (기본 1,000)
```
