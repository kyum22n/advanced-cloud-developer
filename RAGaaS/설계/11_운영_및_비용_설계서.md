## 1. 비용 구조 — 어디서 돈이 나가는가

```
   ① 초기 색인 (1회)
        임베딩 토큰 3,117,319   ← 측정값

   ② 인덱스 유지 (월 고정)
        AI Search 계층 요금 + 저장 (벡터 약 79 MB @1536차원)

   ③ 질의당 (변동) ★ 가장 중요
        임베딩     쿼리 벡터화 20~50 토큰
        검색 토큰  시맨틱 재순위 (에이전트는 하위 쿼리 수만큼 배수)
        LLM 입력   근거 5건 × 252자 ≈ 800 토큰 + 시스템 프롬프트
        LLM 출력   답변 ≈ 200~400 토큰
        (에이전트) 쿼리 계획 입력 ~2,000 / 출력 ~350 토큰

   ④ 재색인 (변동)
        변경 문서만 — 정상 운영에서는 작다
        ⚠️ 청킹·모델 변경 시 «전체» — 실험마다 300만 토큰
```

### 1.1 질의당 비용을 좌우하는 것

| 요인 | 영향 | 통제 수단 |
| --- | --- | --- |
| **근거 개수** | LLM 입력에 선형 | 5건 고정 |
| **에이전트 사용 여부** | 계획 LLM + 하위 쿼리 배수 | **질의 라우팅** |
| 하위 쿼리 수 | 검색 토큰에 선형 | 분해 최대 4개 |
| 지식 원본 수 | 팬아웃 | 1개로 통합 |
| 재순위 청크 수 | 검색 토큰 | `top` 제한 |
| 답변 길이 | LLM 출력 | 최대 800 토큰 |

### 1.2 ⚠️ 단가를 이 문서에 적지 않은 이유

```
   Azure 단가는 지역·계약·시점에 따라 다릅니다.
   임의의 숫자를 적으면 그것이 «근거»처럼 인용되어 예산이 틀어집니다.

   → 이 문서는 «계산 구조»만 제공합니다.
     실제 단가는 Azure 가격 페이지에서 확인해 대입하세요.

   embed.py 도 같은 방침입니다:
     "단가_USD_per_1M": None,   # ← 확인 필요. 임의로 채우면 예산이 틀어진다
```

실행 시 이렇게 출력됩니다.

```
 ⚠️ 단가가 «확인 필요» 상태입니다.
    계산식: 3,117,319 토큰 ÷ 1,000,000 × 단가(USD/1M)
```

## 2. 비용 절감 — 효과 순

| # | 방법 | 절감 | 대가 |
| --- | --- | --- | --- |
| 1 | **질의 라우팅** (단순은 `minimal`) | 큼 | 판별 로직 필요 |
| 2 | **차원 축소** 3072 → 1536 | 저장 50 % | 품질 확인 필요 |
| 3 | **스칼라 양자화** | 저장 추가 75 % | 재순위로 보상 |
| 4 | **지식 원본 통합** (1개) | 팬아웃 감소 | — |
| 5 | **근거 개수 제한** (5건) | LLM 입력 | 완전성 저하 가능 |
| 6 | **큐레이팅된 기준표** | 검색 토큰 | 문서 정리 노력 |
| 7 | dev 환경 축소 | 고정비 | — |

### 2.1 ★ 6번 «큐레이팅»이 가장 근본적이다

```
   질의: "연차휴가 한도가 며칠인가요?"

   ❌ 흩어진 FAQ 20건을 뒤진다
        검색 토큰 20 × 250자
        LLM 이 20건에서 답을 «조합»해야 한다 → 오류 가능성

   ✅ 기준표 1건으로 답이 나온다
        검색 토큰 1 × 400자
        LLM 은 인용만 하면 된다
```

> 이 프로젝트에서 «연차휴가 일수 기준표» 같은 문서를 별도로 둔 것이 그 예입니다.
> **문서를 정리하는 것이 인프라를 키우는 것보다 싸고 정확합니다.**

## 4. 색인 운영

### 4.1 인덱서 스케줄

| 환경 | 주기 | 근거 |
| --- | --- | --- |
| dev | 수동 | 실험 중 자동 실행은 방해된다 |
| stg | PT15M | |
| prd | **PT5M** | 속도 제한에 걸린 호출을 다음 실행에서 재시도 |

```json
{ "schedule": { "interval": "PT5M" },
  "parameters": { "batchSize": 50, "maxFailedItems": 10, "maxFailedItemsPerBatch": 5 } }
```

### 4.2 ★ 색인과 질의의 충돌

```
   문제
     대량 색인 중 Azure OpenAI TPM 이 소진되면
     «사용자 질의의 쿼리 벡터화»도 429 를 받는다
     → 검색이 «먹통»이 된다

   대응
     ① 배포 분리        색인용 · 질의용 Azure OpenAI 배포를 나눈다  ← 가장 확실
     ② 시간대 분리      대량 색인을 업무 시간 외로
     ③ 배치 크기 조정   batchSize 를 낮춰 순간 부하를 줄인다
```

> ⚠️ **①이 실무에서 가장 중요합니다.** 흔한 사고 유형입니다.

### 4.3 증분 색인

```json
"dataChangeDetectionPolicy": {
  "@odata.type": "#Microsoft.Azure.Search.HighWaterMarkChangeDetectionPolicy",
  "highWaterMarkColumnName": "metadata_storage_last_modified"
},
"dataDeletionDetectionPolicy": {
  "@odata.type": "#Microsoft.Azure.Search.SoftDeleteColumnDeletionDetectionPolicy",
  "softDeleteColumnName": "IsDeleted",
  "softDeleteMarkerValue": "true"
}
```

> **삭제 감지가 없으면** 원본에서 지운 문서가 인덱스에 남아 «없는 문서를 인용»하게 됩니다.

## 5. 관측 지표

### 5.1 기술 지표

| 지표 | 목표 | 경고 |
| --- | --- | --- |
| 검색 응답 p95 | ≤ 1.5초 | > 3초 |
| TTFT p95 | ≤ 3초 | > 6초 |
| 검색 오류율 | < 0.1 % | > 1 % |
| 인덱서 실패 문서 | 0 | > 10 |
| 반영 지연 | ≤ 1시간 | > 2시간 |

### 5.2 ★ 품질 지표 — 이것이 더 중요하다

| 지표 | 의미 | 수집 |
| --- | --- | --- |
| **«찾지 못함» 응답 비율** | 커버리지 부족 신호 | 응답 분류 |
| **사용자 «도움 안 됨» 비율** | 품질 저하 신호 | 피드백 버튼 |
| **담당자 재문의 전환율** | 챗봇이 해결 못 한 비율 | 문의 시스템 연계 |
| 근거 최고 점수 분포 | 임계값 조정 근거 | 검색 로그 |
| 질의 유형 분포 | **투자 방향 결정** | 질의 분류 |

```
   기술 지표가 전부 초록인데 사용자가 안 쓰는 경우가 흔하다.
   → 「응답 시간 0.8초」보다 「도움 안 됨 40 %」가 더 중요한 신호다
```

### 5.3 질의 유형 분포를 재는 이유

```
   [분석/03 §6](../분석/03_질의_유형_분석.md) 의 «가정 분포»를 실측으로 대체해야 한다.

   예: 다중 홉이 실제로 30 % 라면
        → 에이전트 검색이 «필수»가 된다
        → medium 추론 노력에 예산을 써야 한다

   예: 다중 홉이 1 % 라면
        → 에이전트 경로를 제거해도 된다
        → 비용이 크게 줄어든다
```

## 6. 정기 점검

| 주기 | 항목 |
| --- | --- |
| **일** | 인덱서 실패 · 오류율 · 응답 시간 |
| **주** | «찾지 못함» 비율 · 피드백 · 질의 유형 분포 |
| **월** | 평가 세트 재실행 · 비용 리뷰 · 커버리지 부족 주제 식별 |
| **분기** | 평가 세트 갱신 (제도 개정 반영) · 권위 가중치 재검토 |
| **연** | 임베딩 모델 재검토 · 아키텍처 ADR 재검토 |

### 6.1 «찾지 못함» 로그가 가장 값지다

```
   사용자가 물었는데 답이 없었던 질의 목록
     → 이것이 «문서를 어디에 더 만들어야 하는가»를 알려 준다
     → 인사·총무팀에 «이 주제 FAQ 를 만들어 주세요»라고 요청할 근거
```

## 8. 배포 절차

```
   ① 코퍼스 준비        generate_corpus.py → corpus.jsonl
   ② 청킹              chunker.py → chunks.jsonl + chunk_stats.json
   ③ 비용 추정          embed.py --estimate-only        ★ 여기서 멈춰 확인
   ④ 구성 생성          build_azure_config.py --env dev
   ⑤ 자리표시자 치환    {AZURE_OPENAI_RESOURCE} 등
   ⑥ 인덱스 배포        deploy_index.py --env dev       ⚠️ 사람이 실행
   ⑦ 데이터 업로드      Blob 또는 푸시
   ⑧ 색인 실행          인덱서 실행 또는 직접 업로드     ⚠️ 과금 시작
   ⑨ 검증              eval_retrieval.py
   ⑩ 플레이그라운드     Foundry 에서 인덱스 연결 · 시나리오 시연
```

> ⛔ **③에서 반드시 멈춰 규모를 확인합니다.**
> 임베딩은 되돌릴 수 없는 비용입니다.

### 8.1 이 프로젝트에서 실행한 범위

| 단계 | 상태 |
| --- | :---: |
| ①~④ | ✅ 실행 완료 |
| ⑤~⑧ | ❌ **실행하지 않음** (Azure 구독·과금 필요) |
| ⑨ | ✅ 로컬 LSA 기준으로 실행 |
| ⑩ | ⚠️ 절차 문서만 |

## 9. 사고 대응

| 사고 | 증상 | 즉시 조치 | 근본 원인 |
| --- | --- | --- | --- |
| 검색 먹통 | 429 다발 | 색인 중단 | TPM 소진 — 배포 분리 |
| 틀린 답변 신고 | 사용자 보고 | 상관 ID 로 근거 추적 | 문서 상태 오류 가능 |
| 제한 문서 노출 | **심각** | **서비스 중단** | 필터 누락 — 코드 검토 |
| 비용 급증 | 예산 경고 | 라우팅 임계 상향 | 에이전트 남용 |
| 응답 지연 | p95 초과 | 근거 개수 축소 | 랭커 또는 LLM 병목 |

> **«제한 문서 노출»은 유일하게 «즉시 중단»이 정답인 사고입니다.**
> 다른 사고는 품질 저하이지만, 이것은 정보 유출입니다.
