# 01. 요구사항 분석 — 인사·총무 Hybrid RAGaaS

> **목적** — "사내 문서로 챗봇 만들자"는 막연한 요청을 **검증 가능한 요구사항**으로 바꿉니다.
> 이 문서가 이후 설계·개발·테스트의 출발점(추적성 매트릭스의 좌측 열)입니다.
> 다음: [02_도메인_지식체계_분석.md](02_도메인_지식체계_분석.md)

## 1. 문제 정의

### 1.1 현재 상태

| 관찰 | 결과 |
| --- | --- |
| 규정·지침·FAQ·공지가 **여러 시스템에 흩어져** 있다 | 직원이 어디를 봐야 할지 모른다 |
| 검색이 **파일명·제목 키워드**만 지원한다 | "연차 며칠 남아요?"로는 아무것도 안 나온다 |
| 같은 주제에 **구버전과 신버전**이 공존한다 | 폐지된 규정을 보고 잘못 신청한다 |
| 담당자가 **같은 질문에 반복 응답**한다 | 인사·총무팀 시간의 상당분이 단순 문의 응대 |
| 답을 못 찾으면 **담당자에게 직접 문의** | 응답까지 수 시간~수 일 |

### 1.2 하려는 것

> 직원이 **평소 쓰는 말**로 물으면, **현행 규정에 근거해서**, **출처와 함께** 답한다.
> 답이 없으면 **없다고 말한다.**

마지막 문장이 가장 중요합니다. RAG 시스템의 가장 흔하고 위험한 실패는
«없는 답을 그럴듯하게 지어내는 것»입니다.

## 2. 사용자와 이용 맥락

| 사용자 | 비중(가정) | 주로 묻는 것 | 특징 |
| --- | --- | --- | --- |
| **일반 직원** | 70 % | 휴가·경비·비품·복리후생 | 구어체·약어. 규정 용어를 모른다 |
| **신입사원** | 10 % | 절차·서식·담당 부서 | 사내 용어 자체를 모른다 |
| **관리자** | 10 % | 승인 권한·평가·조직 운영 | 정확한 규정 조항을 원한다 |
| **인사·총무 담당자** | 10 % | 예외 처리·근거 확인 | **제한 등급 문서** 접근 필요 |

> ⚠️ **비중은 가정입니다.** 실제 구축 시에는 기존 문의 로그를 분석해 대체해야 합니다.
> 이 비중이 «어떤 질의 유형에 투자할지»를 결정하므로, 틀리면 최적화 방향이 틀립니다.

## 3. 기능 요구사항 (FR)

**분해 기준** — «파이프라인의 어느 단계인가»
서로 겹치지 않고(ME) 빠짐없이(CE) 5개 그룹으로 나눴습니다.

### 그룹 A — 데이터 수집·적재

| ID | 요구사항 | 우선순위 | 검증 |
| --- | --- | --- | --- |
| FR‑A‑01 | 인사·총무 문서를 **1만 건 이상** 확보·적재한다 | 必 | 건수 확인 |
| FR‑A‑02 | 문서 유형(규정/지침/FAQ/문의이력/공지/서식/안내서)을 구분한다 | 必 | 스키마 검증 |
| FR‑A‑03 | 분류·시행일·상태·보안등급 **메타데이터**를 보유한다 | 必 | 필드 존재 |
| FR‑A‑04 | 원본이 변경되면 **증분 반영**한다 | 必 | 인덱서 스케줄 |
| FR‑A‑05 | 폐지·만료 문서를 **상태로 구분**한다 (삭제하지 않음) | 必 | 상태 필드 |

### 그룹 B — 청킹·임베딩·인덱싱

| ID | 요구사항 | 우선순위 | 검증 |
| --- | --- | --- | --- |
| FR‑B‑01 | 장문 문서를 **검색 단위로 분할**한다 | 必 | 청크 통계 |
| FR‑B‑02 | 문서 **유형별로 다른 분할 전략**을 적용한다 | 必 | 유형별 배율 |
| FR‑B‑03 | 청크에 **부모 문서 참조**를 유지한다 | 必 | parent_id |
| FR‑B‑04 | 청크를 **벡터로 변환**해 색인한다 | 必 | 벡터 차원 |
| FR‑B‑05 | 청크마다 **메타데이터를 복제**해 필터가 가능하게 한다 | 必 | 필터 동작 |
| FR‑B‑06 | 한국어 **형태소 분석기**를 적용한다 | 必 | 분석기 설정 |

### 그룹 C — 검색

| ID | 요구사항 | 우선순위 | 검증 |
| --- | --- | --- | --- |
| FR‑C‑01 | **키워드(BM25)** 검색을 지원한다 | 必 | 정확 용어 질의 |
| FR‑C‑02 | **벡터(의미)** 검색을 지원한다 | 必 | 동의어 질의 |
| FR‑C‑03 | 둘을 **RRF로 융합**한 하이브리드 검색을 지원한다 | 必 | 융합 결과 |
| FR‑C‑04 | **시맨틱 재순위**로 상위 결과를 정렬한다 | 必 | 순위 변화 |
| FR‑C‑05 | 복잡한 질문을 **하위 쿼리로 분해**해 병렬 검색한다 (에이전트) | 必 | 활동 로그 |
| FR‑C‑06 | 분류·상태·기간으로 **필터**할 수 있다 | 必 | 필터 질의 |
| FR‑C‑07 | **문서 유형 권위**를 순위에 반영한다 | 必 | 부스팅 |
| FR‑C‑08 | 질의 복잡도에 따라 **전략을 라우팅**한다 | 選 | 라우팅 로그 |

### 그룹 D — 응답 생성

| ID | 요구사항 | 우선순위 | 검증 |
| --- | --- | --- | --- |
| FR‑D‑01 | 검색된 근거**만**으로 답변을 생성한다 | 必 | 근거성 평가 |
| FR‑D‑02 | 답변에 **출처(문서·조항·링크)**를 표시한다 | 必 | 인용 존재 |
| FR‑D‑03 | 근거가 부족하면 **모른다고 답한다** | 必 | 범위밖 질의 |
| FR‑D‑04 | **현행 규정**을 우선해 답한다 | 必 | 버전충돌 질의 |
| FR‑D‑05 | 대화 맥락(이전 질문)을 반영한다 | 選 | 다중 턴 |
| FR‑D‑06 | 답변 불가 시 **담당 부서·채널**을 안내한다 | 選 | 폴백 |

### 그룹 E — 운영·보안

| ID | 요구사항 | 우선순위 | 검증 |
| --- | --- | --- | --- |
| FR‑E‑01 | **보안등급별 접근 제어**를 적용한다 | 必 | 권한 질의 |
| FR‑E‑02 | 질의·응답을 **로깅**한다 (개인정보 마스킹) | 必 | 로그 확인 |
| FR‑E‑03 | 검색 품질을 **정기 측정**한다 | 必 | 평가 리포트 |
| FR‑E‑04 | 답변에 **피드백**을 받는다 | 選 | 피드백 저장 |
| FR‑E‑05 | **Azure AI Foundry 플레이그라운드**에서 시연 가능해야 한다 | 必 | 시연 절차 |

> **합계 — 기능 요구사항 30건** (必 26 · 選 4)

## 4. 비기능 요구사항 (NFR)

> ❗ *"정확해야 한다"* 는 요구사항이 아닙니다. **숫자와 측정 방법**이 있어야 요구사항입니다.

| ID | 분류 | 요구사항 | 목표 | 측정 |
| --- | --- | --- | --- | --- |
| NFR‑01 | 검색품질 | 사실 조회 질의 Recall@5 | ≥ 0.80 | 평가 세트 |
| NFR‑02 | 검색품질 | 전체 질의 MRR | ≥ 0.70 | 평가 세트 |
| NFR‑03 | 검색품질 | 숫자 정밀도 질의 Recall@5 | ≥ 0.90 | 평가 세트 |
| NFR‑04 | 검색품질 | 다중 홉 질의 Recall@5 | ≥ 0.50 | 평가 세트 |
| NFR‑05 | **안전** | **구버전 우선 노출** | **0건** | 평가 세트 |
| NFR‑06 | **안전** | **제한 문서 노출** | **0건** | 평가 세트 |
| NFR‑07 | **안전** | 범위 밖 질의에 대한 **환각 응답** | 0건 | 생성 평가 |
| NFR‑08 | 응답성능 | 검색 응답 p95 | ≤ 1.5초 | 부하 측정 |
| NFR‑09 | 응답성능 | 첫 토큰까지(TTFT) p95 | ≤ 3초 | 부하 측정 |
| NFR‑10 | 비용 | 질의당 평균 비용 | 예산 내 | 토큰 집계 |
| NFR‑11 | 확장성 | 문서 10만 건까지 무변경 확장 | 구조 검증 | 설계 검토 |
| NFR‑12 | 신선도 | 문서 변경 반영 지연 | ≤ 1시간 | 인덱서 주기 |
| NFR‑13 | 보안 | 저장·전송 비밀 평문 노출 | **0건** | 정적 검증 |
| NFR‑14 | 관측성 | 질의별 근거 추적 가능 | 100 % | 활동 로그 |

| ID | 제약 | 영향 |
| --- | --- | --- |
| CON‑01 | 플랫폼은 **Azure AI 서비스**로 한정 | 검색·임베딩·생성 선택지가 Azure 로 제한 |

## 6. 성공 기준 — 무엇을 보면 «됐다»고 하는가

```
   ① 데이터    1만 건 이상, 유형·분류·상태가 구분된 코퍼스가 있다
   ② 파이프라인 청킹 → 임베딩 → 인덱싱이 «실행되고» 통계가 남는다
   ③ 검색      키워드/벡터/하이브리드/에이전트가 «각각 동작»하고 차이를 수치로 보인다
   ④ 품질      평가 세트로 전략별 Recall·MRR 을 «비교»할 수 있다
   ⑤ 안전      제한 문서 노출 0건, 구버전 우선 0건이 «측정»된다
   ⑥ 시연      플레이그라운드에서 시나리오 대화가 «재현»된다
```
