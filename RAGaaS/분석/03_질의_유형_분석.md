# 03. 질의 유형 분석 — 어떤 질문에 어떤 검색이 필요한가

> **목적** — 사용자 질문을 **난이도·필요 기능**으로 분류하고, 유형마다 어떤 검색 전략이 필요한지 매핑합니다.
> 이 분류가 그대로 [평가 세트](../테스트/goldenset/)와 [질의 라우팅](../설계/06_Hybrid_검색_설계서.md) 의 근거가 됩니다.
> 앞: [02_도메인_지식체계_분석.md](02_도메인_지식체계_분석.md) · 다음: [04_데이터_소스_분석.md](04_데이터_소스_분석.md)

## 1. 왜 질의를 «유형»으로 나누는가

"검색 성능이 80 %입니다"는 쓸모없는 정보입니다. 무엇이 80 %인지 모르기 때문입니다.

```
   전체 Recall 0.60
        │
        ├── 사실 조회      0.80  ← 잘 된다
        ├── 숫자 정밀도    0.40  ← 못 한다. BM25 가 약하다
        ├── 버전 충돌      0.00  ← 못 한다. 권위 가중이 없다
        ├── 다중 홉        0.44  ← 못 한다. 분해가 없다
        └── 동의어·구어    0.50  ← 반반. 벡터가 약하다
```

**평균 하나로는 무엇을 고쳐야 할지 알 수 없습니다.** 유형별로 봐야 처방이 나옵니다.

---

## 2. 질의 유형 7종 (MECE)

**분해 기준** — «답을 얻으려면 무엇이 추가로 필요한가»

| # | 유형 | 정의 | 필요 기능 | 난이도 |
| --- | --- | --- | --- | :---: |
| **A** | 사실 조회 | 단일 문서로 답이 나온다 | 하이브리드 | ★ |
| **B** | 숫자 정밀도 | 수치·금액·일수가 답의 핵심 | BM25 + 권위 가중 | ★★ |
| **C** | 버전 충돌 | 구버전·신버전이 공존 | 상태 필터 + 권위 가중 | ★★★ |
| **D** | 다중 홉 | 2~3개 문서를 조합해야 함 | **쿼리 분해(에이전트)** | ★★★★ |
| **E** | 동의어·구어 | 표현이 문서와 다름 | 벡터 + 동의어 맵 | ★★ |
| **F** | 권한 제한 | 볼 수 없는 문서를 물음 | **보안 필터** | ★★ |
| **G** | 범위 밖 | 답이 지식 베이스에 **없음** | **거절 응답** | ★★★★★ |

## 3. 유형별 상세

### A. 사실 조회 — 기본 성능

```
   "연차휴가 어떻게 신청하나요?"
   "출장비 정산 필요 서류가 무엇인가요?"
   "건강검진 담당 부서가 어디인가요?"
```

| | 내용 |
| --- | --- |
| 특징 | 하나의 문서(FAQ·지침)에 답이 완결되어 있다 |
| 필요 | 기본 하이브리드로 충분 |
| 실패 시 | **여기서 실패하면 나머지를 볼 필요가 없다.** 파이프라인 자체가 잘못된 것 |
| 측정 결과 | 전 전략 Recall@5 = **0.800** (동률) |

> 💡 전 전략이 동률이라는 것은 «이 유형에서는 전략 선택이 무의미»하다는 뜻입니다.
> 여기에 최적화 노력을 쓰면 낭비입니다.

### B. 숫자 정밀도 — 벡터가 못 하는 것

```
   "연차휴가 일수 기준이 어떻게 되나요?"    → 15일? 25일?
   "출장 숙박비 한도 기준이 어떻게 되나요?"  → 12만원? 8만원?
```

| | 내용 |
| --- | --- |
| 왜 어려운가 | 「15일」과 「25일」은 **의미 공간에서 거의 같은 위치**에 있다 |
| 필요 | BM25 의 정확 토큰 일치 + 권위 있는 기준표를 위로 올리는 가중 |
| 측정 결과 | vector **0.400** · keyword **1.000** · boosted **1.000** |

```
   vector  0.400  ← 벡터만으로는 절반 이상 틀린다
   keyword 1.000  ← 정확 용어 매칭이 결정적
   hybrid  0.400  ← ⚠️ RRF 가 벡터 결과에 희석된다
   boosted 1.000  ← 권위 가중이 기준표를 끌어올린다
```

> ❗ **hybrid 가 keyword 보다 나쁩니다.** 이것은 «하이브리드가 항상 낫다»가 거짓임을 보여 줍니다.
> RRF 는 두 결과를 «순위로» 합치므로, 한쪽이 명백히 옳을 때 다른 쪽이 희석시킵니다.
> → 대책: 벡터 가중치를 낮추거나(`vector_weight < 1`), 권위 가중을 얹는다.

### C. 버전 충돌 — 가장 위험한 유형

```
   "연차휴가 한도가 며칠인가요?"

   문서 A: [폐지] 연차휴가 운영기준 v1.0 — 한도 연 10일    ← 2025-12-31 폐지
   문서 B: [현행] 연차휴가 운영기준 v2.0 — 한도 연 20일    ← 2026-01-01 시행
```

| | 내용 |
| --- | --- |
| 왜 위험한가 | 틀린 답이 **그럴듯하다.** 사용자가 틀렸다는 것을 알 수 없다 |
| 필요 | `status eq '현행'` 필터 + 권위 가중 |
| 측정 결과 | semantic **0.000** → boosted **1.000** |

**측정에서 배운 것 — 지표를 잘못 잡을 뻔했다**

처음에는 «정답 문서가 상위 5위 안에 있는가»(Recall)로 쟀습니다. 결과가 0.000 이라 실패로 보였습니다.
실제로 확인해 보니:

```
   현행 문서 순위: 15위
   구버전 문서 순위: 58위      ← 이미 한참 아래
```

**구버전이 현행을 이긴 적이 없었습니다.** 문제는 버전 처리가 아니라 «FAQ 3,600건이 규정을 덮는 것»이었습니다.
→ 지표를 «상대 순서(구버전이 현행보다 위에 오는가)»로 바꾸니 **전 전략 0건**으로 안전.
→ 진짜 문제(권위)는 문서 유형 가중으로 해결.

> 🔑 **잘못된 지표는 없는 문제를 만들고 있는 문제를 감춥니다.**

### D. 다중 홉 — 에이전트 검색이 필요한 유일한 이유

```
   "3년차 개발직이 육아휴직을 쓰면 급여와 평가는 어떻게 되나요?"

   답에 필요한 문서 3개
     ① 육아휴직 급여 처리     — 고용보험 급여 + 회사 추가 지원 20 %
     ② 휴직자 인사평가 처리   — 평가 기간 절반 초과 시 유예
     ③ 육아휴직 신청 자격     — 재직 6개월 이상, 직군 제한 없음
```

| | 내용 |
| --- | --- |
| 왜 어려운가 | 질문 전체를 **하나의 벡터**로 만들면 «세 주제의 평균 지점»이 된다. 어느 문서와도 특별히 가깝지 않다 |
| 필요 | 쿼리 분해 → 병렬 검색 → 결과 합성 |
| 측정 결과 | hybrid **0.444** · agentic+boost **0.556** |

**실제 비교 (수동 실행)**

```
   단일 하이브리드 질의 상위 5
     1. 육아휴직 한도가 어떻게 되나요?          (FAQ)
     2. 신입사원인데 육아휴직 한도가…           (FAQ)
     3. 퇴사 예정인데 육아휴직 관련 규정이…      (FAQ)
     ⋯ 필요 문서 3개 중 0개

   에이전트 검색 (2개 하위 쿼리로 분해)
     하위쿼리 1: "육아휴직 급여"   → 육아휴직 급여 처리      ★
     하위쿼리 2: "육아휴직 인사평가" → 휴직자 인사평가 처리    ★
     ⋯ 필요 문서 3개 중 2개
```

> ⚠️ **에이전트 검색은 만능이 아닙니다.** 전체 Recall 은 오히려 낮습니다(0.540 vs boosted 0.793).
> 단일 주제 질문을 억지로 분해하면 결과가 흩어져 나빠집니다.
> → **질의 유형에 따라 라우팅**해야 합니다.

### E. 동의어 · 구어체 — 벡터가 필요한 이유

```
   "법카 정산 어떻게 해요"     ← 문서에는 «법인카드»
   "육휴 쓰면 월급 나와요?"     ← 문서에는 «육아휴직»
   "애 낳으면 며칠 쉬어요?"     ← 문서에는 «배우자 출산 휴가»
```

| | 내용 |
| --- | --- |
| 필요 | 벡터 검색 또는 Azure 동의어 맵 |
| 측정 결과 | keyword **0.667** · semantic **0.667** · vector 0.500 |

> ⚠️ **로컬 LSA 임베딩의 한계가 드러난 지점입니다.**
> LSA 는 «이 코퍼스 안의 단어 공기»만 봅니다. «법카 ↔ 법인카드»를 학습한 적이 없습니다.
> 실제 Azure OpenAI 임베딩은 사전 학습 지식이 있어 이 유형에서 훨씬 강할 것으로 예상되지만,
> **측정하지 않았으므로 단정하지 않습니다.**

### F. 권한 제한 — 실패하면 사고

```
   일반 직원: "징계 양정 기준표 알려주세요"
   → 정답은 «결과 없음» 또는 «권한 안내»
```

| | 내용 |
| --- | --- |
| 필요 | `security_level` 필터를 **항상** 적용 |
| 측정 결과 | 전 전략 **위반 0건** |
| 주의 | LLM 프롬프트로 막으면 안 된다. 검색에서 배제해야 한다 |

### G. 범위 밖 — RAG 의 가장 위험한 실패 모드

```
   "경쟁사 연봉 테이블 알려줘"
   "다음 분기 조직개편 계획은?"
   "옆자리 동료 연봉이 얼마인가요?"
```

| | 내용 |
| --- | --- |
| 정답 | **"해당 정보는 없습니다"** + 담당 안내 |
| 실패 모드 | 관련 없는 문서를 근거로 그럴듯한 답을 지어낸다 |
| 측정 결과 | 5건 중 4~5건에서 «근거를 찾음» |

> ⚠️ **이것은 검색의 실패가 아닙니다.**
> 검색은 언제나 «가장 가까운 것»을 돌려줍니다. 그것이 검색의 정의입니다.
>
> «모른다»고 말하는 것은 **생성 단계의 책임**입니다.
>   · 근거 점수 임계값 — 최고 점수가 낮으면 답하지 않는다
>   · 시스템 프롬프트 — "근거에 없으면 모른다고 답하라"
>   · 근거성 평가 — 답변의 각 문장이 근거에 있는지 확인
>
> → [설계/08](../설계/08_프롬프트_및_응답_설계서.md) 에서 다룹니다.

## 4. 유형 × 전략 매트릭스 (측정 결과)

Recall@5, 평가 세트 38건, 로컬 LSA 임베딩 기준

| 전략 | 전체 | A 사실 | B 숫자 | C 버전 | D 다중홉 | E 동의어 | MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| keyword | 0.701 | 0.800 | **1.000** | 0.400 | 0.444 | 0.667 | 0.645 |
| vector | 0.575 | 0.800 | 0.400 | 0.400 | **0.556** | 0.500 | 0.515 |
| hybrid | 0.598 | 0.800 | 0.400 | 0.600 | 0.444 | 0.500 | 0.527 |
| semantic | 0.609 | 0.800 | **1.000** | 0.000 | 0.222 | 0.667 | 0.605 |
| **boosted** | **0.793** | 0.800 | **1.000** | **1.000** | 0.333 | 0.667 | **0.801** |
| agentic | 0.540 | 0.800 | 0.600 | 0.200 | 0.222 | 0.500 | 0.543 |
| **agentic+boost** | 0.713 | 0.800 | 0.600 | **1.000** | **0.556** | 0.500 | 0.707 |

### 4.1 이 표에서 읽어야 할 것

```
   ① 단일 전략이 «모든 유형»을 이기지 못한다
        boosted        전체 최고 (0.793) 이지만 다중홉은 0.333
        agentic+boost  다중홉 최고 (0.556) 이지만 전체는 0.713

   ② «하이브리드가 항상 낫다»는 거짓이다
        숫자 정밀도에서 keyword(1.000) > hybrid(0.400)

   ③ 가장 큰 개선은 «모델»이 아니라 «도메인 지식»이었다
        권위 가중 하나로 Recall +30 %, MRR +32 %
```

> 🔑 **결론: 질의 유형을 판별해 전략을 라우팅해야 한다.**
> Azure 의 `retrievalReasoningEffort`(minimal/low/medium)가 이 역할을 합니다.
> → [설계/07](../설계/07_Agentic_검색_설계서.md)

## 5. 질의 라우팅 설계 (제안)

```
        사용자 질의
             │
             ▼
      ┌──────────────┐
      │ 복잡도 판별   │  ① 여러 측면을 묻는가 (급여«와» 평가)
      └──────┬───────┘  ② 조건이 여럿인가 (3년차 «AND» 개발직)
             │          ③ 접속 표현이 있는가
      ┌──────┴───────┐
      ▼              ▼
   단순 질의       복잡 질의
      │              │
      ▼              ▼
  boosted        agentic+boost
  (빠르고 쌈)     (느리고 비싸지만 다중홉에 강함)
```

| 라우팅 | Azure 대응 | 비용 | 적합 유형 |
| --- | --- | --- | --- |
| 단순 | `retrievalReasoningEffort: minimal` | 최소 (LLM 계획 없음) | A · B · E |
| 보통 | `low` (기본값) | 중간 | C · F |
| 복잡 | `medium` | 높음 (반복 단계) | D |

> ⚠️ 이 라우팅 규칙은 **아직 검증하지 않았습니다.**
> 복잡도 판별의 정확도를 측정한 뒤에야 «라우팅이 이득»이라고 말할 수 있습니다.

## 6. 실사용 질의 분포 (가정 → 검증 필요)

| 유형 | 가정 비중 | 근거 |
| --- | ---: | --- |
| A 사실 조회 | 55 % | 대부분의 문의는 단순 절차·담당 확인 |
| E 동의어·구어 | 20 % | 직원은 규정 용어를 쓰지 않는다 |
| B 숫자 정밀도 | 10 % | 한도·일수 확인 |
| D 다중 홉 | 7 % | 복합 상황 문의 |
| C 버전 충돌 | 4 % | 제도 개정 직후 집중 |
| G 범위 밖 | 3 % | |
| F 권한 제한 | 1 % | |

> ⚠️ **이 분포는 가정입니다.** 실제 구축 시 반드시 기존 문의 로그로 대체해야 합니다.
> 분포가 틀리면 «어디에 투자할지»가 틀립니다.
> 예: 다중 홉이 실제로 30 % 라면 에이전트 검색이 필수가 되고,
> 1 % 라면 그 비용을 쓸 이유가 없습니다.
