# 05. RAG 아키텍처 대안 분석

> **목적** — "RAG 로 하자"는 결론이 **기본값이 아니라 선택의 결과**임을 보입니다.
> 대안을 같은 요구사항에 적용해 보고, 무엇을 얻고 무엇을 잃는지 명시합니다.

## 1. 후보 5가지

### 1.1 ① 검색만 (RAG 없음)

```
   질의 → 키워드 검색 → 문서 목록 제시 → 사용자가 직접 읽음
```

| 장점 | 단점 |
| --- | --- |
| 가장 단순·저렴. LLM 비용 0 | 사용자가 여러 문서를 읽어야 한다 |
| **환각이 원천적으로 불가능** | 구어체 질의를 못 받는다 |
| 출처가 명확 | 다중 홉 질문에 답을 못 준다 |

### 1.2 ② 프롬프트에 전체 문서 넣기 (Long-context)

```
   질의 + 전체 문서 → LLM → 답변
```

| 장점 | 단점 |
| --- | --- |
| 검색 인프라가 필요 없다 | 코퍼스 287만 자 ≈ **312만 토큰**. 어떤 모델에도 안 들어간다 |
| 문서 간 관계를 LLM 이 본다 | 들어가더라도 질의마다 전체 비용 |
| | 문서가 늘면 즉시 한계 |

> ⚠️ 소규모(문서 수십 건)에서는 **진지한 대안**입니다. 이 프로젝트에서는 규모가 배제합니다.

### 1.3 ③ 파인튜닝

```
   문서로 모델을 재학습 → 질의 → 모델이 «기억»에서 답변
```

| 장점 | 단점 |
| --- | --- |
| 추론 시 검색이 없어 빠르다 | **출처를 제시할 수 없다** ← 결정적 |
| 도메인 문체를 학습한다 | 규정이 바뀔 때마다 재학습 |
| | 어느 지식이 반영됐는지 확인 불가 |
| | 권한별 접근 제어 불가 |

> 🔑 **인사·총무 도메인에서 «출처 없는 답»은 쓸 수 없습니다.**
> "연차는 20일입니다"라고만 하면 직원이 근거를 확인할 수 없고, 담당자도 검증할 수 없습니다.
> → 파인튜닝은 **지식 주입**이 아니라 **문체·형식 학습**에 쓰는 것이 맞습니다.

### 1.4 ④ Naive RAG (벡터 검색만)

```
   질의 → 임베딩 → 벡터 검색 → 상위 K → LLM → 답변
```

| 장점 | 단점 |
| --- | --- |
| 구현이 단순 | **숫자·고유명사에 약하다** (측정: 숫자정밀도 Recall 0.400) |
| 구어체·동의어에 강하다 | 필터가 없으면 폐지 문서가 섞인다 |
| | 다중 홉 질문에 약하다 |

### 1.5 ⑤ Hybrid + Agentic RAG (선택)

```
   질의 → [복잡도 판별]
            │
            ├─ 단순 → 하이브리드(BM25+벡터+RRF) → 재순위 → 권위가중 → LLM
            └─ 복잡 → 쿼리분해 → 병렬 하이브리드 → 합성 → LLM
```

| 장점 | 단점 |
| --- | --- |
| 유형별 약점을 서로 보완 | 구성 요소가 많아 운영이 복잡 |
| 출처·필터·권한 모두 지원 | 에이전트 경로는 지연·비용이 크다 |
| 다중 홉 대응 | 튜닝할 파라미터가 많다 |

## 3. 결정 — Hybrid + Agentic RAG

### 3.1 지불하는 대가 (명시적으로)

| 대가 | 크기 | 완화 |
| --- | --- | --- |
| 구성 요소가 많다 | 높음 | Azure 관리형 서비스로 운영 부담 이전 |
| 튜닝 파라미터가 많다 | 높음 | **평가 세트로 근거 있게 조정** |
| 에이전트 경로 지연 | 중간 | 질의 라우팅 — 복잡 질의에만 적용 |
| 에이전트 경로 비용 | 중간 | `retrievalReasoningEffort` 로 통제 |
| 환각 위험이 남는다 | **높음** | 근거 임계값 + 시스템 프롬프트 + 근거성 평가 |

> ⚠️ **마지막 항목이 이 아키텍처의 근본 한계입니다.**
> ①검색만 은 환각이 원천적으로 불가능하지만, ⑤는 LLM 이 답을 «쓰기» 때문에 언제나 위험이 있습니다.
> 완전히 없앨 수는 없고, **줄이고 감지**할 수 있을 뿐입니다.

### 3.2 되돌릴 조건

| 신호 | 의미 | 조치 |
| --- | --- | --- |
| 환각 사고가 반복된다 | LLM 생성의 위험 > 편의 | **①검색만** 으로 후퇴, 문서 목록만 제시 |
| 다중 홉 질의가 1 % 미만 | 에이전트 비용이 낭비 | 에이전트 경로 제거, 하이브리드만 |
| 문서가 수십 건으로 줄었다 | 검색 인프라가 과함 | **②Long-context** 검토 |
| 응답 지연 불만이 크다 | 에이전트 경로가 병목 | 라우팅 임계값 상향 |

## 4. 검토했으나 «지금은» 쓰지 않는 기법

| 기법 | 무엇인가 | 왜 지금은 안 쓰는가 | 재검토 조건 |
| --- | --- | --- | --- |
| **GraphRAG** | 문서에서 엔터티·관계 그래프를 만들어 검색 | 구축·유지 비용이 크다. 이 도메인은 «규정 → 조항»의 단순 계층이라 그래프 이득이 작다 | "A 제도와 B 제도의 관계" 같은 질의가 늘면 |
| **HyDE** | 가상 답변을 생성해 그것으로 검색 | LLM 호출이 1회 늘어 지연·비용 증가. 하이브리드로 충분 | 벡터만 쓸 수밖에 없는 상황이 되면 |
| **Query Expansion** | 질의를 동의어로 확장 | Azure 동의어 맵으로 대체 가능 | 동의어 맵 관리가 한계에 이르면 |
| **Re-ranking 모델 자체 호스팅** | 교차 인코더를 직접 운영 | Azure 시맨틱 랭커가 관리형으로 제공 | 한국어 성능이 부족하다고 «측정»되면 |
| **Parent-Child 검색** | 청크로 찾고 부모 문서를 반환 | 이 코퍼스는 문서가 짧아 이득이 작다 | 문서가 길어지면 (매뉴얼 비중 증가 시) |
| **Multi-index 라우팅** | 인사/총무 인덱스를 분리 | 하나로 충분. 나누면 팬아웃 비용 증가 | 문서 10만 건 초과 또는 권한 체계가 완전히 갈리면 |
| **Semantic Caching** | 유사 질의의 답을 재사용 | 규정이 바뀌면 캐시가 «틀린 답»이 된다 | 동일 질의 반복률을 측정한 뒤 |

> 🔑 **«쓰지 않기로 한 결정»도 설계입니다.**
> 나중에 "왜 GraphRAG 안 썼지?"라는 질문에 «검토했고 근거가 있다»고 답할 수 있어야 합니다.

## 5. ADR

### ADR‑001 · Hybrid + Agentic RAG 채택

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **일자** | 2026‑08‑29 |
| **맥락** | 인사·총무 문의 응대. 출처 제시와 권한 제어가 필수이며, 질의 유형이 7가지로 갈린다 |
| **결정** | 하이브리드 검색을 기본으로, 다중 홉 질의에 에이전트 검색을 적용한다 |
| **근거** | 요구사항 판정표 §2 — 11충족/0미충족. 유형별 실측값 ([분석/03](03_질의_유형_분석.md) §4) |
| **결과** | ➕ 유형별 약점 보완·출처·권한 ➖ 운영 복잡도·튜닝 부담·환각 위험 잔존 |
| **대안** | ①검색만(사용성 부족) ②Long-ctx(규모 불가) ③파인튜닝(출처 불가) ④Naive(숫자 정밀도 부족) |
| **되돌릴 조건** | §3.2 의 4가지 신호 |

### ADR‑002 · 문서 유형 권위 가중 도입

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 |
| **맥락** | FAQ·문의이력이 코퍼스의 69 %. 권위 있는 규정·안내서가 수적으로 압도당한다 |
| **결정** | 문서 유형별 가중치를 순위에 곱한다 (규정 2.0 … 문의이력 0.8) |
| **근거** | **측정: Recall@5 0.609 → 0.793 (+30 %), MRR 0.605 → 0.801 (+32 %)** |
| **결과** | ➕ 이 프로젝트 최대 단일 개선 ➖ 가중치가 도메인 지식이라 조직마다 다시 정해야 함 |
| **되돌릴 조건** | FAQ 가 «공식 답변»으로 승격되는 거버넌스가 생기면 재조정 |

### ADR‑003 · 질의 라우팅 (단일 전략 미채택)

| 항목 | 내용 |
| --- | --- |
| **상태** | 승인 (검증 미완) |
| **맥락** | 단일 전략이 모든 유형을 이기지 못한다 — boosted 전체 최고(0.793)지만 다중홉 0.333, agentic+boost 다중홉 최고(0.556)지만 전체 0.713 |
| **결정** | 질의 복잡도를 판별해 전략을 라우팅한다 |
| **근거** | 유형 × 전략 매트릭스 ([분석/03](03_질의_유형_분석.md) §4) |
| **결과** | ➕ 유형별 최적 전략 사용 ➖ 판별 오류 시 오히려 나빠질 수 있다 |
| **⚠️ 미검증** | **라우팅 판별 정확도를 아직 측정하지 않았다.** 측정 전에는 «라우팅이 이득»이라고 단정할 수 없다 |
